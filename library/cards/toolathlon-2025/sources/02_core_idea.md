Toolathlon's central contribution is to bind realistic cross-application tasks, executable environment setup, full tool-interaction episodes, and a task-specific deterministic final-state evaluator into one benchmark contract. The paper models a task as a POMDP over state, action, observation, transition, reward, and instruction; its practical implementation narrows the reward to execution-based success after the agent has finished interacting (Paper §2.1, p. 3; §2.4, p. 5).

The task object contains a concise or fuzzy instruction, selected MCP servers and local tools, initialization assets, and static or dynamically retrieved ground truth. The trajectory object contains sequential assistant decisions, tool calls, tool responses, and evolving workspace/application state. In the checked current code, `traj_log.json` also records resolved configuration, request and session identifiers, timestamps, execution status, statistics, and costs; `eval_res.json` records `pass` plus details or a failure. These current filenames and fields describe repository commit `3b647e6`, not a claim that every paper-era run used the identical serialization.

The feedback contract is deterministic terminal evaluation. Each task has a manually written evaluator that compares the resulting workspace or application state with a static snapshot or real-time ground truth. `TaskEvaluator` returns `pass=true` or `false` after a successful execution and `pass=null` when execution status is not `SUCCESS`. Agent-loop termination, a final natural-language answer, or `claim_done` is therefore not the terminal predicate for correctness; only the post-execution evaluator establishes benchmark success.

State-action detail and supervision granularity must not be conflated. The log preserves state-action-tool events, which makes state-action-level analysis possible, but the disclosed reward is one terminal binary outcome for the full episode. No per-step correctness label, critique, preference pair, dense reward, or process-reward trace is reported. The evaluator can observe the state fields its task-specific code queries; it cannot certify unqueried side effects, user satisfaction, semantic quality outside the predicate, or whether an alternative valid state was wrongly rejected.

The closest Atlas comparisons are MCP-AgentBench for MCP-centered agent evaluation, τ2-bench for stateful tool interaction, and TheAgentCompany for long-horizon work in a multi-application environment. Toolathlon's distinguishing contract is the combination of 108 fuzzy workflows, a broad MCP/local-tool surface, initialized cross-application state, and one deterministic end-state checker per task. The direction signal is not that programmatic checking is new, but that environment state and evaluator version must be treated as first-class parts of an agent-trajectory record.
