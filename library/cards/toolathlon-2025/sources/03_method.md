**Inputs and task construction.** Researchers and senior computer-science undergraduates first sourced needs freely from more than 50 candidate applications and then targeted important underrepresented applications. They converted those needs into concise, fuzzy tasks whose intended behavior must be inferred from the environment, examples, documents, or templates. After several weeks of checking, filtering, and refinement, the final pool contained 108 tasks. The paper reports 4–6 graduate-student hours to implement a task; 5–6 experienced authors then reviewed and revised each task for about five hours per task in each checking round, followed by benchmark-wide cross-checking and bug fixes (Paper §§3.1–3.2, pp. 5–7). Rejected counts, per-task source URLs, contributor identities, reviewer agreement, adjudication records, and an acceptance threshold are unknown.

**Executable task bundle.** A released task directory may include English or Chinese task and system-level instructions, `task_config.json`, preprocess scripts or an initial workspace, a ground-truth workspace/state, and `evaluation/main.py`. Configuration selects fewer than 10 relevant MCP servers for a task but loads every tool exposed by each selected server; configured local tools may include Python execution, web search, `claim_done`, `sleep`, overlong-output navigation, and context-history management. Across the paper snapshot there are 32 MCP-server/application surfaces, 604 MCP tools, and 16 local tools. 72 tasks have explicit state initialization (Paper Table 2, p. 6; §2.4; official repository `tasks/finalpool/`).

**Interaction and generation.** The evaluated model, not a teacher, generates the trajectory by alternating messages and tool calls with remote services and locally containerized software. Paper experiments use OpenAI Agents SDK v0.0.15, tool-error handling, truncation of tool outputs longer than 100K characters with 10K-character paging, and context-history management, with at most 100 turns per task (Paper §2.2 and Appendix B, pp. 14–15). The current repository additionally supports containerized and decoupled host loops and preliminary Claude Agent SDK integration; these later features must not be back-projected into the paper setup. The paper does not disclose one common temperature or normalized token/compute budget across providers.

**Logging and outputs.** At current repository commit `3b647e60713703d653584c23ff185e3b6cd67722`, the primary episode log is `traj_log.json`, not JSONL. It stores resolved task config, request and session identifiers, initial and completion times, tool catalog/choice, execution status, message history with assistant `tool_calls` and tool responses, interaction/tool-call counts, token statistics, costs, resume metadata, and history path. The evaluator writes `eval_res.json` with `pass=true/false/null` plus details or failure; `eval_stats.json` aggregates run-level success and turn statistics. Exact paper-era field parity and raw archive-level completeness are unknown.

**Verification and selection.** After interaction, a unique manually crafted task evaluator checks final state against static ground truth or dynamically retrieved real-time truth. Only this post-execution check supplies the binary terminal outcome; no step reward is disclosed. The paper evaluates all attempted episodes rather than selecting trajectories for training. The later Hugging Face card describes full success and failure trajectories rather than success-only filtering, but raw gated archives were not inspected, so corrupt-run handling, omissions, and exact per-episode completeness remain unknown.

**Evaluation use and release boundary.** In the paper protocol, 17 models each run all 108 tasks three times. Toolathlon-Verified, released on 2026-06-30 after substantial changes to prompts, ground truths, evaluators, and infrastructure, packages three 108-task runs for each of 10 newer models, nominally 3,240 task-run episodes. Its current defaults include a 5,400-second task timeout and 64K maximum output length per agent turn; temperature and top-p inherit provider defaults. The official dataset policy permits benchmark evaluation, reproducibility, auditing, error analysis, and contamination research, and explicitly forbids pretraining, continued pretraining, SFT, preference/RL post-training, distillation, synthetic training-data generation, and benchmark-answering retrieval.

Reproduction must separately pin arXiv v2, ICLR/OpenReview metadata, repository commit `3b647e6`, the task container image, dependencies, credentials and reset procedures, remote-service versions, each task/evaluator revision, provider endpoints/defaults, and Hugging Face revision `01deb377e5179d654e4282f62c0c336539480837`. No single immutable manifest binds those components, and the repository has no Toolathlon-Verified tag or GitHub Release.
