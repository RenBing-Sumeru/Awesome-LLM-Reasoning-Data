The central construction is an iterative data flywheel around continual pre-training (CT), supervised fine-tuning (SFT), and reinforcement learning (RL). It starts from Seed-thinking-1.6. The current RL policy generates new environment-interaction episodes; a validation function sends higher-quality episodes to SFT and lower-quality episodes to CT, after which the CT-to-SFT-to-RL cycle repeats. The report does not disclose the validation function, routing threshold, yields, or record-level routing decisions.

The episode abstraction follows ReAct. A step interleaves a reasoning trace, an action, and an observation. Actions include mouse, keyboard, scrolling, PyAutoGUI or ADB operations, and SDK functions for terminals, files, software development, and other tools. Working Memory retains recent steps at higher fidelity, while Episodic Memory compresses earlier intentions and outcomes. The exact context-window policy and memory serialization are unknown.

The environment is part of the data object. Cloud VMs cover Windows, Ubuntu, and Android; browser and game sandboxes expose visual observations and selected runtime state; a unified SDK handles allocation, initialization, interaction, screenshots or recordings, evaluation, and resource release. The report says the VM cluster reaches several thousand instances and several thousand queries per second, but it does not release VM images, dependency locks, browser builds, reset scripts, or session logs.

Feedback is domain-dependent. Games use deterministic functions and binary correctness; GUI-Browsing uses reference-answer judging; GUI-General uses UI-TARS-2 as a generative outcome reward model over the text history and last five screenshots. The reported game JSON carries scalar reward, termination flag, game version, and verification checksum, but the paper does not state that this schema is used for all GUI episodes or release any such records.
