模型谱系从具有 128K 上下文的 DeepSeek-V3.1-Terminus 开始。密集预热阶段只训练 DSA 索引器，共 1,000 步，每步 16 个 128K token 序列，总计 2.1B token。随后稀疏继续预训练为每个查询选择 2,048 个键值 token，并用 943.7B token 联合训练主模型和索引器。报告称两个阶段的数据分布与 V3.1-Terminus 的 128K 扩展一致，但没有说明语料来源、许可或去污染情况。

表 1 的智能体 RL 共包含 85,267 个提示：代码智能体 24,667 个，使用真实环境和抽取提示；搜索智能体 50,275 个，使用真实搜索工具和合成提示；通用智能体 4,417 个，环境与提示均为合成；代码解释器 5,908 个，使用真实 Jupyter 环境和抽取提示。这些是任务数，不是轨迹数；尝试次数、保留轨迹、奖励记录和真实环境唯一数量均未知。

搜索合成先从网页语料中采样长尾实体，通过搜索构造问题，再由不同配置生成候选答案，并由具有搜索能力的验证智能体进行多轮检查。只保留参考答案经确认且候选答案错误的样本，随后加入经过筛选的 helpful-RL 提示，并由带评分细则的生成式奖励模型打分。代码智能体构造从数百万 GitHub 问题—拉取请求对中挖掘，要求问题描述、相关金补丁与测试补丁齐全，再由自动搭建智能体构建环境。只有应用金补丁后至少一个目标测试由失败变为通过、且没有原本通过的测试变为失败，环境才算成功；不同语言与测试框架统一解析 JUnit 输出。

通用智能体合成会建立沙箱数据库、任务特定函数工具、任务、解答函数和 Python 验证函数。解答只能通过工具或逻辑计算，不能直接访问数据库；生成者逐步提高难度，并在需要时扩充工具集。经过 RL 尝试后，仅保留 pass@100 非零的任务，得到 1,827 个环境和 4,417 个任务。代码解释器任务通过 Jupyter 覆盖数学、逻辑和数据科学，但其来源、筛选方式和筛选前规模没有详细披露。

Scaling GRPO 修改了优化契约：使用重要性加权估计纠正 KL 偏差；屏蔽策略偏离过大的负优势序列；训练时复用采样阶段选择的 MoE 路由；保留 top-p 或 top-k 采样掩码，使采样和更新的动作空间一致。论文公开了公式，但实际组大小、奖励权重、阈值、优化器参数、批量规模和 rollout 账本均未披露。
