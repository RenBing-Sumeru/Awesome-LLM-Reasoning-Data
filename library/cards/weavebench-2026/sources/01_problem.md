The primary evidence is arXiv:2606.09426v3, revised 2026-07-06, together with the official project, organization-owned repository, Hugging Face release, and trajectory gallery. No formal conference venue was verified. WeaveBench addresses a specific computer-use evaluation gap: many desktop benchmarks allow one interaction channel to substitute for another or can be completed through short, single-application paths, whereas real work often requires a long chain in which GUI-only applications, shell/code tools, and multiple application states depend on one another.

The benchmark contains 114 English tasks across 8 work domains and 23 subcategories. Admission requires all three properties: P1, channel non-substitutability, means at least one GUI atom and one CLI atom cannot be replaced by the other channel; P2 requires multiple interleaved GUI/CLI phases rather than a short sequence; P3 requires linked state across multiple applications. The authors report that all 114 tasks contain at least one GUI and one CLI atom, 103 contain a non-anchor atom, and 50 contain at least two atoms on each side. These are author construction audits, not independent correctness checks (Paper section 3.1; Appendix A.1-A.2, Table A2).

The reusable evaluation object has two joined layers. A task bundle contains the instruction, initial environment, seed data, required assets, expected deliverables, expert reference trajectory, and hidden verification anchors. An evaluated episode adds the frozen Ubuntu VM state, screenshots and tool outputs, GUI plus CLI/file/code/browser actions, full `chat.jsonl`, staged deliverables, logs, judge evidence, and terminal scalar score. The paper reports that the best live rollout per task has a median of 76 tool calls and that 113 of 114 best rollouts exceed 20 calls; these describe observed rollouts, not a minimum task specification (Paper sections 3.2-3.4; Appendix A.2 and B).

This object belongs in `environment_agent_trajectory_data` because state, observation, action, environment response, reset, and terminal judgment are jointly defined. It also belongs in `benchmarks_evaluation_surfaces` because the release turns the full episode into a mixed environmental and model-judgment feedback surface. It does not establish a training corpus: the paper reports evaluation only, and the public best-trajectory gallery does not document a complete immutable set of successful, partial, failed, and hack-flagged episodes.
