**Inputs and admission.** Domain experts first define cooperation archetypes, then source candidate workflows from public GitHub/GitLab issues and pull requests, Stack Exchange, Reddit, forums, documentation, postmortems, design mocks, bug trackers, YouTube, and OpenClaw user requests. A candidate is admitted only if P1 makes at least one GUI and one CLI atom non-substitutable, P2 requires multiple interleaved phases, and P3 links state across applications. The paper reports 174 source URLs from 82 hostnames; 94 are labeled user-pain URLs, and 91 of 114 tasks include at least one such URL (Appendix A.4).

**C1-C4 construction.** C1 uses the archetypes and public artifacts to propose real workflows. C2 packages each into a self-contained task bundle with initial environment, seed data, required assets, user instruction, expected deliverables, expert reference trajectory, and verification anchors. C3 applies independent blind review for clarity, reproducibility, P1-P3 compliance, and anchor faithfulness. C4 pilots each task with three agents; failures attributable to task ambiguity or environment defects trigger revision. The paper does not fully disclose pilot identities, numeric sampling settings, or the complete acceptance log, so these remain unknown rather than inferred (Paper section 3.2 and Figure 2).

**Environment and interaction.** A task runs in a containerized Ubuntu/Linux desktop VM restored from a frozen qcow2 snapshot and rolled back after the episode. Task-local network, output limits, and wall-clock limits constrain execution. The host runtime supplies CLI, file, code, and browser capabilities, while a PyAutoGUI-backed plugin exposes GUI perception/action. The paper describes one screenshot primitive and nine actuation primitives; current code exposes a batched `__computer__` tool with aliases and automatic screenshot persistence, making exact tool enumeration version-sensitive (Paper section 4.1; official architecture and GUI-plugin implementation).

**Episode archive and judgment.** The harness records the task and state, screenshot and shell/tool observations, GUI and CLI/code/file/browser actions, full `chat.jsonl`, deliverables, logs, and terminal status. The evaluated agent is separated from hidden anchors. After the run, the isolated OpenClaw judge actively re-fetches trace and environment evidence, scores requirement clauses and eight dimensions, checks nine shortcut patterns, and emits the hack decision plus scalar score. A catalogued shortcut at confidence at least 0.85 with verbatim trajectory evidence forces zero; otherwise the final score is `min(mean_dimension_score, deliverable_correctness)` (Paper equation 1 and Appendix B.2-B.5).

**Evaluation protocol and outputs.** A complete condition covers all 114 tasks. The fixed-runtime sweep compares model APIs through OpenClaw; the harness sweep evaluates strong APIs with OpenClaw, Codex CLI, Claude Code, and Hermes. Output records support PassRate, score, interface ablations, and failure coding. Paper v3 defines PassRate at score at least `τ = 0.8`, while current `docs/REPRODUCE.md` states at least 0.5. Paper v3 Appendix B.1 names GPT-5.5 as the fixed judge, while the same current reproduction document says the paper used Claude Opus 4.7; current setup documentation also describes a GPT-5.5 default. Both conflicts must remain visible.

The current dataset main observed during curation is `fcb478b0bdee19a7f01c1d3c2f648e3ed91abafa`; post-pin history appears to change README/project/arXiv metadata, but paper reproduction should still use the official pin. No GitHub commit binding paper tables, prompt, runtimes, and judge model was verified. The method is evaluation-only: no SFT, RL, preference, or reward-model training on WeaveBench is reported.
