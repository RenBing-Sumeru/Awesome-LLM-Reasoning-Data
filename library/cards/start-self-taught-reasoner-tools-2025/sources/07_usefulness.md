For the **Data Construction and Open Release Recipes** track, START is useful now as a construction-pattern and audit reference. It is **blocked for direct data, model, or environment reuse** because none of those artifacts is public.

- **Prototype corrective-trajectory acquisition.** Reimplement the before/after intervention design: preserve the original attempt, exact hint, insertion point, Python action, observation, revision, final answer, and both correctness decisions. Treat the pair of trajectories—not only the accepted answer—as the data object.
- **Compare selection policies.** Under fixed prompts, rollout count, decoding budget, base checkpoint, and SFT compute, compare wrong-to-correct selection with random accepted trajectories, correctness-only selection, diversity selection, and retained failures. Measure checker false accepts and false rejects using an independent audit set.
- **Study intervention cost.** Report all four transition cells from Table 5 with denominators and confidence intervals. Optimize net correction rather than wrong-to-correct count alone, because a method that repairs some failures while converting correct answers to wrong ones can still harm overall utility.
- **Separate unique prompts from trajectories.** Publish counts for source prompts, unique prompts after deduplication, sampled candidates, executed candidates, accepted trajectories, rejected trajectories, and final SFT records. START's 10K and 40K figures should be treated as reported sample counts until that separation exists.
- **Build a replayable Python contract.** Pin a container digest, interpreter and package versions, tool schema, timeout, resource limits, filesystem and network policy, state reset, exception schema, and deterministic seeds. Store stdout, stderr, exit status, and tests for every candidate.
- **Make the verifier inspectable.** Release answer extraction and equivalence rules, coding tests, repetition detector, execution-error handling, thresholds, checker versions, per-record outputs, and rejection reasons. A terminal predicate should be reproducible independently of the training code.
- **Test hint design as a controlled variable.** Compare the six functions, linguistic variants, insertion locations, and repeated-hint budgets with fixed generation compute. Preserve hint IDs and paraphrase provenance so gains are not attributed to an undocumented prompt mixture.
- **Use the reported failures as baselines.** The 10.4% correct-to-wrong, 67.0% wrong-to-wrong, hard-code +2.0 point result, and non-monotonic repeated-hint behavior are useful minimum audit targets for a new tool-data recipe.
- **Require a release ledger before training reuse.** Reconcile 49,969 versus 46,969 and 40K versus 36,895; attach upstream IDs, split membership, decontamination results, source licenses, generator revisions, seeds, filter decisions, hashes, and accepted/rejected manifests.

The paper can also guide evaluation of inference-time tool activation, but Hint-infer should not be treated as proof that a model has learned robust agent behavior: a forced Python call is weaker evidence than correct, necessary, safe, and reproducible interaction. The unreleased START objects are unsuitable for PRM, preference learning, or RLVR replay because they expose no step labels, preference pairs, scalar rewards, or public verifier implementation. They should not be reused as an evaluation set because the prompts are described as training sources and exact overlap metadata is absent.
