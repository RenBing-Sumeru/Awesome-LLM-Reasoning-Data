The construction and evaluation pipeline is:

1. **Source and task design.** The authors define banking, airline, and retail workflows. The paper reports 50 original banking tasks, 50 reused tau-bench airline templates, 114 reused tau-bench retail templates, and additional original scenarios created through human writing and LLM assistance. The disclosed components sum to 314 rather than 315, so one record or the meaning of the “50 newly generated scenarios” statement requires release-level reconciliation.
2. **Schema-guided generation.** Appendix A describes domain analysis, tool definition, task-template creation, persona integration, and goal-shift integration. An undisclosed generator receives a JSON schema plus five Markdown reference files and returns ten candidate tasks per batch. Its model, prompt, decoding settings, number of batches, acceptance yield, and rejected candidates are unknown.
3. **Manual filtering and QA.** Each generated batch is reviewed for valid tool parameters and database consistency, enough `known_info` for the user simulator, and `communicate_info` restricted to facts derived from tool responses. Appendix B additionally reports manual review of 10% of tasks, criteria cross-checking, inter-rater reliability analysis, and regular updates, but gives no annotator count, sampling rule, reliability statistic, adjudication protocol, or revision log.
4. **Goal-shift annotation.** Ordered goals, initial state, allowable actions, assertions, information to communicate, and `required_shifts` are attached to each task. Transitions follow progression rules and markers remain hidden from the evaluated assistant.
5. **Episode generation.** A persona-conditioned LLM user simulator reveals only known information and follows the ordered goals; the evaluated assistant converses and alone calls the controlled domain tools. The tau-bench-derived harness allows one tool call per turn, validates calls against API responses, and resets environment state between independent runs.
6. **Post-hoc scoring.** The harness calculates TSR, TUE, and TCRR from communication, actions, assertions, parameters, API results, and exact-call patterns. `gpt-4o-mini` supplies the communication judgment. An unspecified LLM detector identifies post-shift acknowledgment, relevant-tool, and outcome turns for GSRT.
7. **Outputs and use.** The output is a scored episode/shift record and aggregate benchmark result. The standard proprietary-model protocol runs every task three times; Appendix E uses one run per domain for Qwen2.5-14B-Instruct. The paper reports evaluation only—no SFT, preference learning, reward-model training, RLVR, process supervision, or agent training.

Reproduction requires more than the declarative task JSON. A credible replay freeze must pin the exact tau-bench-derived harness commit, banking/airline/retail database snapshots and APIs, user-simulator prompt/model/seed, evaluated-model API snapshots, judge and shift-detector prompts/snapshots, tool schemas, turn/token/retry budgets, sampling parameters, per-run seeds, and metric code. None of these are fully pinned in the accessible sources.

The official MTI-LLM OpenReview record lists a supplementary ZIP that the paper says contains the full benchmark, evaluation-harness configurations, and experimental artifacts. The ZIP was not retrievable during curation. Its file inventory, task-to-sequence manifest, code revision, dependency lock, database snapshot, train/dev/test or old/new split manifest, checksums, data/code license, retained success/failure runs, and deterministic replay instructions must therefore remain unknown rather than inferred.
