Scale evidence must distinguish scenarios from serialized variants. Paper Table 2 reports 2,651 train and 471 test scenarios, with test counts of 118 easy, 201 medium, and 152 hard and train counts of 666, 1,130, and 855. Exhaustive inspection of the released Parquet files agrees: each single- or multi-choice variant has the same 3,122 unique task IDs, split 2,651/471 with no ID overlap. The two variants together contain 6,244 rows, but counting them as unique tasks would double the benchmark. Section 3.5 instead says 417 test points; the current release and Table 2 support 471, so 417 is retained as an unresolved paper inconsistency rather than silently corrected.

The paper also uses three different scale descriptions. Its introduction claims 4K+ proposed scenarios; Figure 1 and Section 3.5 say random combination can enable 10K+ possible scenarios; the verified public release contains 3,122 unique IDs. The 10K+ figure describes construction capacity, not released size, and the 4K+ headline is not reconciled with the release. These counts provide evidence about recipe and packaging, not about semantic correctness or data quality.

Under the paper's single-choice setup, GPT-4o obtains score 0.329, valid-search rate 82.48%, valid-action rate 27.82%, and active preference elicitation 24.06% in Table 3. The authors report that no tested model actively elicits 31% of preferences. Section 5 further reports that adding turns does not consistently improve performance and that pass-k raises the maximum score but not the average; qualitative failures include early guessing, repeated or off-topic dialogue, and lost aspect state. These are author-reported, single-run results under a GPT-4o simulator/judge, maximum 20 turns, temperature 0, and the stated models. They were not independently reproduced and cannot certify task labels, judge validity, or training value.

Repository evidence establishes a mixed evaluator. Search and clarification decisions call GPT-4o prompts, while option-ID rewards and termination are implemented in code. The paper's Figure 8 numbers judge types as 1=available preference, 2=unavailable, 3=vague, 4=normal; the public prompt/code instead uses 1=normal, 2=available, 3=unavailable, 4=vague, and commit inspection shows this mapping from the first public repository commit. This is material documentation drift because an implementation copied from the figure can route classifications incorrectly.

Release inspection also produces direct negative evidence. Default passive elicitation uses unseeded `random.choice`; an official task record states that two restaurant options have the same cost level and either could be chosen, yet only R8 is labeled `best_id`, so the other correct choice receives 0.8 rather than 1.0. No full run archive, raw judge responses, dropped-run ledger, independent verifier calibration, external overlap audit, or exhaustive 3,122-task semantic label audit was found. Benchmark scores therefore measure agents under this evaluator; they are not proof that the released tasks or rewards are high-quality training data.
