For the assigned `environment_agent_trajectory_data` track, UserBench is most useful as a version-pinned evaluation environment and an audit case for how task specifications become runtime episodes. A researcher can map the initial underspecified request to an action schema, simulated-user and search observations, elicited-preference state, option labels, per-step reward, and termination. The key track lesson is that the reusable release stops at task/environment specifications: episodes can be generated, but the paper's actual successful and failed rollouts are not released.

The construction pipeline provides a benchmark recipe. Builders can represent preferences separately from their indirect utterances, compose them across aspects and difficulty tiers, generate correct/wrong/noise option pools, wrap task IDs in environment-launch records, and expose clarification/search/answer actions through a Gym interface. A sound adaptation should additionally publish construction prompts, model versions, seeds, retries, rejected items, human review assignments, split logic, semantic deduplication, per-record lineage, and data-specific rights.

The mixed feedback contract supports verifier research. Investigators can compare GPT-4o search/action classifications with blinded human labels, repeat judgments to estimate variance, swap judge models or prompts, mutate search arguments to measure boundary errors, and test whether option-ID rules reward semantic ties incorrectly. State-transition tests should distinguish successful completion from one-choice termination and should exercise passive elicitation under fixed seeds.

The public task labels and code also support failure and contamination audits. Analysts can search for exact and semantic train/test duplicates, inspect whether public `best_id`, correct/wrong/noise labels and evaluator prompts enable shortcuts, test early guessing and aspect-state failures, and compare active versus passive preference acquisition. Count reconciliation should treat 417, 471, 4K+, 10K+, 3,122, and 6,244 as different claims with different units rather than selecting the largest number.

Safe reuse is **evaluation and audit only**, pinned to commit `80506d2` with explicit task files, dependencies, judge/simulator endpoint, prompts, seeds, and environment configuration. Training reuse is blocked pending a data-specific license and lineage review, split/decontamination audit, complete label and verifier calibration, and release of representative successful and failed trajectories with raw feedback. The presence of a train split or a Gym interface does not itself authorize or validate SFT/RL reuse.
