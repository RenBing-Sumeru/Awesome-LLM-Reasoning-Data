The closest construction baseline is the SWE-bench family: issue/pull-request extraction, repository checkout, environment setup, and gold-patch fail-to-pass validation already exist, but environment engineering and log interpretation require substantial manual work. SWE-Gym likewise packages executable software-engineering tasks and trajectories, using semi-manual dependency configuration.

SWE-Factory changes the construction interface in three concrete ways. It repairs binary test resources omitted by GitHub diffs; it assigns repository exploration, Dockerfile writing, evaluation-script writing, and execution analysis to four collaborating agents; and it standardizes test-status extraction around an exit-code marker. Execution feedback and retrieval of a successful same-repository/version recipe make environment construction iterative rather than one-shot.

The new data object is not merely an issue-patch pair: it links source task fields, an executable environment recipe, a fail-to-pass decision, and a full tool-interaction episode intended for SFT. The quality signal attaches to environment acceptance, not to individual reasoning steps. Public trajectory rows do not carry that signal, so the release does not provide process labels or auditable trajectory-level rewards.

The novelty is automation and lifecycle integration, not a new testing semantics, Docker substrate, SFT objective, or independent verifier. Scaling from 671 benchmark tasks to 2,809 training trajectories is useful engineering evidence, but the absent Appendix, row mappings, immutable images, and release manifest prevent the open artifacts from fully instantiating the paper's claimed end-to-end object.
