Repository-level feature addition requires more than producing a patch that happens to pass a narrow test. An agent must understand an issue, locate relevant code and tests, decompose the change into implementation tasks, order those tasks, edit the repository, and avoid regressions. Standard resolved-rate evaluation reveals the terminal outcome but not where this chain failed.

RACE-bench describes 528 feature-addition instances from 12 public Python repositories also used by SWE-bench. Each instance binds an issue-derived feature request and optional developer-discussion hints to a repository release/base commit, Docker setup, gold and test patches, fail-to-pass (FTP) and pass-to-pass (PTP) tests, and structured intermediate-reasoning references. RACE-bench Lite contains 100 of these instances.

The benchmark's intended episode begins from an isolated base-commit container. The agent receives the feature request and FTP tests, uses repository search, static analysis, editing, and test tools, and emits a final patch. No author-controlled code, dataset, container, evaluator, project, judge bundle, or trajectory release was verified, so this Card distinguishes paper-described objects from publicly reusable artifacts.
