终端 agent 的监督数据需要把推理与 shell 操作同可执行环境中不断变化的状态连接起来。这类数据采集成本高：一个 episode 可能需要新建容器、多轮交互、安装依赖、执行命令并检查最终状态。现有终端 agent 报告往往没有充分披露任务来源、未成功尝试、环境构建方式或过滤过程，因此难以判断真正进入训练的对象。

本文处理两个相互关联的缺口。构建层面的问题是：在缺少人类交互日志的情况下，如何同时获得广覆盖与终端专用任务。审计层面的问题是：如何区分论文实验使用的数据混合与实际可下载的行，以及当发布物没有规范化 verifier result 时应怎样解释“被保留”的轨迹。这里必须保持这些边界，因为论文研究了 490,520 条轨迹，而已确认公开的 corpus 只有 366,154 行；论文证据支持保留 incomplete 和 unsuccessful 行为，但公开行 schema 无法直接枚举这些 outcome 类别。
