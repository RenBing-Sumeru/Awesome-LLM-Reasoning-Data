- **Author-stated workload boundary.** The memory-bound premise applies to small and medium hardware/load. Large servers with hundreds or thousands of simultaneous requests become compute-bound, where token count again tracks cost; Appendix Table 4 empirically shows the latency increase with request count. (Paper §7; Appendix A.4)
- **Author-stated risk boundary.** The paper warns that scaling may degrade underrepresented domains and increase susceptibility to adversarial prompts, but evaluates only four math/science benchmarks and does not test those risks. (Paper §8)
- **Release and reproduction gap.** No author-specific code/configuration release, raw candidate branches, speculative-acceptance trace, prompt/run manifest, hardware description, runtime version, or raw latency log is linked. Consequently, aggregate timing curves cannot be independently replayed. The paper's blanket license statement does not replace artifact-specific revisions and licenses. (Curator inference from §9 and the official records.)
- **Feedback failures.** Majority voting can select a correlated wrong answer; confidence aggregation can inherit miscalibration. Undisclosed extraction, normalization, and tie rules can create false positives or false negatives. Because only aggregate selected-answer accuracy is reported, candidate-level verifier gaming or selector error cannot be audited. (Curator inference.)
- **Experimental and contamination limits.** Three repeats are reported for Tables 1 and 3, but seeds, decoding temperature, prompt order, and variance protocol are unknown. Decontamination is not discussed. The latency optimum is model-, task-, hardware-, runtime-, and load-specific, so it should not be treated as a portable policy. The prose/table mismatch for greedy steps (8–10 in §5.3 versus an 11-step s1.1-3B row in Table 2) also requires care.
