EnConda-Bench studies a concrete failure boundary for software-engineering agents: an agent may recognize that a README contains a dependency, command, path, ordering, or version error yet still fail to turn that diagnosis into a shell script that builds and tests the repository. The formal record is an ICLR 2026 Poster, while the Card retains year 2025 because arXiv:2510.25694v1 was submitted on 2025-10-29. This distinction matters because the checked repository commit, `86ab7858613b85f4a8316f3cda3c83086b8cf7c2`, dates from 2025-10-30 and predates the final conference revision.

The benchmark instance is a task record, not a released interaction episode. Paper-time evaluation combines a pinned Python repository, a base Docker environment, an erroneous README, and structured gold error/repair annotations. In the checked release, each main JSONL row contains only `readme`, `repo_name`, `level`, and `errors`; each error contains `error_type`, `error_description`, `correction_candidates`, and `golden_answer`. README text lives in a parallel directory tree, and repository revisions live in a separate `repo_info.jsonl`. No action, observation, retry, patch, stdout/stderr, container state, test result, or terminal verdict is present in the task row.

This belongs in `environment_agent_trajectory_data` because it defines an environment-grounded evaluation surface and makes process and terminal feedback explicit. It does not establish a public trajectory-training corpus: Appendix C describes a framework capable of generating successful and failed trajectories, but the official tree at the checked commit contains no such rollout collection. It also does not evaluate general code correctness; the target is environment configuration under injected README faults, with final success defined by build, test, and normal-exit conditions.

The Atlas value is therefore twofold. EnConda-Bench provides a countable task corpus with gold diagnoses and repairs, and it exposes the gap between process-level recognition and executable recovery. The current L4 content boundary is supported by the paper, appendix, ICLR record, full-corpus schema/count inspection, and pinned code audit; it deliberately leaves end-to-end replay, experiment trajectories, exact executor provenance, and paper-to-release reconciliation unresolved.
