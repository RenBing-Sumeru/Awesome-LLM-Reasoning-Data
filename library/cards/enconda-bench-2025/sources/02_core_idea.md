EnConda-Bench turns minimally corrupted repository setup instructions into tasks that can be scored at two different surfaces: whether the agent diagnoses and proposes fixes for the injected errors, and whether its final script actually configures and tests the repository.

Construction starts from selected Python repositories whose original setup instructions are manually checked. Claude-4-Sonnet and Gemini 2.5 Pro minimally edit READMEs and attach error types, descriptions, candidate corrections, and gold repairs. GPT-4.1-mini generates a README-faithful setup script and helps filter injections: the erroneous version must block progress, and the repair must permit progress through the affected step. Human review follows the automated checks. The released object is the resulting erroneous README plus per-error gold metadata and separately maintained repository/revision context.

The feedback contract is mixed. Error-type precision, recall, and F1 compare categorical sets. An LLM judge assesses semantic accuracy of predicted error descriptions and fix suggestions. The terminal predicate is environmental: a generated shell script passes only when environment construction succeeds, tests run correctly, and the process exits normally. These signals can observe category agreement, semantic correspondence, and an eventual executable outcome; they cannot recover an unreleased command-observation history, prove that a repair is safe or reproducible under future package state, or establish that every intermediate diagnosis caused the terminal result.

Compared with environment-configuration benchmarks discussed by the paper, including EnvBench, INSTALLAMATIC, ExecutionAgent, and SetupBench, the directional change is the joint treatment of error localization/repair semantics and end-to-end execution rather than a single final outcome. The closest Atlas companions are SetupAgent/SWE-bench and BuildBench: all connect repository tasks to environmental predicates, but EnConda-Bench releases synthetic README error annotations at 4,201-task scale. Its category value comes from that feedback design and its audit gaps, not from reclassifying the released task rows as full trajectories.
