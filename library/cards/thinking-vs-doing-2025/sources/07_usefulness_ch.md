对于 `environment_agent_trajectory_data` track，TTI 最适合作为 construction and audit recipe，而不是可下载的 training-trajectory dataset。构建者可以复现其模块化流程：task source、multimodal browser state、policy action、terminal evaluator、positive-episode filter、state-action serializer、replay sampler 和 horizon scheduler；同时应将 evaluator identity 与 environment version 作为一等 lineage fields 记录。

这张 Card 提供四种具体的 track-level 用法。第一，用 TTI 作为 filtered-BC baseline，比较 fixed 与 expanding interaction horizons，但不要把该 baseline 标为 RLVR。第二，同时记录 episode-level terminal reward 与 step-level serialization，让后续审计能够区分 selection unit 和 loss unit。第三，把 WebArena programmatic evaluation 与 WebVoyager prompted judging 作为两个独立 feedback adapters，分别维护 version、calibration 和 error records。第四，设计 replay manifest，至少包含 task ID、site/domain、policy checkpoint、evaluator checkpoint/prompt、horizon、seed、collection iteration、terminal outcome、retention decision 以及 recency/domain sampling weight。

它也可作为 useful negative-control checklist。应在 training loss 之外保留 failed 与 `ANSWER [N/A]` episodes；比较 positive-only BC 与能够利用 failures 的 policy；报告 raw attempts、successful episodes、unique tasks、duplicates、replay occupancy 和 per-domain selection rates；并测试在 clean task split 与单独固定 judge 后，收益是否仍然存在。这些实验可以定位增益究竟来自 interaction opportunity、curriculum ordering、success filtering、replay composition，还是 evaluator errors。

复用等级：**仅限 reading/audit 与 code-level reproduction reference**。task JSONL 文件可以检查，两个 checkpoints 也可在谨慎核验许可后用于 evaluation；但 training-data reuse 仍被以下事项阻断：明确的 code/task license、干净且 paper-aligned 的 split manifest、固定的 Gemma 3 27B judge 与 prompt、已发布的 rollout/screenshot lineage，以及可复现的 environment snapshot。benchmark scores 本身不能消除这些 blockers。
