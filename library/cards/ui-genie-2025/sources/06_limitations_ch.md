最核心的风险是验证器反馈。一次假阳性的完成判断可能让错误轨迹进入 SFT、把其中步骤标成正例，并进一步影响下一代 agent；假阴性则会丢弃有效替代方案。提前截断、跨任务替换和完成后冗余续跑还可能留下易识别的人工痕迹，与自然发生的 agent 错误不同。自建 RM benchmark 与训练共享数据来源和破坏逻辑，因此对新 app 与新失败模式的泛化仍不确定。

发布规模和计量单位并不完全一致。论文与名称使用 517K RM 样本，但当前 viewer 只暴露 472,769 行。“Agent-16k”在正文或 README 中有时被宽泛描述为轨迹，而表 1 与文件布局支持的是 2,208 条轨迹和约 16K 个步级样本。Agent 仓库还混放了 `AMEX_Agent_34K.jsonl`，却没有说明它是上游背景、训练依赖还是发布组成。由于缺少按代次的 manifest 和记录级接纳来源，这些差异无法被完整对账。

复现链条并不完整。仓库给出了 agent SFT 与 AndroidControl 评测脚本，但没有 RM 训练或迭代生成流程；AndroidLab 与 Android Arena 的评测脚本仍标为未来发布，72B checkpoint 未发布，仓库也没有 tag 或 GitHub release。探索温度、停止策略、任务预算、模拟器/app 版本、账户状态与不可变环境快照均未知。动态界面会让坐标重放和成功判据随时间漂移。

隐私、权利与数据划分也未解决。截图和输入文本可能暴露账户、通知、联系人、查询或第三方内容。HF 数据卡把数据标为 MIT，但这一标签不能证明每张上游截图、app 界面或用户状态都具备再分发权。仓库根 README 声称 MIT，却没有根目录 LICENSE；内嵌的 ms-swift 则使用 Apache-2.0。当前没有经过核验的逐记录同意/脱敏日志、来源许可矩阵、去重报告或 app/任务/账户泄漏分析。

论文自身也承认 RM 可能给出次优奖励、无法保证轨迹完全正确，并带来较高计算与碳成本。实验还显示明显缺口：报告中的 7B agent 在 Android Arena 的 hard 和 multi-frame-query 子集上成功率为 0.0，测试时奖励筛选也没有稳定改善困难样本。
