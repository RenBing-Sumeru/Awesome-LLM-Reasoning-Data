MobileGym's central move is to make one structured state representation serve four roles: task initialization, exact reset/fork, deterministic outcome checking, and reward construction. App views are composed from read-mostly world data, a per-environment mutable runtime overlay, and OS runtime state. The agent sees screenshots, while the benchmark layer can read and compare the complete JSON state (Paper §§3.1–3.2, Figures 2–3).

An episode begins with a parameterized natural-language template and a state patch. Its observable behavior is a sequence from a 17-action abstraction, including touch, typing, navigation, waiting, `COMPLETE`, and `ABORT`; agent adapters may expose model-native subsets. The evaluator checks goal-specific state through `check_goals()` or `get_answer()`, uses typed AnswerSheet fields for query tasks, compares initial and final state for unexpected side effects, and reports Success Rate, Progress Rate, False Complete, Unexpected Side Effects, and Overdue Termination (Paper §§4.2–4.3; Appendices C and F).

The feedback is programmatic but not omniscient. It observes fields represented in simulator state and task-authored checks; it cannot certify real-app backend behavior, pixel fidelity, unmodeled side effects, or semantic correctness outside those checks. The reward called “dense” is denser than binary success because it uses the fraction of passed goal checks, but the paper and current `mobilegym_evaluator` compute it from completed rollout artifacts. It is therefore an episode-level scalar derived from terminal subchecks, not a per-action stream of intermediate rewards (Paper Appendix G; official `mobilegym-rl/cookbooks/mobilegym/evaluator.py`).

Relative to AndroidWorld/AndroidLab emulator benchmarks and MobileBench-OL real-device evaluation, MobileGym changes the substrate: browser instances make JSON state cheap to clone and inspect. Relative to AppWorld-style state-based verification, it applies the idea to screenshot-driven mobile interaction and connects the same checks to online GRPO. The directional contribution is a shared environment/feedback interface, not a new policy architecture or a released expert-trajectory dataset.
