**Inputs and state construction.** MobileGym implements 12 everyday-app surrogates and 16 system apps. Read-mostly world data contains entities such as posts and products; mutable runtime overlays contain the current user's profile, carts, drafts, messages, settings, and task-specific overrides; OS runtime stores device and lifecycle state. A task class supplies a natural-language template, parameter samplers, setup/state injection, allowed expected changes, and deterministic goal or answer checks (Paper §§3–4; Appendices A, D, and E).

**Instantiation and interaction.** The 416 templates are split into 160 train and 256 test templates. Runtime diversity comes from instruction variants, parameter values drawn from curated sets/ranges/current state, and environment configuration. The runner resets the simulator, applies the task state, and forks identical JSON snapshots when grouped rollouts are needed. Agents receive 1080×2400 screenshots, output actions normalized to a 0–1000 coordinate space, and act under 15/30/45/60-step budgets; AnswerSheet tasks receive an additional 15 steps in the paper protocol. The current RL flow runs browser pages through an asynchronous environment pool but adds 10 rather than 15 steps for AnswerSheet tasks, so reproductions must select and pin one protocol (Paper §§4.2–4.3; Appendices C, F, G; official `mobilegym_flow.py`).

**Verification.** At termination or truncation, task code evaluates explicit goal checks against initial and final structured state. Query/hybrid tasks may require the agent to fill typed AnswerSheet fields; matchers cover exact choices/text, numeric tolerance, date/time/duration formats, and repeatable fields. Full-state diffing flags mutations outside declared expected changes. The terminal report separates goal success from clean success and records progress, false completion, post-success abort, overdue termination, and unexpected side effects.

**Reward and online training.** In the reported GRPO case study, Qwen3-VL-4B-Instruct is trained on Train160 for 10 steps using 3 RTX Pro 6000 GPUs, 96 browser instances, group size 8, train/PPO mini-batch size 12, per-GPU micro-batch size 2, learning rate 1e-6, KL coefficient 0.01, clipping 0.2/0.28, training temperature 0.7, maximum prompt/response lengths 32,768/1,024, and vLLM asynchronous rollouts (Paper §5.2 and Appendix G). The base reward is terminal goal-check progress `p`; an incorrect submitted AnswerSheet loses the submission bookkeeping credit, and multiplicative 0.8 or 0.5 discounts apply to unclean success, premature completion, post-success abort, or overdue termination. Binary correctness remains the final success predicate.

**Released outputs and reproduction.** The repository exposes simulator, task definitions, split lists, runner, judge, trajectory recorder/explorer, and a v0.1.0 online-RL stack built around vendored rLLM and verl. The current launch script defaults to `sample_n=1`, `task_seed=42`, group size 8, 96 concurrent tasks, and the train/test splits; its hardware defaults differ from the paper description, so paper results should not be attributed to an unpinned current script. Reproduction must pin arXiv v2, a repository commit or v0.1.0 tag, the data-v0.1.0 archive, Node/Python/browser and dependency versions, split files, task seed/parameter instances, model checkpoint, and all run logs. No canonical corpus of the paper's successful and failed rollouts was verified.
