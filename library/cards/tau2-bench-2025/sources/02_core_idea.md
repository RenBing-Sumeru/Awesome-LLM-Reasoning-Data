The one-sentence contribution is: tau2-bench turns customer-service evaluation into a dual-control environment where an agent and a tool-using simulated user jointly produce a stateful episode, and releases the tasks, environments, component evaluators, and model-generated trajectories needed to inspect success and failure.

Three objects are coupled. First, a versioned task specifies initial agent/user state, scenario constraints, required or reference actions, and evaluator criteria. Second, an orchestrator alternates the agent and user simulator through messages or single tool calls over separate tool spaces and mutable databases. Third, a mixed feedback contract evaluates the resulting state and trajectory. At benchmark level, components can include DB equivalence, environment/status assertions, action matching, required communication, and natural-language assertions. Selected components are multiplied into a binary-like scalar reward; released `RewardInfo` preserves the final reward and the component breakdown. Reported telecom tasks primarily use deterministic environment assertions, with an ACTION gate for applicable expected-failure or transfer cases.

This feedback can observe evaluator-visible final state, recorded actions, required communicated facts, and any natural-language claim sent to an enabled assertion judge. It cannot establish that unspecified semantic requirements were satisfied, that a task predicate is complete, or that user-simulator behavior matches a real customer. Conversation termination is also separate from success: STOP, TRANSFER, OUT-OF-SCOPE, maximum-step, or maximum-error termination ends the episode, while reward components decide task success. The metadata's state/action and full-episode granularity describes recorded supervision surfaces, not a dense process reward at every reasoning token.

Relative to the original tau-bench-style single-control setup, the concrete change is that the user gains a tool-constrained state and can perform actions that the agent cannot perform on the user's behalf. Relative to `the-agent-company-2024`, the chosen depth-calibration Card, tau2-bench concentrates on turn-based customer-service coordination with separate agent/user tool spaces and compositional telecom tasks, rather than a multi-application workplace sandbox with checkpoint scoring. Neither comparison supports a claim that one evaluator is more valid or representative.

For reasoning-data research, the direction signal is the explicit chain `task specification -> shared state -> agent/user actions and observations -> component checks -> terminal reward`. The official v0.1.0 trajectories retain both successful and failed episodes for inspected runs, enabling verifier and failure audit. The paper uses this chain for evaluation only; later Gym and RL-facing repository features are subsequent software evolution, not evidence of paper-era training use.
