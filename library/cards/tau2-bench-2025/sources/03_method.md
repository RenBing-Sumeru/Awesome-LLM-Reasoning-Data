**Inputs and environment construction.** For telecom, the authors first use an undisclosed LLM to draft a product-requirements document, database schema, functions, mock database, and unit tests, then manually refine the package until tests pass. The same LLM-assisted/manual process creates a mocked user-phone database and user tools. Domain-specific agent policies are generated from curated tasks and solutions and jointly refined by humans. The drafting model, exact prompts, sampling parameters, rejection counts, and per-item review history are not disclosed. Airline and retail material is inherited from tau-bench; full per-task upstream lineage is unavailable.

**Task generation and selection.** Each telecom atomic subtask is implemented as initialization, solution, and assertion functions. Compatible subtasks are composed; the generator executes initialization and solutions, checks final-state assertions, and verifies that all solution functions are necessary. 15 atomic subtask groups produce 2,285 full tasks. The evaluation sampler keeps tasks with at least two subtasks, bins them by intent, subtask count, and persona, and uses Python `random.sample` to retain at most three per bin; the CLI default seed is 42. The resulting 114-task sample contains 29 service, 36 mobile-data, and 49 MMS tasks spanning 2–9 subtasks, with None, Easy, or Hard persona assignment.

**Rollout environment.** The orchestrator initializes separate agent CRM and user-phone state plus message history. On each turn, either the evaluated agent or the user simulator emits one natural-language message or one tool call, and the corresponding tool result becomes an observation. Experiments pair `gpt-4.1-mini-2025-04-14`, `gpt-4.1-2025-04-14`, `o4-mini-2025-04-16`, or `claude-3-7-sonnet-20250219` as agent with `gpt-4.1-2025-04-14` as user simulator. The paper uses temperature 0 and four trials per task. Inspected v0.1.0 metadata records `max_steps=200`, `max_errors=10`, trial ids, and seeds. Default, No-User, Oracle Plan, and workflow-policy telecom conditions expose coordination and planning ablations.

**Verification and output.** A task selects reward components from DB, environment/status assertions, communication, natural-language assertions, and action matching. The evaluator computes the selected components and multiplies them; environment assertions are themselves checked individually and multiplied. Termination may result from the simulator's STOP, TRANSFER, or OUT-OF-SCOPE signal or runner guards, but termination alone does not imply success. Each `SimulationRun` stores its task, ordered messages and tool calls, timing, token/cost metadata, termination reason, `RewardInfo`, trial, and seed.

**Release and use boundary.** The paper-era `v0.1.0` release contains policies, mock databases, generator/evaluator code, 2,285 full and 114 sampled telecom tasks, and 26 final result JSON files. The inspected GPT-4.1 telecom-default result contains all 456 episodes from 114 tasks times four trials, including 156 reward-1 and 300 reward-0 runs. This is a released evaluation trace set, not a teacher-filtered training corpus. Exact replay should pin `v0.1.0`, task files, evaluator revision, model endpoint/version, LiteLLM/provider behavior, run configuration, and external credentials. The release has no paper-era train/dev/test split manifest and discloses no decontamination protocol.
