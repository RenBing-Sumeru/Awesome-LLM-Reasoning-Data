Dockerless replaces repeated repository-specific test execution during post-training with a learned, repository-grounded judgment workflow. Given an issue, a golden patch, and a candidate patch, it generates 2–4 diagnostic questions. One parallel ReAct-style sub-agent per question uses read-only shell searches to gather file- and range-grounded evidence from tests, code, documentation, and configuration. A final judge reads the issue, both patches, and the accumulated Q&A, then emits token `0` or `1`.

Three feedback layers must remain distinct. First, held-out tests inside per-repository Docker environments produce the binary execution label used to construct and evaluate the verifier. Second, the learned final judge predicts a binary verdict from repository evidence; its verdict-logit softmax is a scalar score in `[0,1]`. Third, downstream GRPO averages the remaining scores from `M=2` independent verifier passes and group-normalizes them across `G=8` rollouts. Main benchmark evaluation later returns to executable held-out tests. A learned verdict or dense reward is therefore not the same object as the programmatic success label.

The method is “environment-free” only with respect to repository-specific dependency and test environments during downstream training. OpenHands still executes shell commands and edits files in a minimal Linux image, while Dockerless evidence agents execute read-only searches. Moreover, both question generation and final judgment require the golden/reference patch, which sharply limits use on new issues without a known correct solution.
