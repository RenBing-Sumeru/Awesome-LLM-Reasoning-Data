Software-engineering agents normally need a repository-specific environment—pinned dependencies, a test runner, and held-out tests—to determine whether a final patch works. Building and maintaining those environments is costly, and missing or broken dependencies can make otherwise useful issues unavailable for post-training. Dockerless studies whether SFT filtering and reinforcement-learning rewards can instead be supplied by a learned program verifier while the policy operates in a minimal base image.

The paper exposes two related data objects. A verifier-training record contains an issue, repository checkout, golden/reference patch, candidate patch, binary execution label, and a GLM-5-generated sequence of verification questions, evidence-backed answers, and a final judgment. A downstream record is a full OpenHands software-agent rollout in a minimal Ubuntu image, ending in a candidate patch and a Dockerless score. The reported internal scales are 3.7K unique verifier-training issues, 16K candidate downstream rollouts filtered to 4K for SFT, and a 776-example verifier evaluation set.

This is an environment-agent-trajectory paper because the central object is the lineage from issue and repository state through shell/tool interaction to a final patch and feedback. It is not an open-data release: no paper-specific verifier corpus, 16K/4K trajectory set, 776-example evaluation manifest, code, model weights, or project page was verified.
