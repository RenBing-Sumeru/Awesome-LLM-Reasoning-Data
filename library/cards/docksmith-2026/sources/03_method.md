Inputs are versioned GitHub repositories, merged PRs with substantive code and test-related changes, repository/issue/ground-truth-patch context, and optionally LM-refined problem statements. The source filter uses repositories with at least 500 stars and 200 forks, targets ten languages, and covers more than 15,000 repositories. The refinement model and a faithfulness audit for rewritten problem statements are unknown. Repository-level deduplication against evaluation benchmarks is reported, but benchmark snapshots, hashes, matching code, and semantic PR/issue overlap checks are not disclosed. (Paper §2.1.)

Generation proceeds through four coordinated agents. Context Retrieval finds dependency, build, CI, and test evidence. The Dockerfile and Eval Script agents create or repair executable artifacts. Test Analysis turns build/test output into failure summaries and next actions. Each iteration updates the repository/environment state with file edits, commands, logs, and diagnoses. A loop detector diversifies the agent sequence after repeated non-improving combinations, and success memory can inject validated Dockerfile/evaluation-script examples from earlier tasks. The identities and versions of all generation models, prompts, decoding parameters, number of rollouts, per-agent budgets, loop thresholds, success-memory configuration, and universal timeout policy are unknown. (Paper §2.2 and Figure 1.)

Selection first retains only execution-verified successes. Long or redundant successful rollouts are then removed when they repeat the same agent, use excessive turns, or contain unusually many messages; all numeric thresholds are unknown. Per-language token caps balance the source mixture. A Dockerfile complexity score, `0.5 * nonempty lines + 5 * RUN instructions + 3 * distinct apt-get/apt packages`, assigns Easy/Medium/Hard buckets sampled at 1:2:2. Failed terminal rollouts are used in evaluation and error analysis but are not documented as SFT examples. Therefore the SFT corpus teaches successful construction and repair paths without preserving a complete negative-attempt ledger. (Paper §2.3.1 and Equation 1.)

The selected Docker data are used for supervised fine-tuning, alone or token-mixed with Nex Agent-SFT general SWE/coding trajectories. Training starts from Qwen3-Coder-30B-A3B-Instruct with global batch size 32, learning rate `1e-5`, and two epochs. Maximum sequence length is 32K for Docker-only training and 64K for mixed training. Optimizer, scheduler, precision, hardware, gradient settings, seed, exact token counts, checkpoint selection, and the mixture used by the released model remain unknown. This work supports `sft` and `agent_training`; it does not report RLVR, preference learning, reward-model training, or process-supervision training. (Paper §§2.3, 3.1, and 3.3.)

The pinned public release has nine JSON conversation shards and nine index files. Conversation samples are lists of messages containing `role`, `content`, and `loss_mask`; index rows add `index`, `sample_id`, `instance_id`, `agent_type`, `source_file`, and `num_assistants`. Multiple fragments may share one `instance_id`. Reuse must pin dataset content commit `b847dad7371e172fedc44c1510b7619ee1a6f23b` or current revision `1d44cd3be604a339bcdad5e60844a23e4b1eeada`, model revision `1404f4daa0694c3ab2575f2dd8a7b6bbd40848e3`, and the ICML-final/arXiv-v2 paper boundary. Exact replay additionally requires the missing fragment-to-episode assembler, repository and evaluator hashes, image digests, dependency locks, and network/cache/timeout/reset policies.
