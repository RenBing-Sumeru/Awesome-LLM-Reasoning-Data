The disclosed construction pipeline is:

1. **Problem pool.** Crawl 17,503 AoPS contest problems, prioritizing olympiads, team-selection tests, post-2010 items, and problems explicitly requiring proofs; call the pool `D_p` (Paper §2.1.1, p.3). The crawl manifest, rights ledger, duplicate policy, and evaluation exclusions are not released.
2. **Initial proof generation.** A DeepSeek-V3.2-Exp-Thinking variant writes candidate natural-language proofs and iteratively refines them over multiple rounds. Generator identity, number of rounds, sampler, temperature, candidates per task, and retention are unknown.
3. **Expert proof labels.** Randomly sample proofs across mathematical types and ask mathematical experts to assign `s ∈ {0, 0.5, 1}`. This creates `D_v={(X_i,Y_i,s_i)}`. Expert count, labels per proof, agreement, adjudication, and dataset size are undisclosed.
4. **Verifier RL.** Start from a DeepSeek-V3.2-Exp-SFT checkpoint trained on undisclosed mathematics and code reasoning data. The verifier writes an issue analysis and boxed score. Initial reward is `R_format × R_score`, with `R_score=1-|s'-s|`; format checking validates required phrases and boxed syntax, not mathematics.
5. **Meta-verifier RL.** Experts score verifier analyses with `ms ∈ {0, 0.5, 1}`, producing `D_mv={(X_i,Y_i,V_i,ms_i)}`. A learned meta-verifier scores analysis quality. Enhanced verifier reward is `R_format × R_score × R_meta`, and the verifier is trained on both datasets.
6. **Generator RL and self-verification.** Use the verifier's proof score as generator reward. Require the generator to output a proof followed by self-analysis and self-score. Reward is `R_format × (0.76 R_Y + 0.24 R_Z)`, where `R_Z` combines agreement between self-score and verifier score with meta-verification of the self-analysis (§2.2.2).
7. **Iterative scaling and late automation.** The improved generator produces harder proofs. Earlier hard-proof labeling uses multiple verifier analyses to assist experts. In the last two iterations, automation generates `n` independent verifier analyses; for analyses scored `0` or `0.5`, it generates `m` meta-assessments and accepts an asserted issue by majority. If at least `k` validated analyses agree on the lowest score, assign that score; if no legitimate issue is found across all `n`, assign `1`; otherwise discard or route to humans (§2.3, pp.5–6). Numeric `n`, `m`, `k`, yields, class balance, and human-routing rates are unknown.
8. **Optimization sequence.** Use GRPO, first improving verification and then initializing and optimizing the proof generator from that checkpoint. From iteration two, initialize the verifier from a rejection-fine-tuned checkpoint consolidating prior verification and generation ability (§3.1, p.6). GRPO/RFT code, hyperparameters, optimizer details, rollout counts, compute, and checkpoint hashes are not released.
9. **Test-time use.** One-shot evaluation samples 8 proofs and uses majority vote across 8 verifier analyses. Sequential refinement uses a 128K per-attempt limit, up to 8 attempts, 32 threads, and 32 verifier analyses; it stops on self-score `1` or the attempt cap. High-compute search initializes 64 proofs with 64 analyses each, retains the 64 highest-average candidates, pairs each with 8 selected analyses, and iterates up to 16 rounds or until one proof passes all 64 LLM-verifier attempts (§3.3).

Reproduction requires the unavailable training records, expert protocol, generator/verifier/meta-verifier versions, `n/m/k`, sampled and rejected records, reward code, GRPO/RFT implementation, split and contamination ledger, and checkpoint lineage. The released repository supplies inference/evaluation templates, selected contest inputs and predictions, and model weights. Those artifacts do not reconstruct training or constitute a training-data release.
