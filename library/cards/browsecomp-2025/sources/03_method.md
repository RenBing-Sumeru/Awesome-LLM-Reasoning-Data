The construction input is a human-selected factual seed such as a person, event, or artifact. A trainer gathers distinguishing characteristics and supporting evidence, then inverts them into a fact-seeking question intended to have one indisputable, short answer that should not change over time. Trainers were encouraged to use personal interests. Record-level seeds, evidence URLs, passages, timestamps, writer/validator identifiers, and upstream rights are not released.

Candidate filtering combines three difficulty checks. First, GPT-4o with and without browsing, o1, and an early Deep Research version are expected to fail. Second, the trainer performs five simple Google searches and requires the answer not to be readily visible on the first result pages. Third, the intended target is that another person cannot solve the item within ten minutes, but this check was not strictly enforced and only a portion received second-trainer attempts. If a trainer's questions were solved above 40%, the items were revised. A prompted OpenAI chat-model classifier assigns one of ten topics after construction; its prompt, checkpoint, and confidence are unknown.

The initial pool contained 1,287 tasks. Among 118 tasks on which Deep Research had a 0% pass rate, manual review removed 21 because of answer-format mismatch, ambiguity, or incorrect reasoning, leaving 1,266. This review improves some labels but also conditions the final set on an undisclosed Deep Research revision. Removed rows, item-level filter outcomes, alternative-answer adjudication, and a canonical train/dev/hidden split are not released.

For use, the official evaluator downloads the four-column CSV and decrypts `problem` and `answer` with the public canary-derived XOR routine. It prompts the evaluated system for an explanation, a succinct `Exact Answer`, and 0%-100% confidence. A separate LLM grader sees question, response, and reference answer and should return a binary semantic-match judgment. The paper and release page do not disclose the grader checkpoint used for the reported results. The current repository runner supplies `gpt-4.1-2025-04-14`, but that later configuration is not evidence for the paper's grader.

At inspected commit `652c89d0ca9df547706735883097e9537d40dc47`, current `browsecomp_eval.py` has a blocking reference-scorer defect: `grade_sample` returns `match.group(0)`, such as `correct: yes` or `correct: no`, while the caller compares the returned value with bare `yes` and `no`. Matched outputs therefore set neither boolean flag. A reproducer must return the captured yes/no group and add expected-output tests before trusting scores from this code path. This is a static finding about the current reference implementation; it does not by itself show that the paper's separately generated results are invalid.

The output is an aggregate evaluation over answer correctness, model-reported confidence, and optional repeated samples. No SFT, RLVR, reward-model, or agent-policy training recipe is defined. Reproduction requires pinning the CSV checksum, repository commit, corrected scorer, grader checkpoint and settings, evaluated model revision, browsing/search stack, locale/session state, run date, and tool/token/page/time budgets; most of the latter fields remain unknown.
