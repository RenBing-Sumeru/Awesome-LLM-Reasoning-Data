For `environment_agent_trajectory_data`, BrowseComp is most useful as a boundary case: the task requires environment interaction, but the release serializes only question, answer, topic, and canary. A track audit can use it to test whether a Card incorrectly promotes an agent benchmark into a trajectory dataset. Any replayable episode schema built around BrowseComp would need to add query/action/observation records, URLs and captures, tool and model revisions, budgets, stopping reasons, confidence, grader transcript, and successful and failed paths; those are not supplied by the benchmark.

The supported reuse classes are evaluation, audit, and test-time-compute analysis. For evaluation, decrypt the official CSV with the shipped routine, repair and test the label parser, pin a grader and its prompt/settings, pin the agent and search stack, record the live-web date and budget, and report both accuracy and confidence behavior. For audit, measure alternative-answer sensitivity, judge drift, current scorer correctness, canary exposure, train/test overlap, and web drift. For test-time compute, compare equal-budget repeated sampling and state the unit of compute; the paper's 64-sample analysis is a reference design, not a released rollout set.

The release is not established as safe for SFT, distillation, reward modeling, RLVR, or agent-policy training. Public questions and answers are a test set, the post-release contamination status is unknown, and no reusable trajectory or process reward is published. Treat it as evaluation/audit reference material subject to scorer repair and environment pinning, not as training-ready data. Benchmark performance should be used to compare evaluated systems under stated conditions, never as a substitute for validating the questions, reference answers, judge, rights, or lineage.
