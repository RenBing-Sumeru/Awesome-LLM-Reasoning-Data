1. Inputs: a task class, sampled task parameters, a controlled Android emulator, installed apps, and an agent scaffold such as M3A. 2. Pipeline: the environment initializes device/app state, the agent observes UI state and screenshots/accessibility data, emits Android actions, and repeats until it finishes or reaches the budget. 3. Outputs: per-task logs, success/failure labels, aggregate success rate, and optional traces for later audit. 4. Feedback contract: each task owns code that checks the resulting app/device state; the paper reports 116 tasks over 20 apps and uses success rate as the main metric. 5. Reuse notes: pin Android image, app versions, task list, sampled parameters, Docker/runtime support, model prompt/scaffold, retries, timeout, and evaluator commit before comparing scores.
