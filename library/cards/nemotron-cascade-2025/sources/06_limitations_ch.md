
任何阶段都没有完美验证器。标量奖励模型只是偏好代理；论文指出，RewardBench 分数最高的模型不一定产生最佳对齐策略，分布外提示还可能使 RLHF 不稳定。IF 验证器检查明确约束，却不检查整体有用性，作者也报告了直接使用带来的退化。数学奖励检查抽取出的终点，而非每一步推理。代码奖励受测试不完备与执行不确定性影响。SWE 奖励明确不执行代码，因此替代性的正确补丁可能与人工补丁不相似，相似补丁也可能无法通过仓库测试。

与报告流水线相比，发布覆盖仍不完整。已检查 collection 包含 RLHF、Math 与 SWE RL 输入，但没有明显列出专门的 IF-RL 或 Code-RL 数据集。Stage-1 和 Stage-2 数据卡分别报告 5,436,618 与 7,797,730 条样本，而当前 viewer 数量更低。上采样、文件修订、viewer 处理和模型运行归属可能解释部分差异，但官方对照仍为 unknown。仅凭 collection 成员身份不能确定精确用途、混合权重或快照。

谱系在进入在线学习记录前中断。发布内容不包含完整策略 rollout 组、各奖励分量、对数概率、动态过滤决定、被拒候选、随机种子、日志、优化器状态或记录到检查点的清单。报告虽然说明使用 verl，却没有固定精确 commit 与完整分阶段配置。因此，即使中间权重已经公开，重现实验仍需大量重建。

去污染与权利证据都有边界。论文说明数学和代码使用 9-gram 过滤、Code RL 使用 URL 匹配、SWE 使用仓库名加 commit 排除；但基准精确修订版和删除账本为 unknown，通用、指令、安全与工具调用数据也没有同等范围的全语料审计。数据卡声明 CC BY 4.0，但上游署名、仓库代码权利与生成模型条款仍需逐条审查。

最后，顺序课程并不保证不会遗忘。论文承认奖励冲突可能覆盖早期行为，分阶段表格也同时存在小幅提升与退化。这些基准变化描述的是报告设置下的模型行为，不能验证数据集质量、验证器校准或发布的法律与来源链条。
