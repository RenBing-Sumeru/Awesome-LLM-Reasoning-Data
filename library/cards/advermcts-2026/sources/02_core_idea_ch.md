AdverMCTS 通过逐题共享的测试记忆，把两个持久化 Monte Carlo tree search 耦合起来。

| 组件 | 产物 | 接收的反馈 | 对后续搜索的作用 |
|---|---|---|---|
| Solver MCTS | 局部推理思路与完整 Python 程序 | 公开测试通过率；未通过已保留对抗测试时的惩罚 | 只有通过全部可见测试与既有对抗测试的程序才能进入代码池 |
| Attacker MCTS | 漏洞策略与具体测试输入 | 当前代码池中程序输出的分歧 | 搜索能够区分表面正确程序的输入 |
| LLM output Arbiter | 对分歧输入的有效性判断与期望输出 | 题目描述、候选输入和各程序的分歧输出 | 被接纳的 `(input, expected_output)` 进入全局测试记忆 |
| 执行环境 | 输出、失败、超时与通过/失败信号 | 生成程序以及公开/对抗输入 | 提供三类角色共同使用的可观察证据 |
| 最终重排器 | 一个提交程序 | 先比较公开测试得分，再比较累计对抗测试得分 | 以保留测试作为硬性的第二层判别依据 |

同一个所选主干模型家族同时担任 Solver、Attacker 与 Arbiter；系统没有单独训练的验证器或独立教师。因此关键反馈契约是**混合型**：可执行测试给出客观观测，分歧只是搜索启发式奖励，期望输出则来自 LLM judge。即使标签可能错误，一旦测试被保留，它仍会成为持久的硬约束。

相较 MCTS-Thought 与 RethinkMCTS，关键变化是验证证据随候选代码池演化，而不是固定为少量公开测试。相较 CodeT 式测试生成，该方法把测试构造组织成持久的对抗搜索，并把接纳的测试反馈给后续 Solver 扩展。这些是论文中的方法对比，不能据此证明所产测试已经构成质量更高的可复用数据集。

验证器看不到隐藏测试上的真实正确性。如果代码池里的所有程序共享同一错误并输出相同错误答案，输出分歧为零，验证器也无法发现它；论文明确指出了这一限制。
