AdverMCTS targets **pseudo-correctness** in competitive-programming generation: a program can satisfy a few visible examples while still failing hidden cases. The paper treats this as a verifier problem at inference time. Instead of accepting the visible-test signal as fixed, it lets a Solver propose programs and an Attacker construct counterexample tests against the current candidates.

The operative data object is not a released static dataset. For each APPS or TACO problem, the run transiently creates a Solver thought tree, complete Python programs, public-test results, an accepted code pool, an Attacker strategy tree, candidate inputs, per-program outputs, divergence scores, Arbiter decisions and expected outputs, and a growing memory of accepted adversarial tests. The memory is local to the problem and gates later candidates. The final answer is a program selected by public-test score and then adversarial-test score; hidden tests remain evaluation-only.

This makes the paper relevant to `data_construction_open_release_recipes`: it specifies a concrete recipe for generating and retaining verifier data during search. The qualification matters, however. The official repository releases implementation code, not the generated search traces, counterexample tests, code pools, or per-test decision ledger. The Card therefore records a reproducible research recipe only partially, not an open training corpus.
