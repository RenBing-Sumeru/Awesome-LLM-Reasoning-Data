For the `data_construction_open_release_recipes` track, AdverMCTS is useful as a blueprint for turning search-time disagreement into auditable verifier data. A strong reproduction should log, for every problem and test proposal: stable problem/test IDs, prompt and strategy path, code-pool snapshot, all execution outputs, divergence score, Arbiter input and decision, expected output, rejection reason, later revalidation results, and every penalty or ranking change. That would make the construction lineage inspectable and permit test-level precision, recall, duplication, and poisoning analyses.

The recipe is especially useful for research on dynamic verifiers, counterexample generation, test-time compute allocation, process supervision, and adversarial code-agent environments. Its rejected tests and false-positive cases could be as valuable as retained tests for training judge calibration or abstention systems. Those are prospective uses; the paper itself performs inference-time search and evaluation, not parameter training.

Practical reuse is conditional. The released code can inform a research reimplementation, but the missing license must be resolved before redistribution, APPS/TACO must be obtained under their own terms, and generated programs should run in a stronger sandbox. Exact reproduction also needs the sampled problem manifest, pinned dependencies, model/checkpoint identifiers, endpoint and decoding configuration, seeds, prompt versions, full cost records, and an immutable release.

A useful baseline release would pair the current method with independently executable gold validation, repeated execution for flakiness, deduplication, confidence/disagreement fields, and correction or retraction of invalid tests. Until such records are published, this Card should be used to study the recipe and its audit risks, not as evidence that a reusable AdverMCTS dataset is available.
