Important construction facts remain unknown: the exact training prompt sources and mixture, teacher or trajectory-generator policy, verifier model, (K), (n_{max}), continuation threshold, (\alpha), length thresholds, decoding temperature, random seeds, detailed data split, and decontamination procedure. The two Hugging Face cards contain little documentation beyond license metadata, so file availability does not resolve lineage or selection-bias questions.

Cold-start filtering has an asymmetric survival rule. Successful repaired episodes are retained, but fully failed or budget-stopped episodes are discarded. Re-querying the verifier until its binary judgment agrees with known correctness can select a lucky judgment rather than measure calibration, and the evidence path can still be incomplete or misleading. This makes the released successful traces unsuitable as unbiased evidence of failure frequency.

The environment changes across stages: paper training uses Wikipedia-restricted Google Site Search, paper evaluation uses Google Web Search plus Jina, and repository inference uses Serper. API versions, indexes, parser behavior, webpage contents, and page-reader model outputs can drift. Evaluation further uses an LLM-as-a-Judge and permits one answer, whereas SRRL training uses task-specific scores such as F1 and multiple submissions. These predicates should not be treated as interchangeable.

The repository lacks complete evaluation scripts and tagged releases. Smaller-model collapse and malformed JSON constrain scale claims. Source-data licenses, privacy considerations for web content, contamination controls, rejected verifier samples, and exact release completeness are not documented. Consequently, benchmark gains do not establish process-record quality or end-to-end reproducibility.
