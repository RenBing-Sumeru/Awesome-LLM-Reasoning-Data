Code models need more training data, but self-training on unverified outputs can recursively amplify errors. Code generation also has an asymmetric bottleneck: a model may produce plausible solutions more readily than it can generate unit tests that distinguish correct code from subtly wrong code. Training a Solver against a fixed weak Verifier therefore risks converting verifier blind spots into accepted synthetic supervision.

Sol-Ver studies whether the two capabilities can improve together without human annotations or a larger teacher. One Llama 3.1 8B model alternates between Solver, which writes Python functions, and Verifier, which proposes test inputs and expected outputs. Executing generated code against generated tests supplies the feedback used to select SFT examples and form DPO pairs.

For `data_construction_open_release_recipes`, the important object is the entire transformation, not only a final benchmark score: source snippet and prompt template, generated problem and signature, candidate code, test inputs and expected outputs, execution result, accepted and rejected records, role, and iteration. The decision boundary is programmatic execution, but the predicate is only agreement with self-generated tests; it is not proof that the code satisfies the intended specification. This is an L3 Card because the recipe and evidence are documented while the generated records and implementation remain unavailable.
