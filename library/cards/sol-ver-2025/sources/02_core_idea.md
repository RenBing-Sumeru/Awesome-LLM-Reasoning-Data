Sol-Ver couples two synthetic-data streams around the same execution event. The Solver receives a generated problem and function signature and produces candidate code. The Verifier sees the problem and a proposed solution, then generates candidate inputs and expected outputs. The score is the fraction of generated tests passed by the code.

The default recipe treats a solution-test tuple as chosen when at least one generated solution passes every generated test. For Solver SFT, passing code is a positive target; for Verifier SFT, the associated test-generation trace is a positive target. For Solver DPO, other code samples that fail the chosen tests become rejected responses. For Verifier DPO, alternative expected outputs from the test-output sampling space become rejected responses. The same execution record therefore yields answer-level supervised examples and role-specific pairwise preferences.

The updated model generates both sides again in the next round. Sol-Ver runs three SFT-then-DPO iterations; for the third round it combines tests from Iter 1 and Iter 2 and selects solutions that pass both. Unlike a fixed execution filter or CodeDPO's code-only preference construction, the verifier itself is refreshed and produces the next round's supervision. The core claim is a co-evolving construction recipe, not an open dataset release and not an independently certified verifier.
