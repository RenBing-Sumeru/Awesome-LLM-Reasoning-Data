Earlier code-data recipes already used stronger teachers, self-instruction, generated tests, execution feedback, self-correction, and preference optimization. CodeT jointly reasons over code and generated tests; RLTF and code reranking optimize against test outcomes; CodeDPO creates self-generated and verified code preferences. Sol-Ver does not originate these components.

Its specific change is to make the verifier a co-trained data generator rather than a static filter. The same model learns both code and test generation, and both roles receive SFT and DPO signals derived from shared execution tuples. Later verifier outputs then determine the next round's Solver data, while improved Solver candidates give the Verifier more informative positives and failures. The third-round use of two iteration-specific test sets adds a small temporal ensemble to that loop.

The direction signal for this track is operational: generated tests are first-class training records, rejected outputs are retained as preference material, and verifier refresh is coupled to data refresh. The recipe also makes a hidden objective visible: the full-pass rule determines what becomes chosen.

What remains unproven is equally important. Sol-Ver does not supply a formal verifier, independent ground truth, a public data release, a guarantee against recursive errors, or evidence across languages, repository-level tasks, or model scales. A sound reuse study should compare a fixed verifier, Solver-only training, Verifier-only training, SFT-only, DPO-only, gold-test filtering, relaxed pass thresholds, and matched data/compute budgets.
