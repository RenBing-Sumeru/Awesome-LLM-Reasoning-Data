For `data_construction_open_release_recipes`, Sol-Ver is a compact example of a construction loop in which the verifier, filter, and training-data generator are not separate systems. It shows how one execution tuple can create four downstream objects: Solver SFT, Verifier SFT, Solver preference, and Verifier preference data. It is useful for studying self-play, verifier refresh, rejected-example retention, and the way a binary filter becomes an implicit training objective.

An auditable raw record should preserve the source snippet ID and license, template source, generated problem and signature, generator checkpoint, prompt, decoding settings, code candidate, test inputs, reasoning, expected outputs, branch-coverage trace, output-diversity decision, execution environment, dependency versions, timeout, stdout/stderr, and pass fraction. A decision record should add role, chosen/rejected IDs, rule version, alternative candidates, and rejection reason. An iteration ledger should bind every retained record to the source checkpoint, SFT/DPO split, optimizer state, next checkpoint, and downstream evaluation.

Reusers should independently validate generated tests against gold or mutation-based checks before treating full-pass pairs as positive supervision. They should retain failed code and rejected expected outputs, report how many records each gate removes, use secure sandboxing, and audit train/evaluation overlap. Because the Sol-Ver artifacts are not public, the paper is safe as a recipe and audit reference; direct training reuse is blocked pending a frozen release, record-level provenance, split/overlap evidence, and licenses.

The paper also offers a useful negative lesson: synthetic-test reranking can lower code accuracy before verifier training, and increasing the selected-data volume can reduce results. Those observations motivate explicit quality gates; they do not certify the final synthetic corpus.
