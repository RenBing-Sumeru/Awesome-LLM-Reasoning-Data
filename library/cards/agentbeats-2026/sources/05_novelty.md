The baseline is benchmark-specific orchestration: an evaluator owns hidden assumptions about data loading, environment setup, tool invocation, subject integration, stopping, scoring, and report shape. AgentBeats changes the unit of integration by “agentifying” that evaluator. A judge agent exposes task management through A2A and tool/environment access through MCP, while a delegator connects independently developed judge and subject endpoints.

The resulting evaluation object has a reusable outer contract: participant mapping and configuration, judge-issued task, subject interaction, environment effects, terminal response/artifact/state, metric, and result report. The inner action space and result JSON remain judge-specific. This is a protocol and infrastructure contribution, not a claim that all benchmarks now share one data schema or one calibrated reward.

The field study adds empirical scope to the interface: 298 judge agents in 12 categories and 467 subject agents were registered across a live competition snapshot. The coding case then shows how one judge can own isolated containers, expose runtime injection or MCP remote shell, retain artifacts, run benchmark tests, and compare model-harness pairings. Together, these connect interface design to observable episode and terminal-feedback behavior, while the missing frozen inventory and run archive constrain auditability.

AgentBeats does not newly invent A2A, MCP, programmatic benchmark tests, LLM judges, containers, CI evaluation, or agent registries. It composes those components around a judge-agent abstraction and separates construction, registration, and execution across five deployment modes. Claims of openness, standardization, or reproducibility must therefore be evaluated at the artifact level: a common transport does not make tasks open, semantic judges calibrated, remote services resettable, or outputs licensed.

For the assigned track, the direction signal is making the environment and feedback owner explicit in the episode schema. Reuse should verify what each judge observes, how termination differs from success, which metric or predicate produces the score, which failures are retained, and which versions are pinned. No exact v2-bound trajectory/log/result/replay manifest is released, and the old SDK is deprecated, so the contribution is currently stronger as an evaluation-design and audit reference than as a reusable data release.
