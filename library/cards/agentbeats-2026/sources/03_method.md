**Inputs and authoring.** A judge agent owns benchmark data or task generation, environment setup, tool servers, evaluation flow, metrics, scoring, and reporting. Subject agents expose A2A endpoints and use judge-provided MCP tools where required; a delegator supplies participant roles/endpoints and configuration. Community participants authored judges and subjects for the field study. Repositories that were inaccessible or malformed were excluded and the rest deduplicated, but the frozen inventory, exclusion ledger, deduplication keys, and prompt-extraction implementation were not released.

**Construction, registration, and deployment.** Agent blueprints can be represented by Git repositories or Docker images and deployed as A2A endpoints. The platform separates construction from registration and assessment execution. Five modes are described: local, remote, hosted, proxy, and CI. They vary in where agents run, who initiates the assessment, and whether results appear in platform records, logs, or committed artifacts. The current leaderboard template uses scenario/component manifests, GitHub Actions, result directories, Docker images, secrets, sharding, and Amber, but it is a rolling artifact rather than the immutable stack for arXiv v2.

**Episode execution.** The delegator initiates the assessment. The judge loads fixed data or generates/adapts tasks, prepares the environment and MCP tools, and sends A2A task instructions or access information. The subject responds, calls tools, changes the environment, and signals completion; the judge may continue or stop according to its own policy. The output envelope consists of messages/updates, tool calls and observations where observable, subject response or artifact, final state, metrics, score, and a JSON report. No universal action vocabulary or inner result schema is imposed.

**Verifier, reward, and termination.** Each judge defines its own metrics using programmatic checks, environment predicates, semantic prompts/LLM judgment, or a mixture. Termination is assessment-specific. In the coding case, the judge starts an isolated source-tree container, injects the subject runtime or provides remote shell over MCP, waits for completion or timeout, collects artifacts, and runs the benchmark's evaluation scripts. This produces a terminal solve score rather than dense token-level supervision. Runtime injection has a preflight and remote-shell fallback because injection can fail or perturb the container.

**Coding-case selection and settings.** The case study uses 731 SWE-Bench Pro public instances, all 89 Terminal-Bench 2.0 tasks, and 1,222 DevEval instances retained after executing ground-truth tests and dropping failures. Claude Opus 4.7, GPT-5.4, Gemini 3.1 Pro, and Qwen3.5-397B-A17B are paired respectively with Claude Code, Codex CLI, OpenCode, and mini-SWE-agent. Defaults are used; reported thinking effort is xHigh, Medium, High, and enabled without another level, respectively. Main experiment cost is about USD 6,000. Temperatures, seeds, per-instance rollout counts, retries, exact time limits, and full configurations remain unknown.

**Outputs and use boundary.** Appendix A aggregates tool/resource statistics across successful and failed coding runs, but no record-level trajectory/log/result archive or exclusion ledger tied to v2 is released. The earlier agentbeats/agentbeats SDK's latest release is v1.2.6 from 2025-11-17; its README marks it deprecated, and it predates the June 2026 paper. Exact reproduction must therefore pin paper version, repositories/commits, images, benchmark snapshots, model/API behavior, prompts, secrets/configuration, timeouts, result schema, and retained outputs. The demonstrated use is evaluation and audit, not model training.
