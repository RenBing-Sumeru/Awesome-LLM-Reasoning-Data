For the Data Construction and Open Release Recipes track, R-Diverse is a concrete recipe for auditing diversity across rounds rather than only deduplicating the current batch. It places persistent memory at three construction points: a history-aware Challenger penalty, a retrieval surface for diversity measurement, and a replay source for Solver training. It also demonstrates why novelty representation and correctness verification must be audited separately.

An auditable implementation should retain each question, all Solver rollouts, extracted and normalized answers, equivalence groups, consistency, pseudo-label source, canonical code, canonicalizer and embedding revisions, max and mean memory similarity, threshold decisions, memory insert/correct/delete events, replay provenance, reward components, random seed, policy checkpoint, and evaluation outcome. Rejected, malformed, and corrected records should remain visible rather than being silently removed.

Builders can use the paper as a baseline for cross-iteration deduplication, curriculum replay, or data-selection ablations. Before training reuse, they should add an independent correctness check; calibrate SAM against human, symbolic, or executable judgments; version memory snapshots; bound or index retrieval cost; run contamination checks and multiple seeds; and keep benchmark outcomes separate from training-record labels.

The current reuse boundary is recipe reading and independent reimplementation, not direct dataset reuse. No executable official pipeline or generated stream is available, and the repository's prospective release plan should not be treated as an artifact.
