Existing synthetic-reasoning pipelines already paraphrase questions, sample teacher solutions, filter answers, or execute generated code. Caco does not introduce chain-of-thought distillation, Python execution, AST checking, back-translation, or LLM-as-judge verification in isolation.

Its first distinctive move is **unconditional pattern generation**. Source solutions are normalized into executable Code CoTs, and Qwen2.5-Coder-7B learns only the program distribution—not a mapping from a given question to code. Sampling can therefore create new program structures before any natural-language instruction exists. The authors frame this as pattern-level augmentation, in contrast with surface-level question rewriting.

The second move is **instruction reversal after execution filtering**. About 5.3M sampled programs are reduced to about 4.6M executable/structural survivors before Qwen3-8B invents problems and language solutions. The intended correctness anchor flows from the program into both representations, after which answer agreement and Qwen3-32B judgments filter the pair. This order is the core construction idea: generate a candidate reasoning object, validate what can be validated in code, and only then render it as training text.

The third move is the combination of scale study and open final objects. The paper reports the 146K-to-5.3M-to-4.6M-to-1.3M funnel, construction hours, data-size scaling on three downstream models, verification ablations, teacher-distillation controls, and a science-domain extension. The current release includes not only instruction and language output but also extracted answer and code for every visible row, which enables audits that would be impossible from aggregate scores alone.

The verified contribution is therefore an integrated data recipe and a large released product. It is not a guarantee of correctness: execution proves only the behavior of a program on its encoded inputs, AST checks only variable use, answer agreement can be correlated, and an LLM judge can accept shared errors. Nor does the paper demonstrate RLVR; the repository describes that as future work.

To turn the recipe into a stronger auditable standard, future releases would need immutable source and split manifests, per-row parent/source/model/prompt lineage, representative input-output tests and execution logs, all rejection decisions, independent judge calibration, sandbox specifications, upstream-license mapping, and exact/semantic benchmark decontamination.
