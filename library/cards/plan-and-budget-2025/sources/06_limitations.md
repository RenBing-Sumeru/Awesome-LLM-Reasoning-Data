- The sub-question plan, levels, and credits are LLM-generated. A plausible decomposition can omit a dependency, and inaccurate credits can systematically misallocate compute; the paper does not release calibration or error labels for these annotations.
- In the checked weighted implementation, local limits are natural-language instructions expressed in words. The API call can still generate up to its overall maximum, so the implementation does not demonstrate strict isolation of token use per sub-question.
- E3 depends on heterogeneous task scores and average billed completion tokens. Squaring A makes score differences influential, while provider tokenization, reasoning-token reporting, and planning-token accounting can change T. It is a comparison metric, not proof of a better trace or data record.
- TravelPlanner needs a secondary LLM to reconstruct JSON before scoring. Its model/version is supplied through the environment rather than pinned by the release, creating judge/conversion drift and potential false failures or passes.
- The repository ships code and pre-decomposed inputs but not its executed predictions, scores, seeds, endpoint/model revisions, complete prompts, failed calls, or decontamination analysis. Curator inference: absent those artifacts, performance attribution and audit replay remain limited even when the source code runs.
