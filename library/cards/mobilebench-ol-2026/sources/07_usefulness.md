For the `environment_agent_trajectory_data` track, MobileBench-OL is useful first as an evaluation-environment recipe. A defensible derived episode should bind task ID and subset, exact task/rule CSV hash, app/APK version, device/OS/account fixture, initial screen/XML, model and scaffold settings, noise seed/events, every screenshot/XML/action/response, execution errors, matched subconditions, termination reason, final success, reset episode, and post-reset state. Without these fields, apparent model differences can be environment or replay differences.

The rule construction process is a practical verifier-design baseline. Researchers can build task-level predicates from multiple valid trajectories, require both state/action evidence and explicit stopping, compare full success with Sub-SR, and calibrate rule output against human labels. The released false-positive and false-negative counts provide a starting point for stress tests involving alternate paths, stale resource IDs, visually similar pages, server-side state, premature Complete, and harmful intermediate actions.

The five subsets support controlled failure analysis if shared tasks/apps are accounted for. Base versus Long-Tail probes interface familiarity; Long-Horizon can stratify omission, planning, grounding, and loop failures; GUI-Reasoning can test discovery depth; Base versus Noise-Robust can test recovery. Retry studies must hold task, rule, app/device state, model snapshot, action budget, and noise events fixed instead of comparing unpaired pass@k values.

The reset mechanism is useful as an audit checklist rather than proof of deterministic replay. Each task should declare whether reset is task-level, app-level, unnecessary, or infeasible; report reset success separately; retain failed reset episodes; compare relevant state before and after reset; and quarantine tasks whose server-side state cannot be restored. Widening the success predicate should be documented as a verifier change, not silently treated as state recovery.

The current reuse class is **evaluation and audit only**. Direct SFT, RL, preference, or reward-model reuse is not supported because the paper trajectory corpus, failure/rejection ledger, immutable environment bundle, hidden evaluation partition, decontamination policy, and complete APK/content rights are absent. Public task and rule CSVs should be treated as contaminated for any model trained on them and reserved from future clean evaluation.
