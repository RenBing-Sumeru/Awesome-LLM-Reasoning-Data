测试时计算扩展常被概括为“多采样几个答案”或“把一个答案继续改深”，但固定生成预算带来一个具体分配问题：下一次模型调用应通过全新候选让响应树变宽，还是利用反馈修订已有回答、让树变深？固定宽度搜索预先决定这一取舍，可能把调用浪费在重复的同级候选上，也可能反复修补一个没有前景的分支。

Adaptive Branching Monte Carlo Tree Search（AB-MCTS）把这项预算分配决定本身变成搜索对象。根节点保存任务提示；每个非根节点都是一份完整、可评分的 Python 解决方案或 ML-engineering 程序。变宽操作通过选定节点的 `GEN` 选项生成新回答；变深操作沿已有回答向下，在先前回答和 evaluator 反馈的条件下生成子修订。由此得到的数据对象不是单链，而是一棵响应—修订树，其中可包含候选回答、父子谱系、生成顺序、模型身份、外部评估结果、节点分数、访问/价值统计和最终选中答案。

反馈随任务而异。CodeContest 与 LiveCodeBench 在搜索时使用公开测试通过比例，在最终评估时使用隐藏测试。ARC 根据生成的 Python 程序正确处理多少 demonstration transformation 来评分，再对未见测试输出做精确匹配。MLE-Bench 使用 80/20 训练/验证切分提供搜索指标，并在隐藏测试集上做最终评估。这些信号是程序化或环境式代理；它们不验证中间推理，也不保证与隐藏测试成功一致。

该工作准确归入 **Rollout, Search, and Test-Time Trace Data**，因为回答生成、修订、树拓扑、外部反馈和预算分配共同定义轨迹。它是推理时构造与评估配方，不是 SFT、蒸馏、偏好学习、奖励模型训练或 RLVR 的证据。本 Card 达到 L4，是因为论文、附录、官方 supplemental code、TreeQuest 和 ARC-AGI-2 仓库足以支持细致的双语说明。L4 不表示实验中实际生成的树或日志已公开：发布物提供可执行机制，而不是可复用的论文运行轨迹语料。
