**Task inputs and answer objects.** Main experiments cover CodeContest, LiveCodeBench release-v4 problems dated August–November 2024, 100 public ARC-AGI evaluation problems, and three low-complexity MLE-Bench tasks derived from Kaggle. The extended study uses the 120-task public ARC-AGI-2 evaluation set. Every generated non-root node is a complete Python answer or ML-engineering program, rather than a labeled intermediate reasoning step.

**Generation and revision.** AB-MCTS starts with the task prompt at the root. At each iteration it selects through the current tree, chooses between a `GEN` option and an existing response/subtree using Thompson sampling, generates one complete answer, scores it, and backs the result up. Selecting `GEN` makes a fresh branch. Traversing through an existing answer eventually creates a child revision; the supplemental solver constructs its request from the task, the previous assistant generation, and feedback derived from evaluation results. This is the operational widen/deepen response-revision contract.

**Search models.** AB-MCTS-M uses a mixed model for adaptive branching; AB-MCTS-A uses aggregated node statistics with conjugate Gaussian or Beta models. The checked algorithm and `Node`/`MCTSResult` implementation expose no explicit branch pruning or deletion path. “Rejected” means not chosen as the final answer, not erased during generation. All nodes can remain in the local serialized tree, and final submission code ranks nodes and selects the first highest-ranked candidate containing valid Python code. Hidden tests are not used as the search score.

**Evaluators and terminal use.** CodeContest and LiveCodeBench score the fraction of public tests passed. ARC scores the fraction of demonstration examples transformed correctly. MLE-Bench uses task-specific validation metrics, with each candidate executed on one H100 under a one-hour limit. Final evaluation uses hidden code tests, held-out ARC exact outputs, or hidden MLE tests. ARC-AGI-2 also reports Pass@k discovery—whether any branch found an exact solution—separately from contest-style Pass@2 selection. These contracts mix programmatic execution with task environments and can create search-feedback/final-evaluation mismatch.

**Models, sampling, and repeated runs.** The main model settings are GPT-4o `gpt-4o-2024-08-06` at temperature 0.6 and DeepSeek-V3 through the mutable `deepseek-chat` alias at temperature 1.0. LiveCodeBench uses five repetitions, CodeContest and ARC-AGI three, and MLE-Bench one. The ARC-AGI-2 extension uses `gemini-2.5-pro-preview-05-06`, `o4-mini-2025-04-16`, and `deepseek-r1-0528`, all at temperature 0.6. No teacher model or post-training optimizer is disclosed because the procedure is inference-time search.

**Budgets and accounting.** The main maximum is 128 LLM generation/API calls per task, or \(2^7\) added answer nodes. Standard MCTS generates five children per expansion and uses three on its final expansion so that its comparison also totals exactly 128 calls. Appendix ARC-AGI analyses extend to \(2^9=512\) nodes. The later ARC-AGI-2 multi-model experiment uses 250 generation calls, not 128. Call count is only a nominal budget: it omits generated tokens, evaluator runtime, retries, wall-clock latency, provider price, and MLE GPU cost.

**Persistence and release.** The NeurIPS supplemental code can save the full reachable tree through `MCTSResult`, and its OpenAI-compatible client can preserve request-plus-generation responses and usage logs. TreeQuest adds multi-model search, visualization, checkpoint/resume, and ask–tell APIs. These are local capabilities. The supplemental logging directories contain no realized experiment outputs, the repositories do not commit a paper-run trace corpus, and `artifacts.data` and `artifacts.huggingface` therefore remain `null`.
