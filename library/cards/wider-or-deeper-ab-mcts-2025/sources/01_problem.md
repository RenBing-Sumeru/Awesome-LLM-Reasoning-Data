Inference-time scaling is often summarized as “sample more answers” or “refine one answer longer,” but a fixed generation budget creates a concrete allocation problem: should the next model call make the response tree wider with a fresh candidate, or deeper by revising an existing answer after feedback? Fixed-width search chooses this tradeoff in advance and can waste calls either on redundant siblings or on repeated repair of an unpromising branch.

Adaptive Branching Monte Carlo Tree Search (AB-MCTS) turns that allocation decision into the search object. The root stores the task prompt. Every non-root node is one complete, scoreable Python solution or ML-engineering program. A wide move produces a fresh answer from a selected node through its `GEN` option; a deep move follows an existing answer and generates a child revision conditioned on the prior response and evaluator feedback. The resulting data object is not a single chain but a response–revision tree containing candidates, parent/child lineage, generation order, model identity, external evaluation results, node scores, visit/value statistics, and a final selected answer.

Feedback is task dependent. CodeContest and LiveCodeBench use the fraction of public tests passed during search and hidden tests for final evaluation. ARC scores how many demonstration transformations a generated Python program solves, then checks held-out test outputs by exact match. MLE-Bench uses an 80/20 training/validation split for search-time metrics and a hidden test set for final evaluation. These signals are programmatic or environmental surrogates; they do not verify intermediate reasoning and need not agree with hidden-test success.

This work belongs exactly in **Rollout, Search, and Test-Time Trace Data** because response generation, revision, tree topology, external feedback, and budget allocation jointly define the trace. It is an inference-time construction and evaluation recipe, not evidence of SFT, distillation, preference learning, reward-model training, or RLVR. The Card reaches L4 because the paper, appendices, official supplemental code, TreeQuest, and the ARC-AGI-2 repository support a detailed bilingual account. L4 does not imply that the realized experimental trees or logs are public: the release provides executable machinery, not a reusable corpus of paper-run traces.
