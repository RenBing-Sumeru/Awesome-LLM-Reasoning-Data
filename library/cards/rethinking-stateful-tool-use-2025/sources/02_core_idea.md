DialogTool repurposes task-oriented dialogue structure as tool supervision. Services/domains become Apps, intents become APIs, and slots plus values become typed arguments. Source database lookups become API calls. The action vocabulary distinguishes tool-related actions—Request, Confirm, Inform_Count, Notify_Success, and Notify_Failure—from non-tool actions—Inform, Offer_Intent, Req_more, and Goodbye. Tool awareness is therefore state-dependent multiclass prediction, not a binary “call or do not call” label.

VirtualMobile supplies the state transition. Each App is a Python class, each API is a function, and unique lookup results from source dialogues populate an App database. Schema fields describe base required arguments, API-specific required and optional arguments, result fields, types/formats, and whether an API is transactional. Calls execute only after required values are filled; transaction calls require confirmation. Prior results and App/API attributes are available to later responses, making errors capable of propagating across turns.

The same structure supports flat selection—predict App and API together—or hierarchical selection—choose the App, then an API and arguments. The latter usually performs better. However, the paper does not define a recovery controller: missing values may be represented with `?`, and action labels include requests and failure notifications, but automatic retry, rollback, repair, or episode-level recovery success is not evaluated as a separate contract.
