既有编码基准通常在固定仓库状态上评估一次 patch，或把长任务压缩成单一终局 pass/fail。SlopCodeBench 则把智能体自身不断演化的实现作为下一阶段输入状态。其 36 个问题展开为 196 个行为检查点，每个问题包含 3-8 个检查点，因此早期架构、捷径与技术债会被保留，而不是被参考状态替换。

主要方法变化是联合反馈表面。回归感知的 strict 正确性保留路径依赖，isolated 与 core 视角用于定位失败来源；同时，确定性的 erosion 与 verbosity 指标在不使用 LLM judge 的情况下描述结构退化。正确性观测与源码质量观测之间的分离尤其重要：一次较早失败会抹去后续 strict 得分，而缺失工作区会从质量均值中排除。

因此，新数据贡献是环境与 episode schema，而不是开放训练语料库。新运行可以产生 state/action/observation 轨迹、工作区、测试和标量指标，但官方发布的主体是任务/验证器资产。贡献在反馈契约与推理 scaffold，而不是优化器、训练后策略、偏好数据集或 reward-model checkpoint。

规模与工程实现很重要，但不应被误当成概念新意。新的非 root 容器、原生 harness 集成、每问题 2 小时预算、137 条 AST-Grep 规则、快照和固定 runner/问题 commit 让环境可运行，却没有消除模型与 harness 混杂、代理指标误差、公开后的污染，也没有补齐原始实验语料。

最清晰的方向信号是：仓库智能体评测正在从孤立正确性转向路径依赖的状态质量、失败保留与可审计性。复用前应检查 strict/isolated/core 语义、崩溃后续正确性归零与质量缺失排除、prompt/harness 选择、实时 leaderboard 漂移、任务与 runner 许可证、公开测试暴露，以及需要的对象究竟是基准任务还是实际轨迹。
