The primary source is arXiv:2603.24755v2, revised on 2026-05-07, together with the official project, runner, and problem release. SlopCodeBench asks a narrower question than ordinary repository repair benchmarks: when a coding agent must extend its own earlier implementation repeatedly, how quickly do correctness, architectural quality, and efficiency deteriorate?

The evaluation surface contains 36 handwritten black-box software problems and 196 ordered checkpoints, with 3-8 checkpoints per problem. Checkpoint 1 starts from an empty workspace. Each later checkpoint supplies only a new behavioral specification and the workspace produced earlier; prior chat state, hidden tests, verifier results, and quality measurements are withheld. One local episode can contain model, harness, prompt, environment configuration, action/tool trace, per-checkpoint workspace, tests, static analyses, and time/token/cost records. The official release exposes the task and verifier side, but not the complete paper-run episode corpus.

This belongs in Environment and Agent Trajectory Data because the model's actions mutate the persistent state that conditions future actions, and the environment supplies a mixed terminal feedback contract. It is not a policy-training or demonstration-data paper: the evidenced uses are evaluation and audit, and public specifications, tests, and reference solutions carry no-training canaries. It also does not establish general software maintainability; erosion and verbosity are deterministic proxies over source structure.

For the Atlas, the decisive contribution is the auditable boundary between a replayable benchmark environment and a released trajectory dataset. The official arXiv, code, task repository, project page, pinned revisions, tests, prompts, and metric implementations support a dense bilingual Card, while absent historical traces, partial replay, and unresolved rights and contamination questions must remain explicit rather than being inferred away.
