方法上，基准只覆盖 36 个作者设计的问题和 Python track。没有任何配置完整解决一个问题，因此对“干净的成功终局”几乎没有证据。erosion 与 verbosity 虽然是确定性指标，却仍是代理：圈复杂度阈值可能遗漏分布式架构失败，或惩罚天然分支较多的函数；137 条人工整理的 AST-Grep 规则加克隆检测，也无法证明语义清晰度、安全性、可用性或可维护性。

正确性与质量采用不同的缺失数据规则。崩溃或失败会把其余正确性检查点补为 0，但缺失工作区会从 erosion 和 verbosity 中排除。因此质量比较以“存活”为条件，可能偏向那些在产生严重退化的后期代码之前就失败的系统。原生 harness、CLI 版本、推理设置、provider API 与失败处理也不一致，模型排名混合了 base model 与 scaffold 的影响。

实验报告还存在选择与版本边界。主表在 15 个配置中为每个模型保留最佳 just-solve 运行，完整报告包含更多 prompt/harness 变体，实时 v1.0 leaderboard 也持续变化。论文在固定 196 检查点正确性分母上，用 2,869 个实际生成的智能体检查点做质量分析，但完整运行账本、逐配置重试次数、seed、temperature、崩溃、超时和基础设施失败均不可得。2 小时预算也没有 turn 或成本上限，削弱了等计算量比较。

发布完整性是最核心的数据局限。runner v0.3 和问题集 v1.0 支持重新执行，但官方项目没有发布覆盖成功与失败的完整历史轨迹、工作区、快照、验证日志和质量输出。精确回放还缺少论文绑定的 run ID、OCI digest、依赖与网络快照、provider endpoint 版本、随机 seed 策略和不可变结果校验和。可复现的环境描述不等于可复现的历史 episode。

发布后污染会立即出现。全部 36 个问题的测试与参考实现都已公开；canary 只能警告或辅助检测部分直接复制，不能证明受测模型是干净的。部分任务受热门仓库启发，却没有语义/代码/测试重叠清单或记忆探针。直接用该套件训练会破坏后续评测。

权利、隐私和安全状态也只是 partial。runner 采用 MIT，问题仓库采用 Apache-2.0，但二者不会自动覆盖灵感仓库、第三方资产与依赖、473 仓库人类 panel、provider 输出或推理日志。公开 Git 历史可能包含身份元数据，项目未报告同意、脱敏或下架政策。重跑会执行不可信生成代码、安装软件包、允许联网与读写挂载，并使用 provider 凭据，却没有文档化的全局出口白名单、秘密脱敏方案、加固 sandbox 或事件流程。最后这些判断是基于已披露控制与缺失项作出的 curator audit inference，并不表示已经发生安全事件。
