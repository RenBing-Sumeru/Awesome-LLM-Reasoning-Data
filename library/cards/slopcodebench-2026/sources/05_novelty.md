Prior coding benchmarks usually score a patch against a fixed repository state or treat a long task as one terminal pass/fail event. SlopCodeBench instead makes an agent's own evolving implementation the next input state. Its 36 problems unfold over 196 behavioral checkpoints, with 3-8 checkpoints per problem, so early architecture, shortcuts, and technical debt are preserved rather than replaced by a reference state.

The main methodological change is the joint feedback surface. Regression-aware strict correctness retains path dependence, while isolated and core views expose where failures originate. In parallel, deterministic erosion and verbosity metrics describe structural degradation without using an LLM judge. The separation between correctness and source-quality observations is important: one earlier failure can erase later strict credit, whereas missing workspaces are excluded from quality averages.

The novel data contribution is therefore an environment and episode schema, not an open training corpus. A new run can yield state/action/observation traces, workspaces, tests, and scalar metrics, but the official release primarily distributes task/verifier assets. The feedback contract and inference scaffold are the contribution; no optimizer, trained policy, preference dataset, or reward-model checkpoint is introduced.

Scale and engineering matter but should not be mistaken for the conceptual novelty. Fresh non-root containers, native harness integrations, a 2-hour problem budget, 137 AST-Grep rules, snapshots, and pinned runner/problem commits make the environment operational. They do not remove model/harness confounding, metric-proxy error, contamination after public release, or the absence of the original experiment corpus.

The clearest direction signal is that repository-agent evaluation is moving from isolated correctness toward path-dependent state quality, failure preservation, and auditability. Before reuse, inspect strict/isolated/core semantics, crash-zero versus quality-exclusion behavior, prompt and harness selection, live-leaderboard drift, task and runner licenses, public-test exposure, and whether the desired object is a benchmark task or an actual trajectory.
