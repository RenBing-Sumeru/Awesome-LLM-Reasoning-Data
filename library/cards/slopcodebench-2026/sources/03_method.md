The construction pipeline starts with author proposals for novel tasks or tasks inspired by popular repositories. Proposals that do not force meaningful architectural choices, or that frontier agents can solve in one shot, are removed. The authors then write checkpoint specifications, examples, static assets, reference solutions, and black-box tests; validation agents expose ambiguities, and at least one different author reviews each problem for test/specification agreement and solvability. The retained release has 36 problems, 196 checkpoints, and 3-8 checkpoints per problem. The proposal pool, rejection ledger, trial-agent outputs, and adjudication history are not public.

At evaluation time, checkpoint 1 begins with an empty directory. A native Claude Code, Codex CLI, Cursor CLI, Kimi CLI, OpenCode, or related harness receives the current specification and edits the workspace. Each checkpoint runs in a fresh non-root Docker container; only the working directory persists, while installed packages, shell history, agent session, and conversation state reset. Tests, reference solutions, erosion, verbosity, and verifier feedback remain evaluator-side. A complete problem has a 2-hour wall-clock limit with no turn or monetary-cost cap.

After every produced workspace, hidden pytest groups measure core, functionality, error, and regression behavior. Strict success requires all applicable tests, isolated success omits regressions, and core success uses only core cases. A crash or agent failure assigns correctness zero to all remaining checkpoints. In contrast, erosion and verbosity are calculated only when a workspace exists, so missing quality values are excluded rather than zero-filled. This difference is part of the record schema and creates a survivorship boundary.

Static analysis computes erosion from callable cyclomatic complexity and source lines, concentrating mass in functions whose cyclomatic complexity exceeds 10. Verbosity takes the union of source lines hit by 137 curated AST-Grep rules and clone detection, normalized by lines of code. The current runner can additionally serialize user, agent, thinking, and tool-use steps; workspace snapshots; evaluation and quality JSON/JSONL; per-test outcomes; infrastructure status; diffs; and token, step, time, and cost fields.

The official task side includes v1.0 specifications, tests, reference solutions, assets, and canaries under Apache-2.0. The v0.3 runner, prompts, configs, lockfile, metric code, Docker workflow, and snapshot/evaluation machinery are under MIT. The stable anchors are problem commit 4d38d300059667d57e43c31969bc455f5c338b52 and runner release commit 25bd2b9a216df93e85bb46f741c0e2d1f422b111. The project does not publish a paper-bound manifest of historical run IDs, workspaces, trajectories, test logs, quality records, seeds, provider snapshots, or OCI digests.

No training optimizer is involved. Main reporting uses all 36 problems and a fixed 196-checkpoint correctness denominator; the main per-model table selects each model's best just-solve run, while the fuller table retains prompt and harness variants. Temperatures, seeds, complete repeated-run policy, retry/rate-limit behavior, and full sampling ledger are unknown. The warranted use is evaluation and audit, not SFT, RL, reward-model training, or trajectory distillation.
