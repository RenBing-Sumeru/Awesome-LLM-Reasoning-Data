**Inputs and task state.** The reported backend is Gemini 3.1 Pro. Each run starts from a Lean theorem statement, its definitions and dependencies, Mathlib context, LeanSearch retrieval, and an initially open root OR node. Lean-IMO-Bench contributes 60 records split 30/30 into Basic and Advanced; the experiments also use 12 Putnam 2025 statements and two combinatorics case studies. The paper does not disclose the exact Gemini snapshot, Lean version, Mathlib commit, LeanSearch index, prompts, temperature, or token limit.

**Direct formalization.** The model drafts an informal proof, translates it into Lean, executes the compiler, reads errors, retrieves relevant material with LeanSearch, and revises. In the component study, iterative formalization uses one initial attempt and up to 20 compiler-feedback revisions. A complete Lean-accepted proof resolves the current goal; failure triggers decomposition. (Figure 1; §5.1.)

**Blueprint and search path.** The model writes an informal blueprint with proposed supporting lemmas, then produces a formal proof sketch in which the parent proof is sorry-free and `sorry` may appear only in the newly proposed lemma statements. Lean checks this conditional parent derivation. An LLM reviewer separately assesses whether the decomposition is relevant, easier, and plausible. The state writer checks that the update keeps the dependency graph acyclic; accepted decompositions become AND nodes with child OR goals. The agent uses depth-first search, backtracking, and shared lemma nodes until all dependencies of a root-supporting AND node are proved. (Paper §§2.2-2.5; Appendix C.)

**Outputs, selection, and use.** The internal episode can contain informal plans, proof sketches, goals, DAG edges, candidate code, compiler messages, reviewer decisions, and budget counters. The released artifact contains completed Lean proof files, not that episode schema. Tables 2 and 4 mark LEAP as `rollout=2`; Table 3 reports 46 to about 3,000 LLM calls, 8 to 211 active nodes, and 300 to about 2,000 proof lines across solved Putnam problems. The terminal selection rule is a complete Lean-accepted proof. These outputs support evaluation, test-time-compute comparison, and audit, not a paper-demonstrated training objective.

**Reproduction boundary.** Pin arXiv v2, repository commit `96fa6c4cc3a9bb7450ee7b6773b659d3a030dace`, the benchmark CSV, every theorem file, Lean/Mathlib/LeanSearch revisions, model/API snapshot, prompts, sampling settings, rollout/revision limits, and per-problem call and wall-clock budgets. The release does not supply the LEAP implementation, an environment manifest, or failed trajectories, so the public artifacts permit proof inspection but not end-to-end replay.
