For the data-construction/open-release track, FastMCTS is a useful reference for turning a token-budgeted search process into multiple supervision views. A careful implementation can preserve source problem IDs, full tree topology, parent-child steps, prompt/few-shot revisions, generated-token counts, every judge vote and retry, backed values, accepted and rejected paths, and the exact SFT or preference objective. Those records enable audits of search-induced sampling balance and of how step labels change with additional visits.

Reuse should distinguish the released recipe code from the unreleased experimental dataset. Builders should pin a commit and dependencies, replace placeholder endpoints, publish paper-matched configs and seeds, cap and log verifier retries, and avoid calling a zero-score child “incorrect” without coverage evidence. Failed branches are valuable audit data and should be retained. Cross-domain use remains an extrapolation until verifier semantics and search behavior are tested outside mathematics.
