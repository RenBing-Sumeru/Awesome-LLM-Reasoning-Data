CREST creates two labels for a generated rationale. The original-answer score `z` is binary: after the model reads the question together with that rationale, `z=1` when its greedily decoded option equals the dataset label. For an originally correct candidate, the method asks `F` additional yes/no questions, one per answer option. The correct response is yes only for the labeled option and no for every other option; `z_tilde` is the number of these `F` judgments that match the labels.

The 16 rationales are candidate traces, not 16 independent questions or votes over final answers. The score object is also option-wise before aggregation: a ReClor item normally supplies four binary outcomes, CommonsenseQA five, and ARC usually four with a small number of five-option items. The released implementation computes the probes only after `z=1` filtering, so an originally incorrect rationale has `z` but no `z_tilde`.

SFT and DPO consume different transformations of these labels. SFT retains `(question, rationale, gold answer)` when `z=1` and `z_tilde >= F-t`; `t=0` requires every option probe to be correct, while larger `t` deliberately admits known misses. DPO first creates `P_z`, where a `z=1` rationale is preferred to a `z=0` rationale for the same question. It separately creates `P_z_tilde` only between two `z=1` rationales when one has a strictly larger `z_tilde`; equal scores produce no preference.

The final DPO stream randomly mixes the two pools. If `lambda=0.4` and 10,000 pairs are requested, the paper's example draws 4,000 from `P_z_tilde` and 6,000 from `P_z`; pool size is tied to maximum steps times batch size. Thus `z_tilde` is a label-derived scalar reward and ranking signal, not a learned reward model, formal verifier or step-level process label.
