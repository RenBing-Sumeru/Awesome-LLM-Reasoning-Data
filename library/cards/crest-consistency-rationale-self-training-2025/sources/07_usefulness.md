For `data_construction_open_release_recipes`, CREST is useful as a compact worked example of converting a labeled multiple-choice item into more than one training signal. One source label supervises the original answer, an option-wise behavioral vector, a scalar consistency count, a tolerance decision, a correct-versus-incorrect preference pool and a consistency-ranked preference pool. The public code makes those transformations inspectable even though the derived data are missing.

An auditable candidate record should preserve the upstream dataset and revision, split and stable item ID, exact options and label, base checkpoint/tokenizer, instruction and few-shot revisions, decoding parameters and seed, all 16 rationales, every original prediction, and `z`. For each `z=1` candidate it should add the full option-wise inputs, raw outputs, parsed yes/no values, parser version, expected labels, match vector and `z_tilde`; storing only the count is insufficient.

Decision records should separately retain the SFT threshold `F-t`, accepted/rejected status and reason, every potential `P_z` and `P_z_tilde` pair, tie disposition, selected pool, `lambda`, sampling seed, chosen/rejected IDs, and the exact batch or epoch that consumed the pair. Model records should pin LoRA/DPO settings, software, validation selection and checkpoints. This lineage would let a curator distinguish generation quality, probe reliability, filtering behavior and optimizer effects.

The recipe is best reused where answer options and trusted labels make option-specific counterfactual probes cheap. Builders extending it should test independent evaluators, preserve vectors instead of counts, measure parser error, use a reject-all path for uncertain probes, and audit decontamination and rights before publishing. For open-ended tasks, an equivalent set of independently checkable consequences is required; the current option template does not supply it.

The repository is sufficient for method replication but not for consuming a ready-made CREST corpus. Prepared upstream JSONL files should not be described as generated rationale data. Downstream benchmark improvements justify investigating the recipe; they do not certify the absent SFT and DPO objects.
