核心思路是把测试构造拆成“输入生成”和“输出标注”两部分。LLM 为每道题编写输入生成器与验证器，再用不同尺度参数执行这些工具，得到候选输入。种子题通过其 oracle solution 生成输出标签；合成题没有 oracle，因此利用可执行的 QWQ-32B 解答之间的一致性，同时推断期望输出向量和应保留的解答。

| 契约要素 | 论文或发布提供的内容 |
|---|---|
| Prompt | 专家种子题及参考解答，或经过变换的合成题 |
| 测试输入生产者 | 带尺度控制参数、可使用 CYaRon 的 LLM 编写 `generate_test_input` |
| 输入接收条件 | 对每个生成输入执行 LLM 编写的 `validate_test_input` |
| 种子题输出标签 | 运行所提供 oracle solution 得到的输出 |
| 合成题输出标签 | 16 个 QWQ-32B 候选在至少 50 个共享输入上的一致性 |
| 轨迹目标 | 长推理响应与实现代码，监督粒度为 answer level |
| RL 就绪对象 | 题目行及相连的输入输出测试行，并非论文已经展示的 RL 训练运行 |

论文描述的是对完整输出集合做多数一致性判断。公开脚本实现了一个更窄且不同的过程：它对每个输入分别取 plurality，只有在所有输入上都匹配所选输出的解答才算一致；一致性阈值采用严格的 `>`，还会删除所有测试输出都相同的题目。因此，本卡分别记录论文契约和公开代码行为，而不把二者混为一谈。

一致性是可执行 verifier，不是可信 oracle。共同的教师偏差、不完整的生成输入或错误的验证工具，都可能让多个候选在同一错误上达成一致。论文通过 oracle 对比直接测量了这一差距：在 3,150 个测试上报告的输出标注准确率为 96.8%，扩大到 27,613 个测试后为 92.8%。
