Prior tool-use benchmarks often reduce success to an answer string, a single API call, or a short isolated workflow. Environment-agent benchmarks add state and multi-turn execution, but they differ in whether they expose the action/observation trace, target state, collateral changes, failures, and replay metadata. Against that baseline, ComplexMCP combines a large MCP interface with cross-application dependencies, seeded perturbations, manually accepted reference trajectories, and a final-state verifier that separately reports task completion and unintended change.

The concrete change is the evaluation object and feedback interface. A 47-task record couples the natural-language instruction and application set to a seed, a successful human reference trace, a target nested environment state, and state-difference metrics. Because the verifier penalizes collateral modifications rather than checking only the requested target, it makes side effects visible as a first-class evaluation dimension.

Several components are not new in isolation: ReAct, embedding-based tool retrieval, synthetic application state, programmatic final-state checks, and human-written demonstrations all predate this paper. The benchmark's direction signal lies in integrating them around MCP-scale interdependent state and making the evaluator implementation inspectable. Its 315-tool scale is an engineering expansion, not by itself evidence of better trajectory data.

The release also provides a useful negative lesson for reasoning-data curation. Publishing one successful reference episode per task makes task semantics and tool paths inspectable, but omitting all evaluated success/failure rollouts prevents audit of model behavior across the three trials. Public target states and evaluator code improve transparency while also enabling contamination and benchmark-specific optimization.

Before reuse, a researcher should verify a paper-era immutable release, complete rollout retention, task and provider manifests, rights for task rows and generated outputs, replay behavior under injected faults, and independent tests of fuzzy comparison, exclusion keys, collateral-change accounting, and prompt-injection exposure. Benchmark performance is not a substitute for those quality checks.
