The prior baseline is API and function-calling data built around isolated user requests and target calls. Such records can teach tool schema adherence but do not naturally represent incremental disclosure, clarification, multi-step state changes, or recovery across a dialogue. APIGen already supplies related function-calling data; tau-bench supplies executable Retail/Airline tasks and policies. APIGen-MT does not invent those components.

The concrete change is to make a validated task blueprint the bridge between environment specification and conversation. The blueprint records intent, ordered ground-truth actions, expected outputs, and state effects before a user simulator and test agent realize the task. Programmatic execution/policy checks and LLM committee judgments refine this object; reverse task recombination expands multi-action complexity; a final state/output predicate selects successful episodes. This separates task correctness from surface dialogue generation more explicitly than directly prompting for a transcript.

The data object also changes from an isolated function call to an episode with human messages, assistant text, function calls, observations, policy context, and tool schemas. The feedback attaches both to blueprint fields and to the full episode. However, the released 5k object exposes only the transcript-side fields, so the novelty of the construction contract is not preserved as reusable per-row supervision.

What is not new includes API dependency graphs, LLM-generated synthetic data, majority-vote model judging, Best-of-N sampling, self-critique, executable environments, behavioral cloning, or tau-bench itself. The contribution is their integration into a blueprint-to-simulation pipeline and the reported use of reverse recombination and state/output success for multi-turn data selection. It does not establish a new RL algorithm, reward model, preference interface, process verifier, or openly replayable environment.

For reasoning-data research, the direction signal is that environment-grounded agent training data needs two schemas: a rich construction/audit record and a compact model-facing transcript. APIGen-MT shows the value of the former in the paper and releases only the latter in 5k form. Reuse therefore requires checking the missing blueprint-to-row lineage, failed attempts, verifier calibration, environment pin, mixture mapping, and license constraints rather than treating scale or model scores as sufficient quality signals.

Version drift is itself part of the novelty audit. The final proceedings report 5 read and 13 write APIs, whereas the current project page reports 15 read and 13 write APIs. The public release contains 5k rows, while experiments reach 8k and final models use a broader mixture. These differences should remain explicit evidence boundaries, not be harmonized into a cleaner but unsupported story.
