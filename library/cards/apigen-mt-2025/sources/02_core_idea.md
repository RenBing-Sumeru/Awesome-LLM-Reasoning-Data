The one-sentence contribution is a two-phase recipe that first constructs and validates an executable multi-action task blueprint, then realizes it as a simulated multi-turn human-agent-tool episode and retains only successful episodes for behavioral cloning.

Phase 1 builds a dependency graph over APIs, samples paths and context from executable Retail/Airline APIs, domain policy and data, PersonaHub personas, and examples, and generates a blueprint with intent `q`, ground-truth actions `a_gt`, and expected outputs `o_gt`. Validation combines JSON/format checks, executable checks of API names, arguments, and types, state `diff_patch`, policy tests compiled to Python unit tests, and an LLM committee scoring Correctness, Completeness, Satisfaction, and Creativity. Failed proposals can be revised from summarized feedback; reverse task recombination joins validated actions and outputs into longer tasks and revalidates policy and semantics.

Phase 2 separates three actors: a simulated LLM human incrementally reveals the intent, GPT-4o operates as the function-calling test agent, and the executable tau-bench-derived environment supplies tool results and latent state transitions. The simulated user uses Best-of-N self-critique with N=4. Each task is attempted up to three times; all unique successes are aggregated, while failed Phase-2 trajectories are discarded.

The feedback contract has distinct scopes. Format, execution, and policy checks reject malformed or disallowed blueprints; an LLM committee judges semantic task quality; the environment and expected-output matcher produce binary full-episode success `r=1`. These systems can observe serialized calls, policy-test behavior, expected outputs, and final state effects. They cannot establish that every accepted conversation is natural, that committee judgments are calibrated, or that intermediate reasoning is correct. The released 5k rows omit all verifier outputs and reward fields, so the construction signal cannot be reconstructed from the public transcript alone.

The key distinction from APIGen-style single-turn function-calling generation is the validated blueprint-to-dialogue conversion under a simulated user and mutable environment. It should be read alongside `tau2-bench-2025` for the neighboring agent-evaluation and terminal-predicate problem and `magnet-tool-use-2025` for adjacent multi-turn tool-use data. APIGen-MT's specific role is a success-filtered training-data recipe and partial release, not a new replayable benchmark environment.
