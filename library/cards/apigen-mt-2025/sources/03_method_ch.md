输入包括 tau-bench 衍生的 Retail/Airline Python-function API、domain policy/record、API metadata、PersonaHub persona 和 few-shot example。当 B 可消费 A 的输出且 policy 允许二者共同出现时，API graph 建立 A 到 B 的边；random walk 选择多 API context，write API 则锚定 ground-truth action。最终 proceedings 论文写的是 5 个 read API 和 13 个 write API，而当前项目页写的是 15 个 read API 和 13 个 write API。两者是不同版本来源的差异，不能静默合并成同一计数。

Phase 1 生成包含 model thought、user intent、有序 ground-truth action、expected output 和 state diff 的任务蓝图；随后执行格式/JSON 验证、API 名称/参数/类型的可执行检查、以 Python unit test 表达的 policy test，以及 LLM committee rubric scoring 与 majority voting。分数高于阈值的任务被接收，失败任务则获得汇总反馈并迭代修订。committee 成员、模型版本、数值阈值、temperature、seed 和精确采样分布均为 unknown。reverse task recombination 会拼接已验证 action/output、合成组合意图，并重新运行 policy 与语义验证。

Phase 2 使用 LLM user、function-calling 模式的 GPT-4o 和可执行 environment 对蓝图进行 rollout。user simulator 通过 self-critique 从四个候选回复中选择一个；每个任务最多有三次 trajectory attempt。交互在用户结束时停止——appendix prompt 使用 `###STOP###`——或达到预设 turn limit 时停止。只有最终 environment-state effect 与 ground-truth action 一致、assistant response 与 expected output 一致的运行才保留。所有唯一成功运行会被保留，失败的 Phase-2 运行会被丢弃。精确 response matcher、turn limit、endpoint revision、解码设置和逐行 actor lineage 均未披露。

训练时，每条保留轨迹会在每个 assistant response 处分割；prompt 与非 assistant token 被 mask，因此 loss 只预测 assistant 文本和 function call。论文报告的 filtered behavioral cloning 使用 LLaMA-Factory、full fine-tuning、DeepSpeed ZeRO-3、FlashAttention 2、bfloat16、AdamW、最多三轮 epoch 和一台 NVIDIA H200 节点，base 包括 Llama 3.1/3.2 Instruct 与 Qwen 2.5 Instruct。APIGen-MT 轨迹还与 APIGen function-calling data 及其他 xLAM/ActionStudio agentic data 混合；精确数量、权重、deduplication 和 checkpoint-specific mapping 为 unknown。因此证据只支持 SFT/agent behavioral cloning，不支持 preference learning、reward-model training、process supervision 或 RL。

公开输出是 `Salesforce/APIGen-MT-5k`：5,000 行、一个 `train` split、一个 `apigen-mt_5k.json` 文件，没有公开失败 split。官方明确称它只是 xLAM-2 训练数据的一个子集。Appendix B 的实验把 APIGen-MT 样本扩展到最高 8k，最终 xLAM 模型还使用其他数据集；所以 gated 5k 文件既不是最大实验条件，也不是完整 xLAM 训练混合。
