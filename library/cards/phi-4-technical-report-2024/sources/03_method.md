Organic-data preparation starts with targeted acquisitions and filtered bulk sources. The report names academic papers, educational forums, programming tutorials, licensed books, arXiv, PubMed Central, GitHub, CommonCrawl, and Wikipedia as examples, but does not publish a complete source inventory. Web dumps are ranked with small classifiers trained on LLM annotations; multilingual documents use fastText language identification and similar quality filters. Custom parsers ingest HTML, TeX, ePub/XML-like files, Word documents, and PDFs.

Synthetic construction begins from curated seeds. Roughly 50 dataset families use different multi-stage procedures. Techniques include rewriting passages into exercises and discussions, extracting deduction chains as Q&A pairs, iterative self-revision against reasoning and factuality rubrics, and instruction reversal that derives a task description from existing code. Question pools are filtered by generating multiple answers: unanimous agreement is treated as too easy, complete inconsistency as too hard or ambiguous, and plurality answers may replace unavailable ground truth for rejection sampling. Code and some scientific records can be checked with execution loops or tests.

The final pretraining/midtraining run is reported as 9.8T tokens. The report's about-400B figure refers to unweighted synthetic source tokens; final allocation, unique-document count, epoch/repetition accounting, and exact source proportions are unknown. Midtraining extends context to 16K. The official model card reports 1,920 H100-80G GPUs and 21 days, but generation and filtering compute are not separated.

SFT uses one round and about 8B chat-formatted tokens across math, code, reasoning, conversation, model identity, safety, and 40 languages. Prompts mix public instruction data and synthetic prompts; multiple responses are generated and selected by LLM evaluation. The evaluator checkpoint, prompts, candidate count, score distribution, threshold, accepted-record count, and exact SFT mixture are unknown.

Pivotal Token Search recursively examines a completion by estimating oracle-checked success probabilities from sampled continuations before and after segments. It subdivides by cumulative token log-probability and turns a token that sharply increases or decreases success into a single-token accepted/rejected pair. Code can use a comprehensive test suite; math can compare the final answer with ground truth. The search is not guaranteed to find all pivotal tokens unless success probability is near-monotone. Rollout counts, thresholds, memoized estimates, and oracle implementations are not released.
