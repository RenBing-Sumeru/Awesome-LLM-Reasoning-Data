BuildBench's contribution is to turn repository compilation into an environment-grounded agent evaluation with human-verified targets, iterative execution feedback, and explicit filename-based terminal metrics.

The benchmark object has two layers. The released task/label layer records repository identity and metadata, compilability, target or cross-compiled executable filenames, documentation-URL trajectories, failure notes, comments, and—in the current test revision—a source commit hash. The evaluated episode layer begins from the repository, README/file tree, and optional retrieved instructions; a Bash Command Generator emits a command sequence `S_k`, an Execution Agent runs it in the container, and execution result `f_k` becomes the next observation. The public release does not serialize this second layer as a complete rollout corpus.

The feedback contract is mixed programmatic/environmental and attaches to the answer artifact and full episode. Online interaction stops when the undisclosed `Success(f_k)` is true or `k` reaches the undisclosed limit `K`. Offline **Completion** requires error-free termination and at least one binary; **Strict Success** requires every expert-listed binary filename; **Flexible Success** requires at least one listed filename. This contract can observe process termination, binary presence, and filename agreement. It cannot establish executable functionality, semantic preservation after patches, security, deterministic rebuildability, or whether the intended program—not a stale, intermediate, vendored, or submodule binary—was produced.

The closest stated comparison is the 100-project CompileAgentBench/CompileAgent line. BuildBench instead begins from a large GitHub C/C++ population, applies keyword/star/fork filtering, randomly samples 385 candidates, and has systems graduate students attempt every build before retaining 148 positives for agent evaluation. Its OSS-Build-Agent also combines README-first file/web retrieval with batched command generation and iterative error repair. These are benchmark-design and scaffold differences, not evidence of a new training objective.

For reasoning-data research, the directional value is the separation of task provenance, interactive state/action/observation behavior, and an episode-level terminal predicate. The release simultaneously demonstrates an audit boundary: task labels and documentation paths can support evaluation construction, but without command-observation traces, environment snapshots, and evaluator code they must not be reclassified as agent-training trajectories.
