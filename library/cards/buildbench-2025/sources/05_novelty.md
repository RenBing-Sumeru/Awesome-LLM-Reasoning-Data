The prior-work baseline is repository-compilation evaluation represented by the 100-project CompileAgentBench and the CompileAgent scaffold. Containers, shell-command execution, compiler-error feedback, web/document retrieval, retry loops, and target checks are established components; BuildBench does not make any one of them a new verifier class or training algorithm.

What changes is the benchmark construction and the visibility of its terminal contract. The authors start from millions of C/C++ GitHub repositories, apply explicit automated filters, randomly sample 385 candidates, and have experienced systems graduate students attempt every build. The 148 compilable tasks are paired with expert target-executable names. Agent behavior is evaluated through a fresh container, optional README/web retrieval, iterative command batches, and three nested outcome measures: unvalidated Completion, all-target Strict Success, and any-target Flexible Success.

The current release also preserves the complete 385-candidate compilability label pool rather than exposing only the 148 positive evaluation tasks. This makes some selection failures inspectable, although failure reasons are populated for only 126 of 237 negatives and no successful or failed agent rollouts are published. The later addition of source commit hashes for all test rows improves task pinning but is release maintenance, not a paper-time methodological contribution.

For environment-agent data research, the useful direction signal is to treat a repository benchmark as a tuple of pinned task source, resettable environment, action/observation protocol, allowed mutation policy, and terminal predicate. BuildBench makes most of that tuple conceptually explicit and shows why “the process finished” is weaker than target-aware verification. The filename predicate still stops short of functional tests, semantic equivalence, or security checks.

Quality should therefore be inferred from the specificity of the task labels, human construction, retained candidate failures, and explicit metrics—not from the best model score. Before reuse, an evaluator must inspect instance overlap with CompileAgentBench and other repository benchmarks, model-corpus contamination, target-label errors, functional behavior of binaries, allowed source changes, environment/dependency locks, full failure retention, release-version mapping, licenses, and sandbox security.
