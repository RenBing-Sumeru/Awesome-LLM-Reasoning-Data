该工作的核心贡献是一条串联契约：把由 issue/patch 派生的仓库任务变为有测试支撑的任务，用这些任务收集智能体轨迹，再用可执行信号和 LLM 中介信号选择轨迹。测试构造不是一次生成：先抽取仓库信息，LLM 写出 Gherkin 场景，后续生成步骤写出 pytest 风格测试代码；生成的测试不正确时还可根据 traceback 修订。目标条件是 fail-to-pass（F2P）：测试应在参考补丁之前失败、在参考补丁之后通过。（论文图 2、§3.2、附录 A.1。）

论文还为模型轨迹增加第二层筛选。DeepSeek-V3 通过 OpenHands 运行；Llama-3.1-70B-Instruct 将模型补丁与参考补丁比较，标记为 `identical`、`mostly`、`partially` 或 `different`。报告的规则只保留 `identical` 或 `mostly` 的轨迹，约占原始集合的 65%。因此，可执行反馈观察的是某一特定修复前/后行为，LLM judge 观察的是文本/代码补丁相似性；两者都不能观察全部语义要求、隐藏回归或数据来源。

最接近的背景是 issue/patch 数据以及带有现有测试的 SWE 数据集（包括 SWE-bench 风格集合和 SWE-Gym）。SWE-Dev 的差异在于显式合成缺失的 F2P 测试，再收集轨迹并筛选补丁质量。它是构造可执行反馈数据的一种方向信号，而不是标量 reward 或 LLM 比较在所有场景下都可靠的证据。
