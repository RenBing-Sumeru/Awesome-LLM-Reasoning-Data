The contribution is a chained contract: turn issue/patch-derived repository tasks into test-backed tasks, use those tasks to collect agent trajectories, then select trajectories with both executable and LLM-mediated signals. Test construction is staged rather than one-shot: repository information is extracted, an LLM writes a Gherkin scenario, another generation step writes pytest-style test code, and a traceback-guided revision can repair a bad generated test. The target condition is fail-to-pass (F2P): the test should fail before the reference patch and pass after it. (Paper Fig. 2; §3.2; Appendix A.1.)

The paper adds a second selection layer for model trajectories. DeepSeek-V3 operates through OpenHands; Llama-3.1-70B-Instruct compares the model patch with the reference patch and labels it `identical`, `mostly`, `partially`, or `different`. The reported filtering rule keeps only `identical` or `mostly` trajectories, approximately 65% of the original set. Thus executable feedback observes a particular before/after behavior, while the LLM judge observes textual/code-patch similarity. Neither signal observes all semantic requirements, hidden regressions, or data provenance.

The closest background is issue/patch data and SWE datasets with existing tests (including SWE-bench-style collections and SWE-Gym). SWE-Dev's distinguishing unit is the explicit synthesis of missing F2P tests plus trajectory collection and patch-quality filtering. It is a direction signal for executable-feedback data construction, not evidence that a scalar reward or an LLM comparison is a universally reliable verifier.
