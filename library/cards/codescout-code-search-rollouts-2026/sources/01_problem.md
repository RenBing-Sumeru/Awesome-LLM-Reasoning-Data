CodeScout addresses a narrow but consequential data problem in reinforcement learning for software-engineering agents: a repository-search policy needs repeated, inspectable attempts and an automatic signal about whether it localized the code implicated by an issue. A final patch test can verify a repair, but it is expensive and confounds search with editing, dependency installation, and execution. Conversely, a single best trajectory hides how often the policy fails, how alternative attempts differ, and which terminal contract generated the learning signal.

The paper converts Python issue-resolution tasks from SWE-Smith into code-localization environments. The agent receives an issue description and a known repository path, searches a faulty pre-PR repository with a Unix terminal, and ends with one structured `LocalizationFinish` call. Gold targets are extracted from the issue's resolution patch at file, module/class, and function/method levels. Dependencies are not installed and tests are not run: this is localization, not repair verification.

The official rollout release is the main data object considered here. Each of its **54,845 rows** records `instance_id`, training `step`, `rollout_number`, a full tool-using chat, tool definitions, and terminal reward components. It contains **39,040 CodeScout-14B rows** and **15,805 CodeScout-4B rows**. The conversations retain terminal commands and observations, while the reward dictionary exposes file-, module-, and entity-level F1 components, their sum, and a multiturn field.

This object belongs exactly in **Rollout, Search, and Test-Time Trace Data** because repeated attempts, their group structure, their terminal scores, and the treatment of rejected or unsuccessful samples are first-class data properties. The release keeps **8,281 zero-localization-reward rows (15.10%)**, not only successful outputs, and many task-step groups contain both zero and positive attempts. That makes the artifact useful for failure and selection audits even though it is online training data rather than a test-time search benchmark.

The release is not fully replayable. Its 54,845 rows exceed the paper-side nominal 4B+14B budget of 51,200 by 3,645; six 4B groups are incomplete; current launch-script defaults disagree with the paper; and rows omit gold targets, repository commits, policy checkpoints, seeds, stop reasons, loss masks, and sampling logprobs. The Card therefore preserves `partial` status and L4: the paper and pinned artifacts support a detailed bilingual account, but count provenance, licenses, and exact replay remain unresolved.
