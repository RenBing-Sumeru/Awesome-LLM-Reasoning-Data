WindowsWorld appears in *Findings of the Association for Computational Linguistics: ACL 2026*, pages 15262–15280, DOI `10.18653/v1/2026.findings-acl.750`; the Card also uses arXiv:2604.27776v1, the full appendices, and official repository commit `fbccd464…` as primary sources. The paper asks how to evaluate GUI agents on professional workflows that require several Windows applications, long planning horizons, conditional decisions, and explicit recognition that some instructions cannot be completed.

The benchmark addresses two coupled deficits. Existing desktop environments contain many single-application or short tasks, while binary terminal success collapses all partial progress to zero. WindowsWorld therefore supplies 181 tasks across 17 applications and attaches state-based intermediate checkpoints to the task specification. The four levels are L1 single-app atomic, L2 multi-app linear, L3 dynamic reasoning, and L4 infeasible; the official paper reports 77.9% multi-app tasks and 4.97 checkpoints per task (Paper §§1, 3.2–3.5; Table 1).

One public benchmark instance is not a demonstrated training trajectory. In pinned `benchmark.json`, a row contains bilingual instructions, persona, level, involved applications, preconditions, an `environment_setup` request, `evaluation_metrics` with intermediate checks and a final criterion, validity/duplicate metadata, timestamps, and review fields. A run can add observations, actions, screenshots, local environment signals, checkpoint decisions, and final success, but those executed episodes are generated by the user’s agent and runner.

This belongs in `environment_agent_trajectory_data` because the task record, VM state, observation/action trace, terminal behavior, and evaluator jointly define the research object. It does **not** establish an SFT/RL trajectory release: the official repository contains all 181 task definitions and execution code, but no complete corpus of the authors’ successful, failed, timed-out, or retried runs. The paper presents an evaluation benchmark and diagnostic feedback surface, not a post-training recipe validated at scale.

The L4 evidence boundary is therefore explicit. Citation, task scale, task schema, runner, judge path, repository license, and current release revision are verified. Exact VM replay, task-specific setup materialization, paper-run configurations, full trajectory retention, and uniform task approval are not: the pinned JSON itself marks only 126 rows `approved`, 55 `pending`, 160 validity records true, and 21 false. The Card remains `L3_summary_ready`, keeps Review state `new`, and treats those inconsistencies as audit findings rather than silently repairing them.
