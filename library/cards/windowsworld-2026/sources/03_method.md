**Inputs and generation.** The pipeline begins with 16 personas, their daily routines, primary/secondary applications, task level, and an requested batch size. DeepSeek-V3.2 generates bilingual Windows instructions and structured task objects, with web search restricted to allowlisted open platforms such as GitHub, Wikipedia, and Stack Overflow. Exact model snapshot, generation temperature, prompts beyond the published appendix, total candidate count, and retry budget are unknown (Paper §3.3; Appendix D.1).

**Automated refinement and human filtering.** A four-node refiner performs semantic instruction deduplication, asynchronous URL and file/setup validation, LLM dependency reasoning that turns procedural prerequisites into declarative states, and metric refinement that makes intermediate checks observable and path-independent. Four human annotators reject ambiguous/underspecified tasks, subjective criteria, unavailable proprietary software, and inaccessible services. The environment generator synthesizes required `.xlsx`, `.docx`, `.py`, and related files and merges reusable files within a persona. Candidate/rejection ledgers, reviewer-level decisions, exact refiner models, and generated setup artifacts are not public.

**Released object.** Pinned `benchmark.json` contains 181 rows with task ID, English/Chinese instruction, level, persona, apps, preconditions, setup fields, final criterion, intermediate checks, expected final state, validity and duplicate fields, timestamps, review status, and notes. Counts are L1/L2/L3/L4 = 39/80/50/12; direct inspection finds 899 checkpoint strings. The file exactly matches the paper’s row scale, but only 126 rows are `approved`, 55 are `pending`, 160 have `validity_info.is_valid=true`, and 21 are false. Those status fields are unreconciled release metadata, not a curator reclassification.

**Interaction and local trace output.** `hf_run.py` restores the configured VMware environment, supplies screenshot, screenshot+A11y, or SoM observations, and executes PyAutoGUI actions; UiPath uses Computer_13. Level caps are 15/25/40/20 steps. The runner writes post-action PNGs and `traj.jsonl` entries containing step, response, action, reward, done, info, and screenshot filename, then writes checkpoint/final decisions to `result.json`. These are local outputs. The official tree does not ship the paper’s complete experimental runs.

**Evaluation and supervision.** For L1–L3, Qwen3-VL-Plus produces binary checkpoint and final-state labels from instructions, actions, screenshots, and criteria. This yields process-level and episode-level scalar feedback, not verified action-level supervision. For L4, empty actions or a final FAIL action produce terminal success programmatically; intermediate checks are ignored. The paper uses the signals only for evaluation, with no evidenced SFT, RLVR, PRM, or online RL training. In fact, the authors list reliance on full-trajectory execution and manually reviewed checkpoints as a barrier to large-scale/online RL (Limitations).

**Split, setup, and replay boundary.** No train/dev/test split or contamination control is released: all rows form one public evaluation suite. Reproduction should pin ACL/arXiv identity, commit `fbccd464…`, the 531,900-byte task JSON, VM digest and Windows/app versions, dependencies, agent/judge API snapshots, observation/action modes, prompts, temperatures, seeds, retries, and raw results. Current standard runner calls `env.reset()` without passing the task object and does not visibly consume `environment_setup`, so a reproducer must independently verify how 97 file-generating tasks and 16 downloadable-resource tasks are initialized.
