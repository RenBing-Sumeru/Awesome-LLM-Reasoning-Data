The prior baseline is not an absence of tool-use training. FTRL builds on established tool-calling models, locally executable functions, current-policy rollout, GRPO, Reinforce++, and tool-use benchmarks. Programmatic rewards and multi-turn environment interaction are therefore components to audit, not grounds for an unsupported “first” claim.

What changes is the construction-to-training interface. A manually authored question/answer is decomposed into scenario-specific hidden subanswers; GPT-4o helps synthesize tool documents and Python implementations; a policy interacts with those row-specific functions; observations deterministically remove solved subanswers; and an efficiency/completion scalar is attached to the sampled response for policy optimization. The data object is thus neither a static answer nor a complete released episode, but an executable task definition plus transient state/history prefixes generated from the current policy.

The feedback interface is unusually inspectable. The verifier's observable is returned text, its progress state is the remaining-subanswer mapping, and its tool-call reward is `2q/(p+1)`. This makes the link between action, observation, state update, and scalar reward explicit enough to audit. It also makes the weakness explicit: the verifier detects substring-bearing progress rather than semantic task completion, and in-process Python execution expands the trust boundary to every released row.

The five-stage scenario/document/function/scaling/deployment recipe is the methodological contribution described by the paper, but the release provides prompts and completed raw rows rather than the end-to-end construction program, intermediate generations, or human review record. Similarly, using VeRL, GRPO, Reinforce++, Qwen models, or temperature-based sampling is inherited scaffolding; the current repository's later state and one-epoch scripts are release engineering, not evidence of a new learning algorithm.

For `environment_agent_trajectory_data`, the direction signal is to publish executable environment definitions together with explicit progress state and reward code, while distinguishing those definitions from sampled trajectories. Quality signals are concrete schema, code-level verifier behavior, retained error observations, and ablations that reveal reward tradeoffs—not the best benchmark score. Before reuse, researchers must still verify semantic calibration, adversarial substring behavior, sandboxing, five-stage lineage, full trajectory retention including terminal outputs, split/contamination controls, immutable versions, licenses, and checkpoint-to-result replay.
