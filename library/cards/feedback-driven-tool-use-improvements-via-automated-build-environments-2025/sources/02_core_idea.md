FTRL's central contribution is to synthesize row-specific, locally executable tool environments and convert current-policy interactions with them into deterministic environment feedback for GRPO or Reinforce++.

The mechanism has two connected objects. The released **environment row** contains the task prompt, final answer, decomposed hidden subanswers, tool documents, Python implementations, and progress fields. The generated **interaction state** contains the growing `messages` history, assistant tool calls, tool observations, the updated unresolved-subanswer set and solve rate, and a scalar reward attached to the last valid response token. Only the first object is released as raw train/test data; the second is produced by `Code/data_sample/data_sample.py`, and the paper-run outputs are absent from the repository.

The feedback contract is programmatic and environmental. For each tool-calling response with `p` calls and `q` newly solved subquestions, the reward is `2q/(p+1)`. A blank response receives `-0.5`; malformed tool markup receives `-0.3`; a response containing the final reference answer receives `1/(1+t)` when `t` subquestions remain; a no-tool response after all subquestions are solved receives `0.5`; other responses receive `0`. The reward manager writes the resulting scalar on the final valid response token. This is state/action-level scalar supervision, not a released sequence of semantic step labels.

The verifier can observe whether a local function executed, what text or error it returned, whether an expected subanswer occurs as a case-folded substring, how many subquestions remain, and whether final-answer text contains the reference. It cannot establish semantic equivalence, factual truth outside the synthesized function, causal necessity of a tool call, safety of the code, or correctness of unobserved internal rationale. Substring containment can reward leaked/colliding strings and reject equivalent answers with different formatting.

The closest comparison surfaces in the paper are tool-use evaluation suites such as ToolHop, tau-bench, and RoTBench and the two optimizer choices, GRPO and Reinforce++. FTRL uses the former for out-of-domain evaluation and adopts the latter as training scaffolds. Its differentiating element is not a new optimizer or semantic judge, but the integration of a five-stage synthetic local-environment construction process with stateful progress tracking and an efficiency/completion reward.

For reasoning-data research, the direction signal is the explicit bridge from environment definition to sampled state, tool observation, verifier update, and policy reward. The same bridge also reveals the audit boundary: executable consistency and benchmark improvement do not by themselves establish trajectory completeness, data quality, safety, or rights for reuse.
