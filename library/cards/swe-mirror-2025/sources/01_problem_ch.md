这篇 2025 年 arXiv 论文处理的是仓库级软件工程数据中的一个具体瓶颈：真实 GitHub issue 容易找到，但重建其准确依赖、构建与测试环境成本高且经常不稳定。既有路线要么为每个历史 issue 单独搭建 Gym，要么在少量可运行环境内合成大量人工缺陷。SWE-Mirror 转而研究：能否把真实 issue 的语义内容迁移到功能相似、且 Gym 已经可用的另一个仓库中。

构造单元不只是 issue 描述。一个镜像任务将目标仓库与 `base_commit` 绑定到生成的 `problem_statement`、引入缺陷或撤销功能的 `mirror.patch`、隐藏验证补丁 `test.patch`、反向得到的参考修复 `fix.patch`，以及完整测试套件的执行日志。下游轨迹是另一类对象：OpenHands 或 MOpenHands 的动作—观察序列，最终产生提交 patch 和由测试给出的 outcome。区分二者很重要，因为论文报告 60,671 个任务，但训练使用的是仅含成功样本的 12,456 条轨迹混合。

该工作属于“环境与智能体轨迹数据”，因为可复用 Gym、可执行状态转换、隐藏测试、智能体工具接口与 terminal predicate 共同定义了监督信号。它没有解决 Gym 自动构建，没有证明每个镜像 issue 都保持语义忠实，也没有提供足以重放的已核实公开发布物。因此，本卡片的 L4 内容深度由论文全文和附录支撑，但训练复用仍受官方 artifact URL 与 manifest 缺失阻断。
