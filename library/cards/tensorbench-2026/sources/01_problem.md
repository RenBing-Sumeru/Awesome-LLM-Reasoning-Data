TensorBench asks a narrower question than generic code generation: can a coding agent extend a real compiler repository with a new feature or behavior-preserving refactor while keeping the tested repository state valid? Repository-level benchmarks are difficult, but their existing tests were not designed to catch arbitrary generated regressions, and scalable human patch review is unavailable. TensorBench chooses Scorch, a Python/C++ sparse-and-dense tensor compiler, because its randomized regression suite can compare many externally visible tensor results with dense PyTorch or an unoptimized execution path.

The evaluation surface contains 199 tasks anchored to five Scorch commits: 194 feature-addition tasks and 5 refactoring tasks. A task record includes an instance identifier, repository URL, base commit, natural-language description, relevant files, setup and test commands, timeout, task type, and topical categories. An evaluated episode additionally contains the scaffold/model configuration, repository observations and tool calls when logged, final unified diff, implementation and test edits, pytest outputs, and a terminal pass/fail report.

This Card belongs in Environment and Agent Trajectory Data because the repository state, Docker image, action history, patch, tests, and terminal predicate jointly define the data object. It is not evidence for agent training: the paper reports evaluation and audit, not SFT or RL. Its L4 value is the explicit feedback boundary—fresh-checkout executable grading plus a separate adversarial audit—and the equally explicit limitation that feature behavior is tested mainly by tests authored by the same agent. Official arXiv full text and appendices, the TensorBench project/leaderboard, the Hugging Face task artifact, and the Scorch repository support the account; the paper-claimed prediction and trajectory directories were not accessible for file-level verification.
