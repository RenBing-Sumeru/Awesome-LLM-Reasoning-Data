Prior repository benchmarks commonly start from public issues and judge whether a patch passes repository-specific tests derived from issue or pull-request context. TensorBench instead constructs feature-addition requests against a compiler codebase and grades any behaviorally adequate patch; there is no canonical reference patch to imitate. The unit of comparison is therefore the modified repository state, not patch similarity.

The concrete change is the feedback interface. Existing randomized Scorch tests act as a regression-preservation oracle across shapes, sparsity patterns, formats, and compiler paths, while the evaluated agent supplies tests for the newly requested behavior. A fresh-container grader separates final verification from whatever the agent did in its live workspace. The release design also pairs task records and terminal results with structured trajectories, diff artifacts, failure modes, and a post-hoc adversarial audit.

Not every component is new. Dockerized execution, repository agents, pytest scoring, tool logs, LLM-assisted task authoring, and test-based code benchmarks all predate TensorBench. Its contribution is their alignment around difficult compiler feature work and the explicit analysis of regression preservation, self-authored tests, patch size, and tool-use profiles.

For reasoning-data research, the useful direction is to retain the complete episode and audit the verifier rather than storing only a leaderboard score. Reuse still requires checks that the benchmark repository, image digest, exact trajectories, predictions, reports, and licenses are accessible and pinned. It also requires independent hidden or maintainer tests for a representative subset, because the present terminal predicate can reward a mutually consistent but incomplete implementation/test pair.
