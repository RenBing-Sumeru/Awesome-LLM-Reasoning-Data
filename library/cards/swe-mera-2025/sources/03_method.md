The seven-stage pipeline selects active licensed Python repositories with at least 10 stars and 10 forks; maps exactly one closed issue to exactly one merged PR; downloads issue title, body, and comments; removes descriptions shorter than 25 characters; retains PRs changing both source and tests and fewer than 15 source files; validates repository build; executes the task in Docker; and performs Qwen3-32B quality filtering.

For the 2025-01-01 to 2025-06-01 reference funnel, the paper reports 8.4k repositories/55k issues after one-to-one mapping, 8.2k/51k after metadata filtering, 6.7k/30k after patch validation, 1.6k/9k after build validation, 668 repositories/1.6k issues after end-to-end execution, and 279 repositories/528 tasks after LLM evaluation. Build validation installs the project and pytest tooling, runs pytest with JSON reporting, requires a clean command and at least one passed test, then saves the Dockerfile and cache.

Evaluation uses a modified Aider workflow. Each issue receives up to six independent attempts, and each attempt allows up to four reflections over lint or test output. `pass@1` records first-attempt success; `pass@6` records success in any attempt. Participants download tasks, run an agent, replace the `patch` column with candidate output, evaluate through `swemera`, and submit results. Trajectory links are encouraged but optional; otherwise the platform displays the associated GitHub PR.

Docker is the default, with local/Conda execution supported. `repotest` cleans back to base commit and accepts row-level image, build/test commands, and timeouts. Exact OCI digests, dependency locks, network policy, and one end-to-end replay manifest are not released; mutable repository, image, dependency, and dataset revisions must be pinned separately.
