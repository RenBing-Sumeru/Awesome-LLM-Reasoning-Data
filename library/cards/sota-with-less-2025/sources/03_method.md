The pipeline can be reconstructed as six linked stages.

1. **Assemble and normalize the pool.** Combine 69,997 reported items from Geometry3K, GeoQA, Geos, FigureQA, ScienceQA, OK-VQA, IconQA, and TabMWP. Randomly cap FigureQA and IconQA at 10,000 each. Convert IconQA, FigureQA, Geometry3K, TabMWP, and OK-VQA to open-ended answering; retain ScienceQA, GeoQA, and Geos as multiple choice. Output rows conceptually contain image, ID, prompt, and answer. Exact upstream split names, original row IDs, conversion code, and random seeds are not disclosed. (Paper §3.1, Figure 3)
2. **Run a target-policy MCTS pass.** Use Qwen2.5-VL-7B-Instruct or Qwen2.5-VL-72B-Instruct as the policy. A state is a reasoning-chain prefix. Selection uses visit counts with `c_puct=1`; expansion samples three actions at temperature 0.5; the released generation configuration also sets top-p to 0.9. Simulation stops at a final answer or ten reasoning steps. The prompt enforces step boundaries and includes two in-context examples. (Paper §3.2, Appendix Table 6; official `mcts.py`)
3. **Apply the construction critic.** Qwen2.5-7B-Instruct receives question, ground truth, and the simulated rationale/final answer, then emits only whether the generated answer is true or false. A true decision terminates the search and records the zero-based iteration index `K`; otherwise the next iteration begins, up to 50. No process reward model is used. The critic prompt does not include the image, and the paper reports no accuracy, calibration, disagreement, or human audit for these decisions. (Paper §3.2, Appendix Table 7)
4. **Filter per target scale.** Retain all rows with `K > 5` plus all rows unresolved after 50 iterations. For 7B this gives 5.4K late-solved and 5.6K unsolved rows, totaling 11K. The independently run 72B selector gives 7.5K. Their overlap is 5.4K, including 3.6K rows unsolved by both policies. A reusable output should include source dataset/split/ID, policy and critic revisions, all sampled steps and critic decisions, `K` or unsolved status, threshold, and selected/rejected status. Those fields are not released as one complete ledger. (Paper §§3.2, 4.4)
5. **Reinforcement fine-tune.** Fine-tune each corresponding base VLM on its selected prompts with Easy-R1 and GRPO; no SFT or knowledge-distillation stage is reported. The paper sets 32 rollouts and uses a prompt requiring reasoning in `think` tags followed by a boxed final answer. It reports 8x80GB A100 GPUs for training and evaluation. Exact reward code, extraction/normalization, learning rate, schedule, batch details beyond rollout count, seeds, stopping rule, and checkpoint selection are unknown. (Paper §§3.3–4.1, Appendix Table 8)
6. **Evaluate and ablate.** Evaluate with vLLM on MathVista testmini, MathVision mini, MathVerse mini, MMMU, MMStar, MMBench, MM-Vet, and AI2D. Compare base policies, random equal-size subsets, self-consistency selection, full-pool training, late-solved-only, unsolved-only, online selection, thresholds, and cross-scale subsets. Evaluation templates follow each reasoning model's codebase, so exact decoding and extraction should be pinned for reproduction. (Paper §4, Appendix B)

The official implementation is not paper-complete. `run_mcts.sh` launches eight chunks, while `mcts.py` defaults to 50 iterations, three actions, temperature 0.5, top-p 0.9, and a ten-step terminal cap. Crucially, the script appends a row only when `solution is not None`; unsolved rows are omitted instead of being preserved as the paper's unsolved-after-50 stratum. Because 5.6K unsolved rows form more than half of the reported 7B subset, the public script cannot by itself reconstruct Hard-11K. Reproduction must additionally pin repository commit, Qwen revisions, pool checksum, chunking, seeds, critic outputs, failure records, Easy-R1 revision, reward implementation, and evaluation code.
