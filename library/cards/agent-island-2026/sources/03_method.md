**Inputs and sampling.** The engine receives a fixed social-strategy rules/config prompt and an active model pool accessed through OpenRouter. It draws seven distinct model identifiers without replacement, assigns anonymized player labels, and seeds local player/order/tie randomness from the game ID. Same-provider matchups are allowed. The paper set spans 49 model identifiers, but exact provider checkpoint revisions, decoding settings, retry policy, and total simulation compute are unknown.

**Rounds 1–5: interaction and elimination.** Each active player can select a sidebar partner and exchange alternating private messages. Active players then make public advancement pitches and privately vote for another active player, supplying rationales. The parser extracts sidebar and vote choices; the environment tallies votes, uniformly breaks ties, eliminates one player, broadcasts the relevant results, and updates memory. Visibility-filtered histories give different players different private/public observations. Logs retain ordered events plus active/eliminated sets, vote tallies, parser metadata, and response/reasoning/usage fields.

**Round 6: terminal jury vote.** Two surviving finalists pitch. The five eliminated players privately vote, with rationales, for a finalist. The finalist receiving the most parsed votes wins; a tie is broken uniformly at random. In the released schema this is round 6, although the paper calls the preceding five rounds the elimination rounds. Models receive no explicit reward for winning, so the terminal predicate is an evaluation outcome rather than a demonstrated RL reward.

**Record construction and selection.** Each JSON output has top-level `game`, `players`, `stats`, and `history`. Game fields describe configuration, rules, phases, status, and error; player fields bind anonymized IDs to model/config/memory metadata; round fields expose state, tally, selected player, and events; event fields preserve prompt, content, role, visibility, reasoning when exposed, parser/usage metadata, and timestamp. The paper analysis keeps completed games with a parsed final selected player. Incomplete games and games lacking a final selection are excluded, but their counts, IDs, logs, and rejection reasons are unknown. Same-provider analysis further requires parsed final votes and finalists from different providers.

**Ranking and analysis.** For each retained game, the ranking stage discards most within-game detail and consumes only the participant set and winner. Bayesian Plackett-Luce uses Gamma(1,1) priors, 2,000 Gibbs iterations, a 500-iteration burn-in, and seed 42. It produces posterior skill estimates and uncertainty. A separate log-derived analysis tests whether final jurors favor a finalist from the same provider. Neither stage verifies intermediate factual claims or causal reasoning.

**Frozen release, replication, and live continuation.** Dataset version 1.0.0 binds 999 game IDs in a manifest with SHA-256 `73ee6cc97ada604830e933131b19ed81839049b19dfcc1a3c970a72dfce862ad`; the dataset index and Croissant metadata describe the release, and each log has a direct download URL. The anonymous replication ZIP has SHA-256 `5b2c7c5262a46c65b51b659b9c3c0b4edb7eb8cf443cb6d2a4489d2d673e8b2d`; it downloads published logs and regenerates posterior samples, analyses, macros, tables, figures, and excerpts, but does not generate new games. The engine is pin-able at commit `e0fa0ee3944f61c97f3d1e64bae8bbd0e9901742`, yet the frozen logs do not bind that commit as their exact generator. The live source must be treated as a separate, time-stamped evaluation stream. Demonstrated use is evaluation and audit only.
