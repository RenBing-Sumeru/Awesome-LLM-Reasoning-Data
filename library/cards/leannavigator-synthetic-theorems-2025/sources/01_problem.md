The authoritative paper entry is arXiv:2503.04772, **Generating Millions Of Lean Theorems With Proofs By Exploring State Transition Graphs**, submitted on 2025-02-16. No conference or journal record was verified, so the venue remains **arXiv preprint**. The L4 review uses the complete 16-page paper, which has no appendix, together with the official `davidsyin/leannavigator` repository and Zenodo record 13989482.

Automated theorem provers need many examples that map a formal proof state to tactics that complete the proof. Mathlib4 supplies executable Lean proofs, but its human-written theorem set is much smaller than ordinary language-model corpora, and blindly enumerating Lean tactics is infeasible: Mathlib exposes more than 200 built-in tactics, while theorem applications expand the practical tactic universe much further.

LeanNavigator treats each intermediate Lean state as a potential theorem. A state contains local hypotheses and a goal; a tactic-labelled edge moves it to another state. If `ProofFinished` is reachable from a state, the tactic sequence on that path is a machine-checkable proof for the state viewed as a theorem. This reframes synthetic theorem generation as exploration of a directed state-transition graph rooted at an existing Mathlib4 theorem.

The generation-time object is therefore richer than a theorem/proof pair. It includes a seed theorem, current and predecessor states, successful tactic edges, error transitions, terminal reachability, and alternative paths. The public Zenodo artifact does not preserve that object. It releases a top-level JSON array whose rows are two strings: serialized proof-state text and proof/tactic text.

That boundary matters for reuse. A formally valid intermediate state is not necessarily a new human-interest mathematical result, and a flat pair does not reveal its source theorem, graph family, rejected alternatives, or verification environment. LeanNavigator belongs in **Data Construction and Open Release Recipes** because it provides both an executable search recipe and an open SFT-style payload, while exposing the audit loss caused by flattening verified search graphs into independent-looking rows. It is not classified as process-supervision data because the public rows contain no step labels, transition trace, or verifier output, and it is not classified as programmatically verifiable outcome data because the Atlas role here is the construction-and-release recipe rather than an outcome benchmark.

The L4 evidence boundary is explicit. The paper, code snapshot `5c06f1477728ab5e349a0792d68461b1b2961ef9`, Zenodo metadata/archive structure, 10,000-row official sample, and notebook-reported 4,702,639 loaded examples were inspected. The full archive checksum was not independently recomputed, proofs were not bulk replayed, and no release manifest binds the Zenodo file to the Mathlib4/Lean/LeanDojo environment, graph ancestry, rejected transitions, or paper-run notebooks. L4 therefore means bilingual review readiness, not a claim of complete reproduction or decontamination.
