SetUpAgent 把仓库文档和执行反馈转换为受历史时间约束的安装与测试命令，使解决 issue 的 pull request 无需逐仓库人工配置即可形成可执行的 SWA-Bench 和 SWEE-Bench 实例。

其机制分为作者定义的三个阶段。命令提取阶段读取仓库文本、CI/CD 文件及其引用网页；依赖解析使用 `uv`，并排除 issue 日期之后发布的版本。迭代测试阶段在干净的 Docker container 中运行候选命令，由 LLM 分类安装、测试或 Python 错误，再修订命令，最多进行四轮。验证阶段先用 LLM 判断安装与测试是否成功，再请求逐测试输出、选择 parser，并在至少 95% 的已解析测试通过时接受该环境（论文 §3.3 与 Figures 1–4，pp. 2–4；Appendix B，pp. 13–20）。

反馈契约有两个不同层次。构造时，LLM 判断、进程退出行为、测试解析和 95% 阈值共同决定环境是否可用；只有人工修复前后两次参考执行都成功且至少存在一个 F2P 测试，实例才会保留。模型评测时，检查过的 harness 只有在候选补丁使全部 F2P 与 P2P 测试通过时才设置 `resolved=true`。该契约能观察补丁应用和已声明测试行为，却不能证明测试范围之外的语义修复，不能发现所有 flaky 或误解析测试，也不能证明通过 95% 测试的环境完全正确。

最接近的基线是 SWE-bench：它同样以人工测试评估仓库补丁，但依赖少量人工配置的仓库。本文改变的是历史环境自动构造，以及向应用和数百个仓库扩展；它没有提出新的 code-agent policy，也没有发布 trajectory schema。其方向意义在于把 agent benchmark 的环境生成器、依赖时间截断、parser、测试分区和 terminal predicate 视为一等评测数据，而非附带基础设施。
