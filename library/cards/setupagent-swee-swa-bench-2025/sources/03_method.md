Inputs begin with real Python repositories and merged pull requests that resolve an issue and modify a test file. SWA combines 468 popular Python applications with 50 DyPyBench projects and deduplicates them to 475 candidate repositories; SWEE starts from the 8,000 most-downloaded PyPI projects under the paper's download/star criteria. Repositories are restricted to permissive licenses. The task formalization is `(R,T,I,E,S*,X*)`: repository, original tests, issue, execution environment, reference test patch, and reference code patch (Paper §§3.1 and 4.1, pp. 3, 5–6).

SetUpAgent first extracts candidate install and test commands from repository text, CI/CD configuration, and linked pages. It uses `uv` to exclude dependency versions newer than the issue date and stores successful commands in a reference database for nearby repository versions. The default agent model is GPT-4o-mini, reported as `gpt-4o-mini-2024-07-18`, with greedy decoding. It then executes commands in separate Ubuntu 22.04-based Docker containers, classifies failures, and revises the commands for up to four iterations. The image digest, complete package manifest, exact `uv` version, index snapshot, seed, retry policy, and total token/cost budget are not disclosed (Paper §3.3, pp. 3–4; §5.1, p. 7; Appendix A Table 9, p. 12).

Validation combines an LLM setup-success judgment with test-level parsing and accepts when at least 95% of tests pass. For benchmark construction, the authors process eligible PRs, split code and test patches, run every test in `T ∪ S*` on the pre-fix repository and on `R ∘ X*`, and label each test P2P, F2P, F2F, or P2F. Cases with failed pre/post execution or no F2P test are rejected. SWA keeps up to 50 valid PRs per repository; SWEE keeps up to 10 after scraping up to 500 PRs (Paper §§3.1, 4.1; Tables 1 and 10).

The released output is one `test` split per Hub dataset. Rows store repository/commit provenance, issue and hint text, reference code/test patches, timestamps, four test-behavior lists, install commands, test framework/commands, and Docker image root. `version` and `environment_setup_commit` are typed but null in the current releases. Complete construction logs, failed attempts, per-row canonical issue/PR URLs, and immutable image digests are absent.

Evaluation submits a candidate repository patch to the SWE-bench-compatible fork. The inspected support branch applies the patch, runs row-specific commands, normalizes and parses logs, and marks the task resolved only when all F2P and P2P tests pass; timeout, missing markers, parser failure, or patch-application failure is unsuccessful. The paper evaluates OpenHands, AutoCodeRover v2, SWE-Agent v1, and ZeroShot variants. No training on SWA-Bench or SWEE-Bench is reported, so the supported use is evaluation only (Paper §§5.1–5.3, pp. 7–8; harness commit `c11e96679247719201db83c06012adb3221b33be`).

Reproduction must pin the PMLR paper version, Hub revisions, non-default harness support branch, parser behavior, Docker images, dependency-index state, and evaluation subset. The public harness fork is not the SetUpAgent generation implementation; no SetUpAgent source or reference-command database was found in the inspected official artifacts.
