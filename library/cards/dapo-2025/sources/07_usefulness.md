For the Data Construction and Open Release track, DAPO is most useful as a recipe and audit case, not as a ready-to-run 1.79M-example corpus. A builder can reconstruct the intended modules: source collection, integer-target transformation, prompt-answer packaging, grouped online generation, final-answer reward, overlong shaping, non-degenerate group selection, token-level loss aggregation, and metric monitoring.

The paper suggests a concrete logging contract for future RLVR releases. Preserve the immutable prompt ID and source, original and transformed task, each rollout, extracted answer, raw correctness, length reward, total reward, token count, group accuracy, keep/drop reason, policy/checkpoint version, and update assignment. Releasing both retained and rejected groups would make Dynamic Sampling auditable instead of hiding the changing curriculum.

Reuse class: **blocked pending verification for direct training**. The public file can support schema inspection and a small controlled reproduction only after pinning revision, deduplicating with an explicit rule, validating target consistency, checking source rights and benchmark overlap, and pinning the training verifier and recipe. The paper and artifacts are already useful as a reading/audit reference for comparing static prompt data with the larger online feedback object.

Useful controlled comparisons include fixed prompt sampling versus Dynamic Sampling, raw correctness versus length-shaped reward, sample-level versus token-level loss, and paper settings versus the pinned official reproduction. Report unique prompts, generated groups, retained groups, total tokens, hardware, and wall-clock cost separately; AIME accuracy alone cannot attribute improvement to data quality.
