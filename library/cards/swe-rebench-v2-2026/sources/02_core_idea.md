The contribution is a language-agnostic factory for turning public repository history into training-oriented executable repair environments, with repository-specific setup and test parsing synthesized automatically and each surviving task paired with a terminal test contract. The paper's unit of scale is therefore not merely an issue prompt: it is a task row plus a repository state and enough environment metadata to execute a submitted patch.

The feedback contract has two distinct layers. During construction, the pipeline applies the `test_patch`, runs the repository's full suite before the solution, then applies the historical solution patch and reruns the full suite; tests changing from fail to pass become F2P, while tests expected to stay passing become P2P. At evaluation time, the released Docker evaluator applies a candidate patch and the `test_patch`, runs `install_config.test_cmd`, parses the final log into PASSED/FAILED/SKIPPED test states, and sets `passed_match` only when the normalized passed-test set exactly equals `PASS_TO_PASS + FAIL_TO_PASS`. It also reports unrecovered F2P tests and regressed P2P tests.

This programmatic/environmental verifier can observe patch application, process exit, parser-visible test identities, and the expected F2P/P2P terminal state. It cannot establish semantic equivalence to the historical fix, maintainability, security, specification completeness, behavior not exercised by tests, or whether a generated parser silently omitted a test. The separate gpt-oss-120b, GLM-4.7, and DeepSeek-V3.2 ensemble filters issue clarity; it is a conservative construction judge, not the terminal correctness oracle and not human verification of every row.

Relative to SWE-bench-style manually curated evaluation sets, SWE-rebench V2 shifts emphasis toward automated training-scale collection across 20 languages, reusable per-repository setup, synthesized log parsers, and two release tiers. Relative to an ordinary benchmark, its central value is the exposed data-construction and environment contract. Existing ingredients—GitHub issue/PR history, Docker, F2P/P2P tests, mini-SWE-agent, and LLM judges—remain identifiable; the contribution is their integration and scaling into inspectable task releases, not invention of each component.
