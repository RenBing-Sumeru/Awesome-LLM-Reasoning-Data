Inputs are public GitHub Archive issue/PR activity, cloned repository histories, issue descriptions, PR discussions, commit SHAs, diffs, test changes, license labels, activity statistics, and primary-language metadata. Candidate repositories must have a permissive license; candidates require a resolved issue, a merged PR, and a PR that changes tests. High-resource ecosystems use thresholds of 25 stars and 15 closed issues, while long-tail ecosystems use 10 stars and one closed issue. A case-insensitive `(?i)(test(?:ing|s)?|e2e)` heuristic separates test files from the non-test solution patch, with inline-test pathologies annotated later. (Paper §3.1; Appendix A.1)

Environment construction first asks Qwen3-Coder-480B-A35B-Instruct to generate language base Dockerfiles. Then mini-SWE-agent v1.14.4, backed by the same model, inspects each repository, installs dependencies, runs tests, and emits repository-level install and test scripts. The production collection uses one setup attempt per repository. Qwen3-Coder-480B-A35B-Instruct also synthesizes a repository-specific Python log parser mapping raw test output to test-name → PASSED/FAILED/SKIPPED; parser regeneration is capped at five iterations. One successful setup is reused across tasks from that repository. (Paper §§3.2, 4.1; Appendix A.2–A.3)

Executable validation applies `test_patch` at `base_commit`, runs the full suite, then applies the historical solution `patch` and reruns the full suite. A candidate survives only when setup and parsing work and at least one test changes from fail to pass. The pipeline then sends issue text independently to gpt-oss-120b, GLM-4.7, and DeepSeek-V3.2 and retains the instance only under unanimous adequacy. gpt-oss-120b adds difficulty, PR categories, A/B pathology codes, confidence, external-URL and test-alignment notes; another prompt extracts the interface exercised by the tests. The paper prompt defines B1–B7, while the current main Hugging Face schema exposes B1–B6.

The larger PR-derived branch reuses successful repository setups for PRs without linked issues. It generates a problem statement from the PR description and gold patch, then applies a refined prompt and post-processing intended to reduce solution leakage. The PR problem generator, interface generator, decoding parameters, exact suspicious-leakage detector, threshold, rejection counts, and measured leakage rate are unknown. Its current release has 126,300 `train` rows and install/F2P/P2P metadata but no top-level prebuilt image field.

For downstream evaluation or RLVR, the official evaluator starts the task image, applies a submitted patch and `test_patch`, executes the full-suite `test_cmd`, and reduces the final parsed state to `passed_match` plus F2P/P2P diagnostics. Supervision attaches to the completed repair episode; no step labels, shaped reward, or released action trace are provided. The authors propose agent training, test-reward RL/RL warm-up, SFT subset selection, and evaluation, but the paper trains no agent and contains no data-training ablation.
