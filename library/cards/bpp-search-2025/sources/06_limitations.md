The public boundary is narrow. StructuredOR exposes 124 final question, structured-label, and objective-value objects, not raw trees, parent-child edges, visited or pruned branches, rejected candidates, final queues, objective or constraint checker outputs, solver logs, terminal-verdict provenance, PRM scores, pairwise scores, or per-example budgets. The official GitHub repository at the audited commit contains only `README.md` and `LICENSE`; it provides no search, parser, solver-validation, training, or evaluation implementation.

Reproducibility details are missing at several stages. The exact GPT-4o snapshot and prompts, sampling settings, retry and stopping rules, parser and Gurobi configuration, numerical tolerances, PRM and pairwise corpus sizes and splits, perturbation logs, optimizer hyperparameters, seeds, checkpoints, and calibration analyses are unknown. Matching a reference objective value is treated as path correctness, but objective agreement alone does not prove that every variable definition or constraint is semantically correct.

The dataset audit is also incomplete. Public records lack stable IDs and template, rephrasing, augmentation, and source-lineage fields. Split rationale, family-level isolation, semantic deduplication, and benchmark-overlap checks are undisclosed; the paper itself warns that parameter-only expansion can produce leakage and overfitting. The 124 checked questions have no exact cross-split duplicate, but that is not a semantic contamination test. The GitHub repository is MIT-licensed, while the separately hosted StructuredOR dataset license is unknown; the repository license must not be assumed to cover the data.

Finally, reported search accuracy is measured on GPT-4o-solvable subsets rather than full test sets. Search cost changes with width and depth, yet record-level compute is absent. Performance comparisons therefore should not be read as dataset-quality evidence or as an equal-budget causal estimate of the selectors’ contribution.
