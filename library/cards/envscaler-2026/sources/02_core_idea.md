EnvScaler’s central move is to scale the executable environment before scaling interaction data. SkelBuilder derives candidate worlds from a filtered task pool, generates state schemas, constraint rules, operations, class code, and documentation, and keeps candidates that survive repeated LLM-agent checking. ScenGenerator then attaches initial state, a task, checklist text, and—in the RL release—Boolean Python check functions. This separates what the agent may do from how final success is measured.

A released environment row contains env_id, summary/introduction, state-space definition, constraint rules, operation and tool schemas, environment class name, executable code and definition, and function details. Across the 191 retained environments, Paper Table 2 reports averages of 4.58 constraint rules, 21.38 state categories, and 18.58 tools. SFT and RL scenarios share environment/task IDs, class name, JSON-serialized initial configuration, and task text; only RL scenarios publicly include checklist_with_func.

The released SFT trajectory record is a conversation or non-conversation transcript containing task_info, serialized tool definitions, system/user/assistant/tool messages and tool calls, simulated-user messages where applicable, and step count. This is genuine published trajectory data. It must not be conflated with the paper’s online RL rollouts: the official collection contains no RL rollout dataset, reward-trace archive, full final-state log, or successful/failed rollout corpus.

The feedback contract is mixed. At RL runtime, each generated check function evaluates a Boolean condition on final environment state, and reward is the fraction of checks passed, producing a scalar in [0,1]. Yet the environments and checks were generated and selected with LLM agents, and raw pass/warning/fail votes, rejected checks, and independent false-positive/false-negative audits are absent. Programmatic execution at use time therefore does not make the end-to-end contract purely programmatic.

Termination is also separate from success. Non-conversation episodes end when the model emits Task Completed or reaches an action limit; conversation episodes end when the simulated user emits ###STOP### or the action limit is reached. Only verifier-bearing RL scenarios compute terminal-state checklist reward. SFT environments intentionally return zero reward and omit check functions, so a clean completion marker is not proof that a released SFT trajectory solved its task.

The closest Atlas comparisons named in the accepted metadata are Feedback-Driven Tool-Use Improvements via Automated Build Environments, EnvFactory, and ScaleEnv. EnvScaler’s verified direction signal is the explicit four-object release and its split between SFT transcript construction and verifier-bearing RL scenarios. This Card does not infer comparative advantages beyond the evidence ledger.
