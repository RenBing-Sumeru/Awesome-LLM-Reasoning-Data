**Inputs and tool curation.** The input pool is RapidAPI-derived tools in ten domains. The authors execute tools under parameter combinations, discard errors, use LLM summaries to remove semantically trivial outputs, refine descriptions from observed input/output behavior, deduplicate functionally identical tools with LLM assistance plus manual verification, and retain tools with meaningful parameter complexity. The output is a catalog of 1,228 tools. Exact endpoint versions, parameter grids, attrition counts, curation-model identity, and adjudication records are undisclosed (Paper §3.1; Appendix Table 8).

**Parallel construction.** The authors manually collect 50 representative task types—five per domain. An LLM synthesizes independent tool-call sets, typically spanning 3–10 or more calls, subject to the task and tool descriptions. The official README describes five trajectories for each tool count from 3 through 10 for every task type, yielding 2,000 parallel references. Each reference is converted into a direct simple query and a less explicit hard query. The paper says automatic LLM validation and human inspection follow; prompts, seeds, rejection counts, reviewer rubric, and exact published generator are unknown.

**Sequential construction.** Tool output fields and input parameters define a directed compatibility graph. Authors manually design chain templates and adjacent output-to-input bindings, after which an LLM instantiates concrete calls and user queries. The reference stores dependency/order information as well as names and arguments. The released design is limited to chains; richer dependency graphs are left to future work. Construction is therefore hybrid rather than fully synthetic or fully manual (Paper §3.2.2 and Figure 1).

**Validation and released outputs.** Generated pairs receive LLM-based automatic validation and human review according to the paper. The public `simple_traj_gen_v2.py` only activates checking/refinement under `--enable_checking`; official sources do not say whether that flag or which checker produced the hosted release. The current Hugging Face row exposes `query`, `tool_list`, `trajectory_type`, `final_answer`, `task_name`, `task_description`, and `tool_count`; raw intermediate API-response snapshots and a rejected-item ledger were not verified. Hosted `tool_list` also differs from code that expects `tool list`, which must be treated as a schema/version risk.

**Evaluation pipeline.** A model receives the query plus a domain-restricted, all-tools, fixed, or retrieved tool pool. Retrieval experiments compare three retrievers with top-20 as the default. Native tool-calling and ReAct conditions are also tested; ReAct executes calls and incorporates live observations. Predictions are scored by programmatic EM/Inclusion/Usage/retrieval metrics, a Claude-4-by-default Traj-Satisfy judge, and an LLM final-answer judge. Provider-recommended/default temperatures are used and thinking is allowed for reasoning models, but most exact decoding settings, endpoint revisions, judge prompt snapshots, and run manifests are not pinned.

**Use and reproducibility boundary.** Outputs are evaluation records and aggregate benchmark metrics, not selected training rollouts. Exact reproduction must pin the paper/PDF version, a GitHub commit, an HF revision and file hashes, tool schema, API endpoint and credential/subscription state, dependency environment, retrieval configuration, model endpoint/decoding, judge revision/prompt, and response fixtures. No single manifest currently binds these objects, and the only hosted split verified is `test`.
