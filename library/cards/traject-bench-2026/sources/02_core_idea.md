The contribution in one sentence is: TRAJECT-Bench binds multi-tool natural-language tasks to fully parameterized parallel or sequential reference trajectories and evaluates models with a mixed contract that separates tool selection, argument use, dependency order, trajectory satisfaction, and final-answer correctness.

The core mechanism begins with a curated tool catalog and two trajectory structures. A parallel reference is an unordered set of calls whose inputs are known in advance; simple and hard queries describe the same underlying behavior at different levels of directness. A sequential reference is a chain built from output-to-input compatibility, manually designed templates, and explicit adjacent-call bindings, so later arguments depend on earlier outputs. The released row couples this reference with task metadata and a final answer, allowing a predicted trajectory to be compared at several levels rather than collapsed into one success bit.

The feedback contract is mixed. Programmatic metrics check Exact Match over reference tool names, Inclusion recall, Usage through normalized argument comparison for tools shared by prediction and reference, and retrieval rate. Parallel EM ignores order, while sequential EM requires it. Traj-Satisfy is judged by Claude-4 by default, and final-answer accuracy is also LLM-judged; ReAct conditions execute tools and receive observations from live APIs. These components observe named calls, some arguments, required order, judged semantic satisfaction, and answer equivalence. They do not establish semantic equivalence for alternate valid trajectories, completeness of the reference plan, correctness of unobserved side effects, stability of live outputs, or calibration of the unpinned judge.

This feedback is not a training reward. It attaches evaluation labels to reference state/action targets and whole predicted trajectories. Inclusion alone does not penalize extra calls, Usage only checks tools common to both lists, and a normal ReAct stop is not a terminal success predicate. Those boundaries matter because a model can score well on one submetric while omitting a necessary tool, adding redundant tools, exploiting exact names, or benefiting from judge/API behavior.

The closest comparisons named in the accepted metadata are Toolathlon, $\tau^2$-Bench, and MCP-AgentBench. Toolathlon emphasizes long-horizon application state plus task-specific terminal evaluators; $\tau^2$-Bench exposes dual-control user/agent state and component rewards. TRAJECT-Bench instead centers a large production-style API catalog and reference multi-tool call structure, especially parallel independence versus sequential dependency. This difference is useful for the atlas, but it does not by itself show greater realism, stronger verification, or better training data.
