- **Count and schema drift:** Paper §3.2 says 5,670, while Table 9 sums to 5,870. The current HF raw tree lacks sequential Email; the Viewer additionally lacks parallel Mapping and exposes 28 configurations. Hosted `tool_list` and code-side `tool list` also differ. Without a tagged manifest and hashes, record counts and schemas cannot be assumed interchangeable.
- **Verifier blind spots:** Inclusion is recall-only and does not penalize extra calls; Usage checks arguments only for tools present in both prediction and reference; name-based EM can reject semantically equivalent tools or accept a name match without meaningful execution. Sequential exact order can also reject valid alternative plans. These are curator inferences grounded in the released metric implementation.
- **Judge risk:** Traj-Satisfy and final-answer accuracy depend on an unpinned Claude-4/default LLM-judge setup. No calibration set, human agreement, repeated-run variance, semantic-equivalence study, adversarial audit, or false-positive/false-negative rate is reported. Judge preference can therefore change scores independently of agent behavior.
- **Dynamic replay risk:** ReAct executes live production-style APIs. Endpoint behavior, content, availability, authentication, subscription tier, rate limits, cost, and output format can drift. No immutable response snapshots, endpoint-version map, reset semantics, or offline replay bundle was verified, so an unchanged agent may receive different observations and answers.
- **Construction lineage risk:** Exact generation/checking models, prompts, temperatures, seeds, command lines, validation flag, rejection counts, reviewer identities, rubric, agreement, and adjudication are undisclosed. The released checking path is optional, so repository defaults do not prove the pipeline used for the hosted data.
- **Split and contamination risk:** The release exposes one public `test` surface and no train/dev/hidden-test or decontamination policy. Public queries, references, tools, and metric code enable future training contamination, reference memorization, retrieval leakage, and benchmark-specific optimization.
- **Retention and completeness risk:** Some visible final answers contain API or JSON-generation failures, but no ledger accounts for successful, failed, rejected, malformed, or dropped records, and no complete evaluated-model trajectory archive was verified. The visible failures do not establish unbiased failure retention.
- **Rights and privacy risk:** GitHub and HF declare MIT, and the paper says data are synthetic or appropriately licensed public data. Those statements do not establish per-tool RapidAPI terms, schema/output redistribution rights, third-party-content rights, or generated-provider-output rights. Record-level PII scanning, consent, and API-output privacy review are undisclosed.
- **Scope limitation:** Sequential cases are chains rather than general graphs, evaluation depends on a finite curated API catalog, and provider-recommended/default decoding is incompletely pinned. Reported benchmark scores do not prove trajectory quality, real deployment validity, legal training reuse, or generalization beyond the tested models, tools, and budgets.
