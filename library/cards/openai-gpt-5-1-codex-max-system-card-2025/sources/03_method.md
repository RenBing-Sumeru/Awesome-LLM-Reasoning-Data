The disclosed pipeline can be reconstructed only at a stage level.

1. **Inputs and prompt sourcing.** OpenAI names broad agentic domains—software engineering, math, research, medicine, and computer use—and four real-world software-engineering task types: PR creation, code review, frontend coding, and Q&A (PDF §1, p.3). Safety-specific inputs include synthetic malware prompts, code snippets, environment configurations, prompt-injection attacks, and coding rollouts with conflicting user edits. Item sources, counts, rights, dates, mixture weights, and split membership are not disclosed.
2. **Generation and interaction.** A synthetic pipeline creates malware-relevant scenarios, including edge cases and adversarial examples (§4.1.2.1, p.7). New Instruction Hierarchy data supplies coding-environment prompt injections (§4.2.2.1, pp.7–8). During destructive-action RL, a separate user model changes the workspace over the rollout (§4.3.2.1, p.8). Generator checkpoints, prompts, sampling, temperature, rollout count, and retained failure policy are unknown.
3. **Behavior and outputs.** The agent produces code changes, answers, refusals or defensive assistance, and long-horizon trajectories. Compaction allows operation across multiple context windows and is described as supporting millions of tokens in one task (§1, p.3). The exact context state, action schema, tool-call serialization, compaction threshold, summaries, and stored trajectory fields are not disclosed.
4. **Feedback.** Malware behavior is conditioned on policy compliance and evaluated with an expert golden set; prompt injections are scored by successful ignoring; destructive-action RL gives positive reinforcement when user changes are not reverted. Evaluation-only feedback additionally includes hidden tests, end-to-end Playwright tests, scenario pass/fail, rubrics, model graders, cheating classifiers with manual review, and expert judgment. Reward magnitudes, aggregation, calibration, grader versions, and the boundary between training and evaluation are unknown.
5. **Filtering and optimization.** The malware pipeline includes adversarial and edge cases, but filtering thresholds, yields, rejection reasons, and failed-example retention are absent. RL is explicitly named only for the destructive-action intervention; optimizer, objective mixture, schedules, batches, checkpoint selection, and total training compute are undisclosed.
6. **Use.** The disclosed objects plausibly support safety alignment and coding-agent RL; the named benchmarks support evaluation, and compaction supports long-horizon test-time compute. The report does not justify broader claims such as SFT reuse, reward-model training reuse, or released agent trajectories.

Reproduction would require fixed prompt and repository revisions, user-model and synthetic-generator versions, environment images and tools, action and patch schemas, reward or grader code, accepted and rejected episodes, train/evaluation membership, sampling budgets, optimizer settings, compaction configuration, checkpoint hashes, and source licenses. None of those artifacts is released. The only verified official artifacts are the OpenAI publication page, Deployment Safety Hub HTML, and official PDF.
