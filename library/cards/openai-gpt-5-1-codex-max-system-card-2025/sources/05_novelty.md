The relevant prior-work baseline is not an open coding dataset but frontier system cards that name broad alignment methods without exposing the data object, feedback event, or environment intervention. Compared with the *GPT-5 System Card*, this report makes coding-agent post-training more legible by naming a synthetic malware scenario object, new coding-specific prompt-injection data, and an RL episode in which a user model creates conflicting edits and preservation receives positive reinforcement. Compared with the later *GPT-5.3-Codex System Card*, it provides a broader package of safety-data and evaluation disclosures rather than only the conflicting-edit intervention.

The concrete change is the visibility of interfaces across a coding-agent lifecycle. Inputs include prompt, code, and environment configuration; interaction can include a user-model edit; feedback can come from policy compliance, non-reversion reward, hidden tests, Playwright, environment success, rubrics, model graders, or experts; long-horizon operation is enabled through compaction across context windows. This makes it possible to distinguish answer-level safety examples, full-episode RL, executable benchmark episodes, and deployment safeguards rather than collapsing them into one generic "safety training" claim.

What is not new is the use of synthetic safety cases, adversarial examples, RL, hidden tests, expert rubrics, or environment-based agent evaluation in isolation. The report does not establish that compaction, preservation rewards, or mixed graders were invented here, and it offers no ablation that isolates the contribution of each training-data component from model, optimizer, scaffold, or inference-budget changes. Its novelty for the Atlas is disclosure granularity and cross-layer auditability, not an unprecedented algorithm or open release.

The directional importance is that frontier coding agents increasingly turn workspace state, user edits, tool interaction, and long-horizon context management into post-training and evaluation surfaces. Those surfaces require episode-level provenance and versioned environments; a prompt-response ledger is insufficient. Before reuse or comparison, a reader must still inspect source rights, task and repository revisions, user-model policy, trajectory retention, reward implementation, grader calibration, failed samples, compaction configuration, train/evaluation overlap, and checkpoint lineage. Because none is released, the Card remains a high-value audit reference rather than a reusable construction recipe.
