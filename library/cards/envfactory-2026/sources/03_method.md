Inputs and environment discovery. EnvGen searches authentic online resources for useful tool ecosystems. Kimi-K2-Thinking acts across environment proposal, drafting, implementation, and verification. Source research notes can retain official documentation, API, or repository URLs, but there is no unified record-level manifest binding every environment to a dated source snapshot or redistribution right.

Environment construction and checking. Search Agent prepares the source-grounded sketch; Code Agent creates a Pydantic database state, Python tool implementation, standardized metadata, and MCP interface; Test Agent writes tests, diagnoses failures, and requests revisions. Verification checks interface/metadata agreement, import and execution, expected output behavior, and state transitions. The inspected repository contains 156 schema-sketch/research files, 88 metadata JSON files, 86 executable tool files, and 84 intermediate checkpoints, which is current-revision inventory drift relative to the paper’s 85 verified environments.

Dependency-aware task sampling. Parameter embeddings propose directed tool dependencies; an LLM adds missing logical edges and removes false ones. Recursive feasibility sampling uses depth 3 and override probability 0.1, then partitions each chain into 1–5-tool turns. QueryGen creates profile, scenario, schema-conforming state, and natural requests. Similarity threshold, paper-run candidate count, generation temperatures, source/API versions, and maximum environment-revision budget are unknown. Current code sets `pass_k: 4`, but that mutable preset is not an immutable paper-run value.

Interaction, selection, and conversion. Qwen3-30B-A3B-Thinking-2507 generates SFT conversations and reasoning traces; DeepSeek-V3.2-Chat generates RL conversations. Sandboxed assistant and simulated user interact until stop or step limit. Among generated candidates, the best solving trajectory is retained, redundant calls/interactions are removed, and correctness-insensitive arguments are masked. SFT conversion expands each accepted tool-call or user-interaction step and removes failed calls. RL conversion makes each interaction turn a row and serializes the initial state, target final state, MCP servers, and reference calls needed by the reward function.

SFT training. The paper reports full SFT with LlamaFactory on Qwen3-1.7B, Qwen3-4B, and Qwen3-8B at learning rate 1e-6, batch size 256, and 3 epochs. Subsequent RL starts from the first SFT epoch checkpoint. Current repository configuration and official HF model cards instead state 1 SFT epoch. These statements conflict; no exact paper-run command, checkpoint hash, or manifest resolves them.

RL training and reward. The paper uses GRPO in VeRL at learning rate 1e-6, rollout size 8, batch size 256, maximum trajectory length 16k, maximum generation length 4k, and 10 epochs. Reward combines order-insensitive reference-call coverage, exact target-state comparison, extra-call penalty, and malformed-call penalty. The paper’s alpha ablation uses values 0, 0.3, 0.5, 0.7, and 1 with length penalty fixed; released configuration defaults to equal trace and state weight.

Scale, split, and replay. Paper units are 1,622 SFT and 953 RL conversations; public units are 26,463 SFT-FILTERED, 53,412 SFT-ALL, and 3,092 RL expanded rows. Current processing code requests a 95/5 conversation-level RL split with default seed 42 before row conversion, but official HF releases expose only `train`, and no immutable split manifest proves that current code produced the paper release. Replay requires pinning both repositories, all three HF revisions, environment code/config, model/API versions, dependencies, and seeds; no lockfile, image, or paper-run manifest binds them.
