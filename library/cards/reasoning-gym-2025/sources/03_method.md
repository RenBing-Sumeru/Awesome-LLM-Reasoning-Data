The pipeline is executable rather than a one-time corpus build:

1. **Inputs and identity.** Select a registered task and provide its full configuration, virtual dataset size, and seed. Appendix A.1 lists more than 100 tasks, while Appendix A.2 shows representative rows whose `metadata` include `source_dataset`, `source_index`, solution state, and difficulty fields. Appendix A.3 publishes easy and hard configurations for the zero-shot study.
2. **Procedural generation.** A task-specific `ProceduralDataset` deterministically derives an item from configuration, seed, and index when these inputs are fixed. Each item returns `question`, `answer`, and `metadata`. Finite virtual datasets expose a chosen length; wrappers can continue generation through reseeding. The current library can materialize those fields as Hugging Face rows, but no canonical official fixed dataset is released.
3. **Composition and curriculum.** A composite dataset selects among named generators using configured weights. In the paper experiments, included tasks are sampled uniformly. Supported curricula expose task attributes such as word length, empty Sudoku cells, or number range; the reported controller increases difficulty when performance exceeds 70% over the previous 20 steps (Paper §5; Appendix A.6).
4. **Policy rollouts and reward.** Most experiments train Qwen2.5-3B-Instruct with GRPO through a modified `verl` stack. The Appendix A.6 example uses a 20,000-item virtual dataset, prompt batch 32, maximum prompt/response lengths of 4,096/2,048, temperature 1.0, top-p 1, eight responses per prompt, learning rate 1e-6, and 500 steps. The paper's total training reward sums accuracy and a formatting reward scaled by 0.2; evaluation reports only accuracy. A separate qwen-math path produces the RG-Math model.
5. **Selection and outputs.** There is no library-wide accepted-example filter. Each generator enforces its own validity constraints, and each `score_answer` implementation defines correctness or partial credit. Training consumes online prompts, responses, and scalar rewards; evaluation consumes frozen questions and accuracy. Anyone needing an auditable dataset must explicitly persist both successful and failed responses, reward components, exceptions, and training context.

The paper reports identical 50-problem evaluation sets across three independent intra-domain and cross-domain runs, and 50 held-out examples at each curriculum difficulty. It also discloses about 1,500 A6000 GPU-hours rented from Runpod and says the main runs use a four-A6000 node (Paper §4–5; Appendix A.6).

Reproduction requires two separate pins. For paper-era claims, the exact Reasoning Gym commit is unknown, although the current official training README records Python 3.11, CUDA 11.8, `verl` commit `c34206925e2a50fd452e474db857b4d488f8602d`, vLLM 0.7.3, and flash-attn 2.7.3. For current reuse, pin the audited repository revision `49b07130b3fcd12f2d064bba7c43869543a0e7e7`, package metadata `0.1.26.dev0`, task registry, all configs/seeds/indices, native versus cascade scorer mode, and optional `math-verify` version. Current scorer behavior must not be treated as the undocumented paper-era implementation.
