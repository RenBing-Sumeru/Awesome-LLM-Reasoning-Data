- **Version and split drift.** The paper's v1 benchmark has 100 tasks from 68 repositories. The release later added 126 tasks; live manifests now contain lite 50, default 100, default_v2 100, and full 226, while the dataset card still says full 137.
- **Trajectory completeness.** The 115 GB trajectory repository says all raw runs are lightly sanitized, but supplies no per-task coverage, success/failure/timeout/retry index, archive schema, or paper-result mapping.
- **Success semantics.** Runner success means no orchestration exception, not all tests passing. An unresolved task can stop at 20 epochs; invalid pytest output can be archived with gap -1, so resolved and failed states require explicit health labels.
- **Verifier brittleness.** Weak tests permit overfitting and false positives; flaky or environment-sensitive tests cause false negatives. TDD exposes tests, RDD hides them from the Programmer, and short sequences are padded to the 20-epoch horizon.
- **Replay limits.** v1 manifests include archive hashes, but compact v2/full manifests omit repository, license, and hash fields. Python 3.11 setup, apt/npm downloads, API behavior, concurrency, retries, and mutable repositories remain unpinned.
- **Rights and privacy.** Runner code is Apache-2.0 and metadata is CC BY 4.0, but upstream code, tests, packages, images, and model outputs retain separate terms. “Light sanitization” has no published secret/PII method or retention policy.
- **Security.** Third-party code and tests run in Docker while API keys are written into agent configuration; documented controls emphasize 8,192 MB hard memory, 4,096 MB reservation, and 128 MB/s I/O rather than network allowlisting or least privilege.
