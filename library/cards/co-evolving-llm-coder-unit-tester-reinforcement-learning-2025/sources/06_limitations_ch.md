Gold-test 覆盖率是首要有效性边界。CURE 在计算 tester 奖励时，把通过全部可用私有测试的采样程序视为正确程序。若语义错误程序因测试套件不完整而漏检，它就会成为假阳性：既获得 coder 奖励，也可能导致拒绝它的优质生成测试反而受罚。论文没有为这个标注步骤报告 mutation score、覆盖率或假正确审计。

共演化会产生非平稳反馈。由于同一策略同时生成程序和测试，两个角色可能共同收敛到特定格式、输入分布或弱测试情形。Gold tests 能约束该回路，却无法阻止其在覆盖范围之外共适应。因此，生成测试准确率、reward precision 与最终 hidden-test 准确率必须保持为不同测量。

执行环境还带来操作风险。公开数据模式记录时间限制，但论文实验所用的精确隔离边界、依赖镜像、非确定性处理、超时策略和失败分类没有被打包为不可变环境。16×16 矩阵在加入私有测试前，每个任务就需要 256 次生成代码—测试执行，因此环境失败或资源限制可能系统性改变奖励。

发布的可复现性仍不完整。数据、代码、配置和权重均已公开，但 GitHub 仓库没有带标签的 release，也没有可见的代码许可证。当前默认优化配置使用 120 步，而论文中的 7B/14B 模型报告 350 步。随机种子、确切划分成员、完整论文实验 rollout、执行日志，以及被拒绝或格式错误的样本并未作为固定 bundle 发布。

评测主要集中于 Python stdio 编程。函数式任务被转换为 stdio，且若干评测参考程序是通过有限测试筛选的 QwQ-32B 输出。结果未必能迁移到仓库级工程、多文件构建、有状态服务、flaky tests 或安全敏感执行。公开发布名为 private tests 的字段有助于复现，却也使其不再适合作为未来评测中的秘密测试。

最后，准确率提升是关于特定预算下训练模型与 selector 的证据，不能单独证明公开提示、测试、rollout 或验证器标签属于高质量训练数据。
