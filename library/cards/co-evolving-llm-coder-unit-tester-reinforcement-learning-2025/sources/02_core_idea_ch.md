CURE 把代码与测试的交互转化为两个耦合的奖励通道。对于一个任务，同一策略生成 16 个代码 rollout 和 16 个任务派生单元测试 rollout，交叉执行后形成二值的代码—测试矩阵；额外的私有 gold-test 列用于识别通过全部可用 gold tests 的代码候选。

Coder 奖励较直接：通过的私有 gold tests 越多，奖励越高。Tester 奖励不能简单定义为“正确程序是否通过该测试”，因为这种规则会鼓励无区分力的平凡测试。论文从 reward precision 目标推导逐测试奖励：有价值的测试应让被 gold tests 判为正确的代码通过，同时拒绝被判为错误的代码；若测试拒绝了通过 gold tests 的候选，或让大量未通过 gold tests 的候选通过，则受到惩罚。

策略交替执行 coder 和 tester 更新，因此更好的代码采样能为 tester 提供更困难的负例，而更好的测试又能支持更可靠的代码候选选择。对于 long-CoT 的 Qwen3-4B，方法还根据回答长度变换 tester 奖励，在保留奖励正负性的同时抑制过长的测试生成轨迹。

在推理阶段，生成测试可在多个候选程序之间复用：Best-of-N 选择通过最多生成测试的程序。这个测试时 selector 是共演化训练的下游用途，记录时应与训练 episode 以及最终 gold-test 评测分开。
