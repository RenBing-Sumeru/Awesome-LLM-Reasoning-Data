**获取特权最优解是核心假设。** Guided-ReST 需要最优 Countdown 路径或参考程序。Countdown 还假设存在 oracle，能够定位第一个错误步骤及其回退位置。作者指出，普通指令模型未必能可靠地定位推理错误；若改用更强模型充当 oracle，就会引入本文未验证的教师错误与校准问题。

**特权边界随任务而异。** Countdown 会有意把最优运算和算术状态插入保留轨迹。这可能教授有用的恢复结构，也可能传递目标模板，使记忆与搜索能力难以区分。代码修复通过在 SFT 前替换真实参考程序，建立了更清晰的文本边界；但复现时仍需检查序列化消息、loss mask、路径和测试夹具，确认特权 token 没有从其他位置残留。

**交互反馈与筛选反馈并不相同。** 代码回合向模型展示选出的公开测试失败，官方整理流水线却用任务附带的全部 ground-truth tests 为候选打分，并只保留正分记录。这可能在消除可见公开测试失败的同时，隐藏其他候选被拒绝的原因。测试覆盖、harness 错误、timeout、非确定性和 sandbox 差异都可能产生假阳性或假阴性；通过全部可用测试仍不能证明程序在测试之外语义正确。

**结果检查不能认证过程质量。** Countdown 合法性检查和代码执行只验证其 parser 与 tests 覆盖范围内的结果，不能判断 rationale 是否忠实、某个搜索分支是否必要、解释是否安全或程序是否稳健。二元筛选还会删除对审计或对比监督有价值的失败轨迹。论文没有发布接受率、拒绝原因、重复率或轨迹长度分布。

**划分与污染证据不完整。** Countdown 的未见目标划分降低了直接目标记忆风险，却没有审计结构模板复用。CodeContests 因训练混合中含同源题而被明确视为近分布。论文与核验仓库均未披露 SYNTHETIC-1、APPS、CodeContests、TACO 和 CodeForces 之间的去污染流程，也未给出精确来源版本与各来源数量。

**发布复现性仍为 partial。** 代码以 Apache-2.0 发布并提供命令，但核验仓库没有 tag 或 release、生成 rollout buffer、checkpoint、record manifest 或冻结环境镜像。仓库许可证不会自动决定上游题目、参考程序和生成派生物的权利。直接训练复用因此仍被阻塞，需先完成冻结快照、谱系与重叠审计和许可证核验；当前更适合作为实现配方与审计参考。

**实验范围较窄。** 证据只覆盖四数字 Countdown 与带可执行测试的 Python 代码自修复。代码增益中等，episode-level guidance 无法定位细粒度代码子目标，代码任务也没有 PPO 实验。主结果没有 error bar，总生成成本未披露；基准提升不能被当作每条入选轨迹都高质量或可广泛复用的证明。
