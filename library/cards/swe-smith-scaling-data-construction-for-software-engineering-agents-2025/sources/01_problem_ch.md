仓库级软件工程智能体所需的训练对象,不只是问题描述和参考修改。可用于后训练的样本还需要可执行的仓库状态、能够区分故障与修复的测试、智能体交互轨迹,以及足以重放结果的来源信息。较早的 SWE 风格数据通常先寻找历史问题,再为每个任务搭建环境;这会反复产生环境构建成本,也限制了单个仓库能够提供的任务数量。

SWE-smith 改变了构造单元:先让某个仓库提交可执行,再在共享环境中生成数百到数千个合成修复任务。论文将该流程用于 128 个 Python 仓库,报告保留 50,137 个任务。每个任务从一个会破坏原有正确行为的 diff 开始;执行确定哪些原本通过的测试变为失败后,流程才生成对应的修复问题描述。

因此,本 Card 严格区分三类对象:合成任务行、智能体对该任务的一次尝试,以及用于监督微调的成功轨迹子集。同时还区分"测试可验证"与"现实性"。某个修改能够在可见仓库测试下制造故障并被修复,说明它满足可执行契约,但并不能单独证明问题描述像真实维护工作、没有解法泄漏,或适合作为留出评测集。
