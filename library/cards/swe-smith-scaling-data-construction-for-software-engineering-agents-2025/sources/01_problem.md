Repository-level software-engineering agents need more than issue text and a reference edit. Useful post-training examples require an executable repository state, tests that distinguish broken from repaired behavior, an agent interaction trace, and enough provenance to replay the outcome. Earlier SWE-style collections usually identified historical issues first and then built an environment for each task. That makes environment construction a repeated bottleneck and limits the number of tasks that can be harvested from one repository.

SWE-smith changes the unit of construction. It first makes one repository commit executable, then produces hundreds or thousands of synthetic repair tasks inside that shared environment. The paper applies this process to 128 Python repositories and reports 50,137 retained tasks. Each task begins with a diff that introduces a regression into code that was previously covered by passing tests; the repair issue is generated only after execution identifies which tests fail.

The Card therefore separates three objects that are easy to conflate: the synthetic task row, an agent attempt on that task, and the successful trajectory subset used for supervised fine-tuning. It also separates test-backed validity from realism. A patch that breaks and then can be repaired under the visible repository tests satisfies an executable contract, but this alone does not show that its issue text resembles real maintenance work, that it has no leakage, or that it is suitable as a held-out benchmark.
