GitTaskBench asks whether code agents can do more than emit a patch or answer a repository issue: can they understand an unfamiliar repository, establish its runtime, write or modify code, execute it, and deliver a task-specific artifact that a program can check? The formal record is the AAAI-26 proceedings paper published in 2026. The stable atlas ID remains `gittaskbench-2025` because the work first appeared as arXiv:2508.18993 in 2025; the year and venue in canonical metadata follow the formal AAAI publication.

The benchmark covers 54 tasks associated with 18 GitHub repositories, spanning seven application domains and 24 subdomains. Outputs may be files, text, or visual artifacts rather than patches alone. A released task ties a natural-language description and prompt to a repository, a working subdirectory, input files, an expected output location, configuration, optional ground truth, and a task-specific test script. This makes the evaluation object an environment-bound task plus its terminal checker, not merely an instruction/answer pair. (AAAI paper, pp. 2–4; arXiv Appendix A)

Its decision boundary is important for this atlas. The benchmark is relevant to `environment_agent_trajectory_data` because repository state, dependency installation, execution, output delivery, and terminal predicates determine the episode outcome. However, neither official release is a canonical trajectory corpus: evaluated agents necessarily produce interactions, and the extended paper discusses selected OpenHands events and failure cases, but the confirmed artifacts do not publish normalized per-step actions and observations for the benchmark runs. The Card therefore treats GitTaskBench as an evaluation harness and task release, with `training_use` restricted to evaluation.

The L4 content boundary is also explicit. The formal paper, arXiv appendix, project page, fixed GitHub commit, fixed Hugging Face revision, representative task/config/grader files, and release tree counts support a detailed description of the data object and feedback contract. They do not establish complete replay: upstream repository commits, container digests, a run manifest, full rollout retention, benchmark-wide licensing, and contamination controls remain unknown. Inclusion is warranted because these missing fields are themselves central audit concerns for environment-mediated reasoning evaluation, not because the reported scores prove the tasks or graders are high quality.
