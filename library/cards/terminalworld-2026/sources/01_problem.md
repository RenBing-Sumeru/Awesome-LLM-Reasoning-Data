TerminalWorld was submitted as arXiv:2605.22535v1 on 2026-05-21. It addresses a specific evaluation gap: command-line agents are often tested on short, curated tasks, whereas public terminal sessions contain longer and less standardized work whose environment, successful end state, and tests are not already packaged. The paper converts such recordings into executable tasks rather than treating the original shell transcript as a gold trajectory (Paper §§1 and 3; Appendix A).

The construction starts from 80,870 public asciinema recordings, filters them to 9,492 candidates, reproduces 5,035 environments whose cleaned reference solutions exit successfully, and admits 1,530 tasks after state-based test validation. The release also contains a manually checked 200-task `verified` configuration and a 20-task `sample` configuration; all three Hugging Face configurations are test-only. These figures describe successive gates, not three interchangeable dataset sizes (Paper §§3.1–3.4 and 4.1–4.2; official Hugging Face dataset card and manifest).

A released task is an executable bundle: `task.toml`, `instruction.md`, `solution/`, `tests/`, and `environment/`. The current top-level manifest records `task_id`, `instruction`, `artifact_path`, `requires_docker`, `terminal_domain`, `source_type`, `pii_status`, and `license`. During evaluation, the agent receives the instruction and Docker terminal, issues shell actions, observes terminal responses and state changes, and receives task-level success only from the final programmatic test suite. The released object is therefore a task/environment/verifier package, not a corpus of paper-evaluation trajectories with step-level correctness labels.

This boundary places TerminalWorld in `environment_agent_trajectory_data`: environment state transitions and the terminal predicate are part of the reasoning-data contract. It does not establish a training recipe or authorize converting reference solutions into SFT/RLVR targets. Appendix C.1 says no models were trained or fine-tuned, and the dataset card describes evaluation use.

The bilingual Card has L4 content depth for screening, but canonical metadata remains at the accepted `L3_summary_ready`. The paper snapshot, stable README, and live manifest disagree on whether there are 18, 19, or 20 categories; the dataset license surfaces conflict; current records omit the paper-described `source_url`; and neither the production construction recipe nor immutable cold replay is pinned. Those unresolved facts prevent an evidentiary upgrade.
