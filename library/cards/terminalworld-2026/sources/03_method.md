**Inputs and filtering.** The pipeline begins with 80,870 public asciinema recordings represented during collection by `.txt` transcripts and metadata. It removes PII, credentials, malicious commands, TUI/GUI interaction, non-Docker-reproducible or inaccessible/proprietary/Windows-dependent sessions, short or trivial activity, and low-signal recordings. An LLM scores state-action alignment, task complexity, and signal clarity; 9,492 recordings remain. Exact production model assignments, prompts, thresholds, retry policy, and decoding settings are only partly disclosed (Paper §3.1 and Appendix A; released `data_filtering/` code).

**Instruction and reference solution.** An LLM distills each retained transcript into a goal-focused instruction without procedural hints and adds explicit output-path requirements when artifacts must persist. A second synthesis step rewrites the transcript into a cleaned Bash reference solution, removing failed or redundant commands and redirecting outputs as needed. Public users authored the source behavior; the synthesized reference is a construction artifact, not a teacher-labeled optimal trajectory (Paper §3.2; released `task_synthesis/` scripts).

**Environment reconstruction.** A coding agent generates Dockerfile/docker-compose artifacts, builds each environment, and replays the reference solution. The paper reports 5,035 environments reaching a zero-exit replay state. This gate establishes that the cleaned solution can execute in the reconstructed substrate; it does not establish that the intended task semantics are satisfied (Paper §3.3).

**Test generation and admission.** State-based tests are generated from persistent pre/post conditions and artifacts, avoiding volatile identifiers such as timestamps and PIDs. A candidate is admitted only when the reference passes all tests, no-op fails all tests, and every truncated/ablated partial solution fails at least one test; otherwise the artifacts are repaired or discarded within the construction budget. The final `full` release has 1,530 tasks. Four authors with more than three years of terminal-development experience non-randomly selected 200 diverse, complex, longer, nontrivial tasks, replayed solutions stepwise, repaired artifacts, and cross-reviewed instruction/test/artifact alignment for `verified` (Paper §§3.4 and 4.2).

**Released records.** The official Hugging Face configurations are `full` (1,530 test rows), `verified` (200 test rows), and `sample` (20 test rows), with no train/validation splits. A current manifest row has eight fields: `task_id`, `instruction`, `artifact_path`, `requires_docker`, `terminal_domain`, `source_type`, `pii_status`, and `license`; all 1,530 checked rows set `requires_docker=true`, `source_type=public_terminal_recording`, `pii_status=filtered`, and record-level `license=CC-BY-NC-4.0`. Each task archive holds `task.toml`, `instruction.md`, `solution/`, `tests/`, and `environment/`.

**Evaluation.** The paper evaluates only Verified-200, using eight models, six agent scaffolds, and Harbor in pass@1-style runs. Harbor supplies the isolated Docker terminal and records shell interaction; the task tests determine terminal success, while harness/environment errors are tracked separately. The documented configuration disables networking with `network_mode: none`. Appendix C.1 says the authors did not train or fine-tune a model, so the supported use is evaluation only.

**Production-recipe and replay boundary.** Released scripts currently expose defaults including `claude-haiku-4-5-20251001` for instruction/solution synthesis, `claude-sonnet-4-6` for test generation, temperatures/max tokens of 0.1/2048, 0.5/2048, and 0.6/4096, up to 30 turns/USD 1.50 for environment building, and up to 40 turns/USD 3.00 plus five refinement iterations for tests. These are code defaults, not proof of the production recipe that created the 1,530 tasks. Reproduction must pin arXiv v1, Git commit `784698ba93735470ce1664bff2ec44bcd7b28e15`, HF commit `dda7c099cc076735aef28c03bf8d3624dc0564e1`, task archives, base-image digests, package mirrors, cache/build policy, Harbor/agent versions, prompts, models, seeds, retries, and repair/discard logs. No immutable manifest binds that full stack.
