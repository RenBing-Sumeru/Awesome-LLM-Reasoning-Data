Direct LLM judges produce one holistic answer; majority-vote baselines execute a fixed set of perspectives; ordinary MCTS commonly uses UCT and a learned or self-evaluation reward. MCTS-Judge makes the action space a set of code-review perspectives, adds a local history-conditioned LLM gate to global UCT, and constructs a terminal signal through generated tests plus repeated line-by-line simulated execution. This differs from execution-based verification because no candidate code is actually run in the stated reward mechanism.

For the atlas, the direction signal is that judge search produces reusable state-action and trajectory-value objects only if the complete tree and reward provenance are preserved. The test-generation and simulated-execution branches are especially important because the reward's apparent precision depends on them. MCTS, UCT, generated unit tests, majority voting, and LLM self-assessment are established components; novelty lies in their task-specific assembly for test-time code judging. Benchmark gains should not be converted into a blanket quality label for intermediate analyses, generated cases, or reward values.
