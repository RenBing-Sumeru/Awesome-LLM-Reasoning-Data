For the Data Construction and Open Release Recipes track, GVM is an implementable recipe for deciding where an expensive online rollout budget goes. It is most relevant when prompts have heterogeneous success rates, the current policy can generate on-policy traces, and a reasonably reliable programmatic outcome checker is available.

A replication should treat the allocation ledger as a first-class data release. Preserve source/item IDs, oracle and checker version, policy checkpoint, prompt template, seed, every pilot and additional response, extracted answer, verifier output, `p_i`, gradient layer/reduction and `G_i`, `alpha/beta`, global budget, integer `n_i`, accepted/rejected status, replay/group membership, optimizer step, tokens, verifier calls, backward passes, wall-clock, and hardware.

The paper supports matched experiments comparing uniform, pass-rate-only, gradient-only, and combined allocation. Report accepted-example counts and pass@n alongside Average@8, and factor allocation from `N'`, clipping, negative-sample use, model size, and refresh frequency. A robust follow-up should also add parser adversarial tests, process-validity audits, zero-accept handling, and semantic contamination checks.

Reuse class: the code and algorithm are suitable as a research implementation or audit reference under their own dependencies and licenses. The work is not safe for direct training-data reuse because no paper-run trace package, item-level lineage, complete source manifest, or data license is released. Benchmark results should guide hypothesis selection, not certify the unavailable records.
